This guide is a reference for the tools you use in every assignment: the **terminal** you type commands into, the **editor** you write code in, and **Git**, the system that saves and syncs your work. You do your work on the OSU ENGR servers; connecting to them for the first time is covered in the first recitation, and this page covers what you do once you are there.

## The Terminal

A terminal is a program that lets you control a computer by typing commands instead of clicking. It can do everything a graphical file explorer can, and more, which is why it is the everyday tool of software work.

Every modern operating system ships with one:

- **Windows**: open the Start menu, search for "powershell", and launch it.
- **macOS**: open Spotlight (the magnifying glass), search for "terminal", and launch it.
- **Linux**: use whichever terminal you prefer.

### The Prompt

The **prompt** marks where you type. A typical one looks like this:

```shell title="A shell prompt"
user@hostname:~$
```

It carries some context at a glance:

- `user`: the account you are logged in as.
- `hostname`: the computer you are connected to (useful when you work on several).
- `~`: your current working directory. A `~` means your home directory; it may instead show a path like `/var/log`.
- `$`: a normal user. A `#` would mean elevated (superuser) permissions.

Two features save a lot of typing: press **Tab** to auto-complete a file or command name, and press the **up arrow** to bring back previous commands.

## Getting Around with Shell Commands

A terminal always operates inside one folder, called the **working directory**, just like a file explorer shows one folder at a time. Most of what you do is move between directories and act on the files in them.

A **path** names the location of a file or directory, with `/` separating the parts: `A/B/C.py` is the file `C.py` inside `B` inside `A`. Paths come in two kinds, plus a few shortcuts:

- An **absolute path** starts from the root, `/`, and gives the full location (`/nfs/stak/users/<ONID>/A/B/C.py`).
- A **relative path** starts from your current working directory (`A/B/C.py`).
- `.` is the current directory, `..` is the parent directory, and `~` is your home directory.

The commands you will use constantly:

| Command | What it does |
|---|---|
| `pwd` | Print the working directory (where you are now). |
| `ls <path>` | List the files in a directory (the working directory if `<path>` is left off). |
| `cd <path>` | Change into a directory. `cd ..` goes up one level; `cd` alone returns to your home directory. |
| `mkdir <path>` | Make a new directory. `mkdir -p A/B/C` makes any missing parent folders too. |
| `cp <src> <dst>` | Copy a file. `cp -r <src> <dst>` copies a whole directory. |
| `mv <src> <dst>` | Move a file or directory, or rename it. |
| `rm <path>` | Delete a file. `rm -r <path>` deletes a whole directory. |
| `cat <path>` | Print a file's contents to the terminal. |
| `clear` | Clear the terminal screen. |

Every command follows the same shape:

```shell title="Command structure"
command [options] [arguments]
```

The **command** is the program to run (`ls`). **Options** (or flags) change how it behaves and usually start with a dash: `ls -l` lists in long format, and short flags can combine, as in `ls -lh`. **Arguments** are what the command acts on, such as file or directory names: `cp file1.py file2.py backup/`.

## Editing Files

You edit files on the servers with **vim**, a text editor that runs entirely in the terminal. It has its own way of moving and typing that is worth learning early; the [Vim Cheat Sheet](/practicalities/vim/) has the keys you need to open a file, make changes, and save and quit. On your own computer you may also use a graphical editor such as VS Code, but knowing enough vim to edit a file over a terminal connection is a basic skill this course expects.

## Git

Imagine finishing ninety percent of a program, making one last change, and watching everything break the day it is due, with no working version to fall back on. **Git** exists to prevent that. It is a version control system: it records snapshots of your files over time, called **commits**, so you can always recover a working version and see what changed. It is a command-line tool, pre-installed on the ENGR servers.

### Configure It Once

Before your first commit, tell Git who you are. It stamps this on every commit you make. Run these once, with your own name and email:

```bash title="One-time Git setup"
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

You can confirm the settings with `git config --list`.

### Get a Repository

A **repository** (repo) is a directory Git is tracking. In this course you start each assignment from a repository that already exists online, and you **clone** it to make a local copy you can work in:

```bash title="Clone a repository"
git clone <repository-url>
```

This creates a new directory named after the repo. `cd` into it and run `ls` to see the files. Every clone holds the full history, so you can work offline and sync when you are ready.

### The Everyday Cycle

Inside a repo, `git status` is the command you run most: it tells you what has changed.

```bash title="See what changed"
git status
```

Every file in a repo is in one of four states: **untracked** (Git does not know about it yet), **modified** (tracked and changed since the last commit), **staged** (marked to go in the next commit), or **committed** (saved and unchanged). Saving your work is a three-step rhythm:

```bash title="Stage, commit, push"
git add hello.py          # stage the files you want to save
git commit -m "Describe the change"   # save a snapshot locally
git push                  # sync your commits to the online repo
```

You **stage** the files whose changes you want to keep with `git add` (name the files, or a directory to stage everything under it). You **commit** them with `git commit -m`, where the message is a short sentence describing the change; keep commits small and frequent. At this point the snapshot lives only on your machine, so you **push** it to the online repo with `git push`. Going the other way, `git pull` brings down changes from the online repo into your local copy.

<Aside type="tip" title="Push often">
A commit you have not pushed exists only on the servers you made it on. Push whenever you reach a working point: it is how you back up your work and avoid last-minute surprises.
</Aside>

Two more commands are worth knowing. `git log` shows the history of commits, newest first, each with its author, time, and message. `git diff <file>` shows the exact lines you have changed since the last commit, with removed lines marked `-` and added lines marked `+`. Git has many more commands (for undoing commits, or for branching), but clone, status, add, commit, push, and pull are all you need for this course.
