Six weeks into the cruise to Mars, the crew keeps the habitat's daily safety checks running exactly the way they will once nobody on Earth can talk you through a bad call. Flight software leans on a family of interlocks: small yes-or-no checks that decide whether a suit is safe to don, whether a hatch is safe to open, and whether the habitat as a whole is running normally, needs attention, or needs it right now. HAB, the habitat's assistant, has already drafted one of these checks. Your job is to write the interlock functions the rest of the checks depend on, and to catch HAB's mistake before it clears something that is not actually safe.

## How This Assignment Works

You write the functions named below and nothing else: the program's `main`, its input, its output, and the local test runner are already written, and the automated grader calls your functions directly with values it chooses, reading only what you `return`. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your functions to the grader from the course starter repository, as described in [Running and Submitting Your Code](/practicalities/starter-repo-and-check/). The assignment has four parts: the problem set below, a paper trace, a two-sentence reflection, and an optional summit problem.

## Problem Set

### Problem 1: The Suit Check, and One of HAB's Drafts

**Context.** Suits stay staged and ready throughout the cruise so the donning drill is second nature before the first Mars EVA. Before a suit is cleared for a drill, flight software checks its oxygen tank level, its battery charge, and whether its pressure seal reads intact.

**Requirements.**

1. `oxygen_ok(oxygen_percent)` must return `true` when `oxygen_percent` is at least `20`, the minimum flight rules allow before a suit counts as safe to don.
2. `battery_ok(battery_percent)` must return `true` when `battery_percent` is at least `30`.
3. `suit_ready(oxygen_percent, battery_percent, seal_intact)` must return `true` only when all three checks hold at once: `oxygen_ok(oxygen_percent)` is `true`, `battery_ok(battery_percent)` is `true`, and `seal_intact` is `true`. It must call the two functions above rather than repeating their comparisons.

The modeling step is deciding that suit readiness needs all three yes-or-no checks to hold at once, joined with `and`; the analysis step is calling `oxygen_ok` and `battery_ok` from inside `suit_ready`, pushing and popping their stack frames as the [Scope and the Call Stack](/lectures/scope-and-the-call-stack/) lecture described, and combining what they return with `seal_intact`.

### Problem 2: The Airlock Interlock

**Context.** Once a week the crew drills moving between the habitat's two pressurized modules through the connecting corridor, which holds about six cubic meters of air. Before the inner hatch may open, flight software checks that the connecting valve has equalized pressure across both sides and that the valve itself is fully closed, with no venting in progress.

**Requirements.**

1. `pressure_equalized(pressure_diff_kpa)` must return `true` when the pressure difference across the valve sits strictly between `-0.5` and `0.5` kilopascals, the tolerance flight rules allow before the two sides count as equalized. A difference of exactly `0.5` or exactly `-0.5` does not count as equalized.
2. `hatch_can_open(pressure_diff_kpa, valve_closed)` must return `true` only when `pressure_equalized(pressure_diff_kpa)` is `true` and `valve_closed` is `true`.

### Problem 3: The System Status Check

**Context.** The crew display in the command module has room for a single number, not a sentence, so flight software condenses three subsystem checks, power, comms, and life support, into one status code: `0` for nominal, `1` for advisory, and `2` for critical.

**Requirements.**

1. `system_status(power_ok, comms_ok, life_support_ok)` must return `2` whenever `life_support_ok` is `false`, no matter what `power_ok` or `comms_ok` read, since a life-support failure outranks everything else.
2. Otherwise, it must return `1` when `power_ok` is `false` or `comms_ok` is `false` (or both).
3. Otherwise, when all three inputs are `true`, it must return `0`.

The modeling step is choosing the priority order among the three subsystems, life support first, then power and comms together, then nominal; the analysis step is writing that priority as nested `if`/`else` blocks, since `elif` chains are not on the ladder yet, checking the highest-priority condition first and only asking about the others once it has ruled that one out.

## Paper Practice

Trace this program by hand, on paper. Build a variable table: for the call to `is_low_power`, write the value its `battery_percent` parameter holds and what it returns; then, for `check_drill_status`, write the values bound to its two parameters, to `low_power`, and to `result`. Write the exact value the program prints. Photograph your table and trace and attach it. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.

```python title="trace_me.py"
def is_low_power(battery_percent):
    return battery_percent < 25

def check_drill_status(oxygen_percent, battery_percent):
    low_power = is_low_power(battery_percent)
    if oxygen_percent >= 20 and not low_power:
        result = 1
    else:
        result = 0
    return result

status = check_drill_status(22, 18)
print(status)
```

<Reveal label="Reveal the completed trace">
The call `check_drill_status(22, 18)` pushes a frame with `oxygen_percent = 22` and `battery_percent = 18`. Inside it, `is_low_power(18)` pushes a second frame with `battery_percent = 18`, computes `18 < 25`, and returns `true`; that frame is popped, and `true` is bound to `low_power` in `check_drill_status`'s own frame.

| Line | frame | `oxygen_percent` | `battery_percent` | `low_power` | `result` |
|---|---|---|---|---|---|
| `is_low_power(18)` called | `is_low_power` | | `18` | | |
| `return battery_percent < 25` | `is_low_power` | | `18` | | (returns `true`) |
| `low_power = is_low_power(battery_percent)` | `check_drill_status` | `22` | `18` | `true` | |
| `if oxygen_percent >= 20 and not low_power:` | `check_drill_status` | `22` | `18` | `true` | |
| `result = 0` | `check_drill_status` | `22` | `18` | `true` | `0` |

The condition checks `22 >= 20`, which is `true`, `and`ed with `not low_power`, which is `not true`, or `false`. `true and false` is `false`, so the `if` block is skipped and the `else` block runs, binding `result` to `0`. The program prints `0`.
</Reveal>
