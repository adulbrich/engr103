WRO's annual air-quality inventory is built from a year of raw reading lines the field network has been sending in, one line per reading, in the fixed format the archive has always used. Not every line arrives clean: a station drops a character mid-transmission, or a byte flips somewhere on the way in. Your job as a junior engineer on the office's software team is to write the one function that reads an incoming line, decides whether it can be trusted, and folds every trustworthy reading into the year's running station manifest as the lines come in.

## The Problem

The [Sensor Drift Check](/assignments/sensor-drift-check/) assignment fixed the field archive's reading line: one line per reading, three fields in a fixed order with no separator between a field and its own characters, `station_id,code,reference_ugm3`. `station_id` is always exactly six characters. `code` is always exactly three base-36 characters, the reading's whole number of micrograms per cubic meter, most significant character first: the ten characters `0` through `9` stand for the values zero through nine, and the lowercase letters `a` through `z` continue counting from there up through `z`, which stands for thirty-five. `reference_ugm3` is the only field with no fixed width: it holds either a decimal number or the letters `NA`, the archive's sentinel for a station with no co-located reference monitor.

The [Field Logger Codes](/assignments/field-logger-codes/) assignment built the function that packs a reading into that three-character `code`. `log_reading` is the piece of the pipeline that finally reads one back: the same base-36 mapping, run in the other direction, turning three characters back into the number they stand for. That earlier assignment could only ever look at `code` one character at a time, because a whole string could not yet be a function parameter. Now that a list and a string can both be handed to a function, `log_reading` can take the whole line at once and finish the job that the codec started.

Write `log_reading(manifest, line)`. First decide whether `line` is a **valid reading**: it is at least twelve characters long, the character at position 6 (counting from zero) is a comma, the character at position 10 is also a comma, and each of the three characters at positions 7, 8, and 9 is a valid base-36 digit character, one of `0` through `9` or a lowercase letter `a` through `z`. When `line` is not a valid reading, the function must return exactly the string `REJECTED` and leave `manifest` completely unchanged.

When `line` is a valid reading, the six characters at positions 0 through 5 are its `station_id`, and the three characters at positions 7 through 9 are its `code`. Decode `code` back into the whole number it stands for: the character at position 7 carries the largest share of the value, position 9 the smallest, the same order `code_for` built it in. The function must then append the entry `station_id:reading_ugm3` to the end of `manifest`, with `reading_ugm3` written as a plain whole number, and return the report line `LOGGED station_id reading_ugm3`, its three pieces separated by single spaces.

`log_reading` changes the caller's `manifest` in exactly this one case, and only by adding to it; it never removes or reorders anything already there. How you walk the line's characters, and what intermediate values you give names to along the way, is entirely your decision.

**Assumptions and edge cases.** `line` may be any string at all, including the empty string; only a line with the exact shape above counts as valid. `reference_ugm3`, everything after position 10, is guaranteed to be either the letters `NA` or a decimal number whenever `line` is otherwise well-formed, but your function does not need to parse its value, only confirm that something is there. A reading decoded from a valid `code` always falls between `0` and `46655` inclusive: a shorted, negative reading is never packed into a `code` in the first place, so decoding a valid `code` never produces a negative value. No uppercase letter is ever a valid `code` character, exactly as in Field Logger Codes's `digit_value`. `manifest` may already hold any number of entries, including none, and a logged entry is always appended after whatever is already there, never in place of it. WRO's air-quality network currently reports through 84 active field stations across the district.

<WhatDiffers>
<Fragment slot="differs">
Two real differences show up here. First, how a list reaches a function at all: in Python a list is shared the moment you pass it, so a plain `manifest.append(...)` inside the function changes the caller's list with no special syntax anywhere, while Rust spells the sharing out in the type, `manifest: &mut Vec<String>`, and the caller must write `&mut` at the call site too. Second, how you reach a character by position: Python indexes a string directly, `line[7]`, and hands back the character. Rust refuses to index a string with an integer at all; you first collect it into a list of characters, `let chars: Vec<char> = line.chars().collect();`, and index that instead, `chars[7]`.
</Fragment>
</WhatDiffers>

## Paper Practice

Trace this program by hand, on paper. It is the aliasing pattern from the [Sharing and Mutation](/lectures/sharing-and-mutation/) lecture: `backup` is set to `daily`, which gives the one list a second name rather than making a second list. Build a variable table with a row for each line, tracking what `daily` and `backup` each hold after that line runs. Then write the exact two values the program prints.

```python title="trace_me.py"
def log_note(notes, text):
    notes.append(text)

daily = ["calibration ok"]
backup = daily
log_note(daily, "sensor swapped")
print(daily)
print(backup)
```

<Reveal label="Reveal the completed trace">
The line `backup = daily` does not copy the list; it makes `backup` a second name for the very same list object, so anything that changes one is seen through the other.

| Line | `daily` after | `backup` after |
|---|---|---|
| `daily = ["calibration ok"]` | `["calibration ok"]` | (not yet bound) |
| `backup = daily` | `["calibration ok"]` | `["calibration ok"]` (same list, second name) |
| `log_note(daily, "sensor swapped")` | `["calibration ok", "sensor swapped"]` | `["calibration ok", "sensor swapped"]` |

`log_note` appends `"sensor swapped"` to the one shared list, so the change shows through both names even though `log_note` returns nothing at all. The program prints `['calibration ok', 'sensor swapped']`, then the exact same list again. Rust prints a `Vec<String>` the same way, `["calibration ok", "sensor swapped"]`, with no display difference here since every value is a string, never a float.
</Reveal>

## Equity Critique

This part is not code. Write about one page (roughly 300 to 500 words) critiquing the coverage of the tool you just built: the station manifest `log_reading` folds valid readings into.

Regulatory air-quality monitors, the kind whose readings show up as a station's `reference_ugm3`, are not spread evenly across a region. A 2024 analysis of the EPA's own Air Quality System monitoring network found that under the tightened 2024 PM2.5 annual standard, coverage gaps leave roughly forty-four percent of urban areas that exceed the standard undetected, about 20 million people in all, and that the people living in those undetected hotspots are substantially more likely to be people of color or low-income than the U.S. population overall (Wang, Marshall, and Apte, "U.S. Ambient Air Monitoring Network Has Inadequate Coverage under New PM2.5 Standard," *Environmental Science & Technology Letters*, 2024). A neighborhood with no station nearby never produces a line for `log_reading` to read at all, and it never appears in the manifest, `LOGGED` or `REJECTED`, either way.

Your one page must address all three of these:

1. **What the manifest assumes.** `log_reading` reports a whole number of micrograms per cubic meter for every station that sends it a valid line, and it reports nothing for anywhere else. Describe, specifically, what a reader of the finished manifest would have to already believe about where WRO's stations sit in order to read that manifest as a complete picture of air quality across the district.
2. **Where it fails, and how.** Name the concrete mechanism by which the manifest goes wrong for a place with no station: is the gap visible to whoever reads the manifest, or does it look identical to a place that was checked and found clean? Be specific about what in `log_reading`'s own behavior produces that outcome.
3. **Whom it fails, and what closing the gap would take.** Using the source above or one you find yourself, describe who is more likely to live somewhere the network does not cover. Then describe one real change that would narrow the gap, and name the trade-off it carries: more stations to fund and maintain, a different siting rule that costs the easiest locations, or something else. A fix with no trade-off at all is a sign you have not looked closely enough.

This critique is graded on completion, evaluated on whether it genuinely engages with all three points, not on whether the instructor agrees with your conclusions. It is not shared with anyone but the instructor.
