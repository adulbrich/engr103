Touchdown is confirmed, and the rover is cleared to drive down the ramp for its first traverse across the landing site. The ramp deployment itself took forty-three seconds, a detail for the mission log and nothing your functions need. Before the wheels turn, flight software needs three things: a running budget of how much battery the drive will cost, a warning for when the charge gets low, and a scan of the ground ahead for spots the descent thrusters kicked dust onto. Your job as the flight-software crew member on shift is to write the functions that produce those numbers, one loop at a time. HAB has already drafted one of them; do not trust it until you have checked it yourself.

## How This Assignment Works

You write the functions named below and nothing else: the program's `main`, its input, its output, and the local test runner are already written, and the automated grader calls your functions directly with values it chooses, reading only what you `return`. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your functions to the grader from the course starter repository. ## Problem Set

### Problem 1: The Battery Budget for the Traverse

**Context.** The rover's battery does not drain at a constant rate over the whole drive: the ground gets rockier as the traverse goes on, so each step pulls a little more charge than the last.

**Requirements.**

1. `total_battery_used(steps, base_drain, wear_rate)` must return the total percent of battery capacity used across `steps` whole drive steps, as a float. Number the steps starting from `1`, not `0`. Step `n` drains `base_drain + wear_rate * n` percent, and the total is the sum of every step's drain from step `1` through step `steps`. For example, with `base_drain` `2.0` and `wear_rate` `0.5`, step `1` drains `2.5`, step `2` drains `3.0`, step `3` drains `3.5`, and so on: `total_battery_used(3, 2.0, 0.5)` sums those three and returns `9.0`. A `steps` of `0` means the rover has not moved yet, so the total is `0.0`.
2. `remaining_charge_after(start_charge, steps, base_drain, wear_rate)` must return the battery charge left after `steps` drive steps: `start_charge` minus the total that `total_battery_used` would return for the same `steps`, `base_drain`, and `wear_rate`.

The modeling step is deciding that a step's drain grows with its position in the traverse rather than staying fixed; the analysis step is accumulating that per-step drain with a `for` loop over the range of step numbers, then reusing the total to find what charge is left.

<Aside type="tip" title="The loop variable is a whole number, the drain is a float">
Your loop variable `n` walks a range of whole numbers, but `wear_rate * n` mixes a float with that whole number. Python converts a whole number to a float automatically wherever one is needed, so `wear_rate * n` just works. Rust does not: multiplying an `f64` by an `i32` is a type error, so you must convert the loop variable yourself before the multiplication.
</Aside>

<WhatDiffers>
<Fragment slot="differs">
Python's `wear_rate * n` mixes a float and an int without complaint, because Python converts the int for you. Rust has no implicit conversion between `f64` and `i32`, so the loop variable must be cast explicitly, `n as f64`, before it can multiply against a `f64`. Forgetting the cast is a compile error in Rust, not a wrong answer, so the mistake is caught before the program ever runs.
</Fragment>
</WhatDiffers>

### Problem 2: How Many Steps Until the Battery Runs Out, and One of HAB's Drafts

**Context.** On a flatter stretch of ground the drain per step holds steady instead of growing. Mission control wants to know, before the rover sets out, how many complete steps it can take before the next one would push the charge below zero.

**Requirements.**

1. `steps_until_empty(start_charge, drain_per_step)` must return the number of whole drive steps the rover can complete before taking one more step would drop the charge below `0.0`. A step counts as completed if the charge remains at or above `0.0` after it is taken; a reading of exactly `0.0` still counts as a completed step.

The modeling step is deciding that a step is allowed only if the battery can still cover it, landing at or above zero, not merely above zero; the analysis step is a `while` loop that checks the remaining charge before committing to each step.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="HAB's draft"
def steps_until_empty(start_charge, drain_per_step):
    charge = start_charge
    count = 0
    while charge > 0.0:
        charge = charge - drain_per_step
        count = count + 1
    return count
```
</TabItem>
<TabItem label="Rust">
```rust title="HAB's draft"
fn steps_until_empty(start_charge: f64, drain_per_step: f64) -> i32 {
    let mut charge = start_charge;
    let mut count = 0;
    while charge > 0.0 {
        charge = charge - drain_per_step;
        count = count + 1;
    }
    return count;
}
```
</TabItem>
</Tabs>

For `steps_until_empty(10.0, 3.0)`, HAB's draft returns `4`, not `3`. Work out why before you open the hint, then write the correct version yourself.

<Reveal label="Reveal a nudge on HAB's mistake">
HAB's loop checks whether the charge is still positive *before* taking a step, then takes the step no matter how much charge is left. On the pass where `charge` is `1.0`, `1.0 > 0.0` is true, so the loop takes another full step and drains the charge to `-2.0`, counting a step the battery could not actually supply. The loop stops one step too late. The fix is to check whether the charge can *survive* the next step before committing to it, which is what `charge - drain_per_step >= 0.0` asks, rather than checking whether the charge is merely still positive right now.
</Reveal>
</Aside>

### Problem 3: The First Low-Battery Warning

**Requirements.**

## Paper Practice

Trace this program by hand, on paper. Build a variable table with a row for each pass of the `while` loop, tracking `n`, `cost`, `used`, and `charge`. Write the exact values the program prints. Photograph your table and trace and attach it. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.

```python title="trace_me.py"
def step_cost(base, wear, n):
    return base + wear * n

charge = 20.0
base = 2.0
wear = 1.0
n = 1
used = 0.0
while n <= 3:
    cost = step_cost(base, wear, n)
    used = used + cost
    charge = charge - cost
    n = n + 1
print(used, charge)
```

<Reveal label="Reveal the completed trace">
Each pass computes this step's cost, adds it into `used`, subtracts it from `charge`, and then advances `n`.

| Pass | `n` at start of pass | `cost` | `used` after | `charge` after |
|---|---|---|---|---|
| 1 | `1` | `3.0` | `3.0` | `17.0` |
| 2 | `2` | `4.0` | `7.0` | `13.0` |
| 3 | `3` | `5.0` | `12.0` | `8.0` |

After the third pass, `n` becomes `4`, and the condition `n <= 3` is false, so the loop ends. The program prints `12.0 8.0`. The same program written in Rust prints its two whole-valued `f64`s without the trailing zero, `12 8`.
</Reveal>
