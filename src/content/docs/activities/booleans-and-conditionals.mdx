## Predict the Compound Short-Circuit

The lecture showed short-circuiting with a single operator, where the left operand alone obviously settles the result. Real conditions stack `and`, `or`, and `not` together with comparisons, and then two things at once become hard to call: what the whole line reduces to, and whether the function on the right ever runs. This section makes you commit to both before you run anything.

Read the program below and, on paper or in a comment, write down every line it prints and the order they print in. Do not run it yet. Watch out for two things. First, precedence: a comparison like `x == 7` reduces to a boolean before `not` touches it, `not` binds tighter than `and`, and `and` binds tighter than `or`, so `a or not b and c` groups as `a or ((not b) and c)`. Second, the side effect: `touch` prints `touched` every time it actually runs, so decide for each line whether short-circuiting reaches it at all.

```python title="predict.py"
def touch():
    print("touched")
    return True

x = 7
print(x < 0 or not x == 7 and touch())
print(x > 5 and (touch() or x < 0))
```

<Reveal label="Reveal the real output and reconcile it with your prediction">
```bash title="Run the Python program"
python3 predict.py
```

```text frame="terminal" title="Output"
False
touched
True
```

Take the first line, `x < 0 or not x == 7 and touch()`, and group it by precedence into `(x < 0) or ((not (x == 7)) and touch())`. The left side of the `or` is `x < 0`, which is `7 < 0`, so `false`; a `false` left operand does not settle `or`, so the right side runs. On that right side, `x == 7` is `true`, `not true` is `false`, and now `false and touch()` has a `false` left operand, which already settles `and` at `false`, so `touch` is skipped and `touched` never prints for this line. The whole line is `false or false`, which is `False`. So the first thing printed is `False`, with no `touched` before it.

The second line, `x > 5 and (touch() or x < 0)`, starts with `x > 5`, which is `true`; a `true` left operand does not settle `and`, so the right side runs. Inside the parentheses, `touch()` is the left operand of the `or`, so it runs now: it prints `touched` and returns `True`. A `true` left operand already settles `or`, so `x < 0` on its right is skipped, and the parenthesized part is `True`. The line is `true and true`, which is `True`. So the second line prints `touched` first, then `True`.

If you predicted `touched` twice, you evaluated a right operand that short-circuiting had already cut off; if you predicted the first line as `True`, you let the `and` win over the `or` instead of grouping `or` last. Rust's `&&`, `||`, and `!` short-circuit and combine the same way, so the equivalent program, with the boolean parts parenthesized explicitly, prints `false`, then `touched`, then `true`.
</Reveal>

## A Zero Float as a Condition

The lecture put a nonzero integer where a condition belongs, and Python happily ran the `if` branch. The interesting case is the other one: a value that Python treats as **falsy**, so it quietly takes the `else` branch instead of failing. A reading of `0.0` is a real measurement, not a missing one, yet Python's truthiness rule throws it away. You read both tabs and name what genuinely changes and what stays fixed.

Study the two programs below. They are the same `if`/`else`, with a float that happens to be `0.0` where the condition goes. Before opening the reveal, predict what each one prints, or whether it prints at all, then name one thing that is truly different between the languages and one thing that is the same.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="truthy.py"
readings = 0.0
if readings:
    print("sensor active")
else:
    print("no signal")
```
</TabItem>
<TabItem label="Rust">
```rust title="truthy.rs (will not compile)"
fn main() {
    let readings: f64 = 0.0;
    if readings {
        println!("sensor active");
    } else {
        println!("no signal");
    }
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the outputs and what differs">
```bash title="Run the Python program"
python3 truthy.py
```

```text frame="terminal" title="Output"
no signal
```

```bash title="Compile the Rust program"
rustc truthy.rs
```

```text frame="terminal" title="Output"
error[E0308]: mismatched types
 --> truthy.rs:3:8
  |
3 |     if readings {
  |        ^^^^^^^^ expected `bool`, found `f64`
```

<WhatDiffers>
<Fragment slot="differs">
Python decides at run time: its truthiness rule counts `0.0` as falsy, exactly as it counts the integer `0` and the empty string as falsy, so it skips the `if` block and prints `no signal`. Nothing errors, and that is the trap: a legitimate zero reading is silently treated as no reading. Rust decides while compiling: it never treats a float as standing in for a boolean, so it rejects the identical line before the program runs, reporting `E0308`, mismatched types, `expected bool, found f64`, and building nothing. What stays fixed is the source: both are written as the same two-branch `if`/`else` with the same `0.0` condition. What changes is whether that float is allowed to be the condition at all, so Python runs the wrong-looking branch and Rust never runs either.
</Fragment>
</WhatDiffers>

To make the Rust version compile, give `if` an actual boolean by writing the comparison Python was leaving implicit. If the rule you meant was "any reading at all," the honest condition is not truthiness but something like `readings != 0.0`, and once you write it out you can see the design question Python hid from you: is a reading of exactly `0.0` active or not? Rust forces you to answer it; Python answered `no signal` on your behalf.
</Reveal>

## Fix the Guard That Never Fires

A range check is one line of code and a favorite place for a silent bug: the program runs, prints a plausible message, and quietly lets the wrong values through. The guard below is meant to reject any reading outside 0 to 100, but a reading of `150` sails past it. You find the bug with the systematic method: read the symptom, form a hypothesis, test it.

Run the program, see which branch it takes for a clearly out-of-range reading, then work out why the guard never catches it.

```python title="guard.py"
reading = 150
if reading < 0 and reading > 100:
    print("out of range")
else:
    print("in range")
```

<Reveal label="Reveal the diagnosis and the fix">
```bash title="Run the buggy program"
python3 guard.py
```

```text frame="terminal" title="Output"
in range
```

**Symptom.** There is no error. The reading is `150`, which is plainly outside 0 to 100, yet the program prints `in range` and takes the branch meant for good readings. The wrong branch is the only signal you get.

**Hypothesis.** The guard `reading < 0 and reading > 100` must be reducing to `false` even for `150`. Read it as English: it fires only when the reading is below `0` *and* above `100` at the same time. No single number is both negative and above one hundred, so `and` can never see two `true` operands, and the condition is `false` for every possible reading. Printing the guard directly for two out-of-range values confirms it never fires:

```python title="probe.py"
print(150 < 0 and 150 > 100)
print(-5 < 0 and -5 > 100)
```

```bash title="Run it"
python3 probe.py
```

```text frame="terminal" title="Output"
False
False
```

Both are `False`. For `150`, the left half `150 < 0` is `false`; for `-5`, the right half `-5 > 100` is `false`; either way `and` needs both halves and never gets them. The guard is dead code that always falls through to `else`.

**Test.** The rule is "out of range if the reading is below `0` *or* above `100`," so the operator should be `or`, not `and`. A reading is bad when it fails *either* boundary, and `or` fires as soon as one operand is `true`:

```python title="guard.py (fixed)"
reading = 150
if reading < 0 or reading > 100:
    print("out of range")
else:
    print("in range")
```

```bash title="Run the fixed program"
python3 guard.py
```

```text frame="terminal" title="Output"
out of range
```

Now `150 > 100` is `true`, so `or` settles at `true` and the guard finally catches the bad reading. The lesson is that `and` where `or` was meant produces no crash, just a condition that is silently always false, so a guard that never rejects anything is the symptom to watch for. This is a logic error, not a type error, so it hides just as well in Rust: the same guard written with `&&` compiles without complaint and prints `in range` too. The compiler cannot tell you that you asked the wrong question.
</Reveal>

## Write a Safe-Range Check

Write a function `in_safe_range` that takes a temperature and returns `True`/`true` when it is at least 18 and at most 26, and `False`/`false` otherwise. Build the condition from two comparisons joined with `and`/`&&`, the way the range check earlier in the lecture did. Print the result for a temperature of `20` and for a temperature of `30`.

<Reveal label="Reveal a sample solution">
More than one correct solution exists; this is a sample.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="saferange.py"
def in_safe_range(temp):
    return temp >= 18 and temp <= 26

print(in_safe_range(20))
print(in_safe_range(30))
```
</TabItem>
<TabItem label="Rust">
```rust title="saferange.rs"
fn in_safe_range(temp: i32) -> bool {
    return temp >= 18 && temp <= 26;
}

fn main() {
    println!("{}", in_safe_range(20));
    println!("{}", in_safe_range(30));
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 saferange.py
```

```text frame="terminal" title="Output"
True
False
```

```bash title="Compile and run the Rust program"
rustc saferange.rs
./saferange
```

```text frame="terminal" title="Output"
true
false
```

`20` clears both boundaries, at least `18` and at most `26`, so both comparisons hold and `and`/`&&` reduces to `True`/`true`. `30` fails the upper boundary, so the second comparison is `False`/`false`, and `and`/`&&` reduces to `False`/`false` regardless of the first comparison.
</Reveal>
