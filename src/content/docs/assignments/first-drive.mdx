Touchdown is confirmed, and the rover is cleared to drive down the ramp for its first traverse across the landing site. The ramp deployment itself took forty-three seconds, a detail for the mission log and nothing your functions need. Before the wheels turn, flight software needs three things: a projection of how much charge the parked rover's solar array will bank over the coming sols, a budget of how many drive steps the battery can afford and when to warn the crew, and a scan of the ground ahead for spots the descent thrusters kicked dust onto. Your job as the flight-software crew member on shift is to write the functions that produce those numbers, one loop at a time. HAB has already drafted one of them; do not trust it until you have checked it yourself.

## How This Assignment Works

You write the functions named below and nothing else: the program's `main`, its input, its output, and the local test runner are already written, and the automated grader calls your functions directly with values it chooses, reading only what you `return`. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your functions to the grader from the course starter repository. The assignment has four parts: the problem set below, a paper trace, a two-sentence reflection, and an optional summit problem.

## Problem Set

### Problem 1: Banking Charge Before the Drive

**Context.** While the rover sits parked in the sun, mission modeling treats its stored charge as growing by a fixed percentage of its current level each sol, so the charge compounds: a larger reserve gathers a larger gain the next sol. Planners want to know how much charge will be banked after a given number of sols before they commit to the drive.

**Requirements.**

1. `solar_charge_after(start_charge, growth_percent, sols)` must return the stored charge, in watt-hours, after `sols` whole sols of compounding growth, as a float. Each sol multiplies the current charge by `1 + growth_percent / 100`, so a `growth_percent` of `25` leaves the charge `1.25` times as large at the end of a sol as at its start. There is no exponentiation operator on the language ladder, so build the compounding one sol at a time with a loop rather than raising a factor to the `sols` power. A `sols` of `0` means no sols have passed, so the charge is unchanged and the function returns `start_charge`.
2. `charge_gained(start_charge, growth_percent, sols)` must return only the charge gained over those sols: the value `solar_charge_after` would return for the same `start_charge`, `growth_percent`, and `sols`, minus the `start_charge` it began with.

The modeling step is deciding that each sol's gain is a fixed fraction of the current charge, so the charge compounds rather than growing by a fixed amount; the analysis step is accumulating that growth as a running product in a loop, because the ladder has no exponentiation operator, then reusing the result to isolate the gain.

<Aside type="tip" title="Build the compounding with a loop">
This is a loops exercise, so build the compounding the loop way: start the charge at `start_charge` and multiply it by `1 + growth_percent / 100` once per sol, `sols` times over. This is the running-product form of the accumulator from the loop patterns lecture, where the accumulator starts at a value and is multiplied rather than added on each pass. Rust has no exponentiation operator at all, and although Python has `**`, reaching for it here would skip the very pattern this problem exists to practice. In both languages the loop is the point.
</Aside>

### Problem 2: How Many Steps Until the Battery Runs Out, and One of HAB's Drafts

**Context.** On a flatter stretch of ground the drain per step holds steady instead of growing. Mission control wants to know, before the rover sets out, how many complete steps it can take before the next one would push the charge below zero.

**Requirements.**

1. `steps_until_empty(start_charge, drain_per_step)` must return the number of whole drive steps the rover can complete before taking one more step would drop the charge below `0.0`. A step counts as completed if the charge remains at or above `0.0` after it is taken; a reading of exactly `0.0` still counts as a completed step.

The modeling step is deciding that a step is allowed only if the battery can still cover it, landing at or above zero, not merely above zero; the analysis step is a `while` loop that checks the remaining charge before committing to each step.

def steps_until_empty(start_charge, drain_per_step):

        count = count + 1
    return count

### Problem 3: The First Low-Battery Warning

**Context.** Mission control also wants the earliest step at which the charge would fall to a warning level, so the drive can be cut short if it comes too soon. The crew only surveys a fixed number of steps ahead, since the plan can always be recomputed later.

**Requirements.**

1. `first_warning_step(start_charge, drain_per_step, threshold, max_steps)` must return the smallest step number `n`, counting from `1` through `max_steps`, at which the charge after `n` steps, `start_charge - drain_per_step * n`, first falls to or below `threshold`. If no step from `1` through `max_steps` reaches `threshold`, return `-1`.

The modeling step is choosing `-1` as a signal meaning "no warning inside the surveyed steps," a value that can never be a real step number; the analysis step is a loop over the surveyed steps that returns the moment it finds the first one that qualifies, never checking a later step once it has.

### Problem 4: The Calibration Sweep

**Context.** Before the rover crosses the ramp's shadow, the crew scans the ground the descent thrusters may have kicked dust onto. The scan covers a grid of `rows` rows and `cols` columns, numbered from `0`. A cell's dust reading, in instrument units, is <Latex formula="3 \times row + 5 \times column" />. A cell is safe to drive across without a re-scan only if its reading is strictly below a clearance threshold.

**Requirements.**

1. `count_clear_cells(rows, cols, threshold)` must return how many of the `rows * cols` grid positions, row from `0` through `rows - 1` and column from `0` through `cols - 1`, have a dust reading of `3 * row + 5 * column` strictly less than `threshold`. The modeling step is writing the dust reading as a function of a cell's row and column instead of storing a reading per cell; the analysis step is a pair of nested loops, one for the row and one for the column, that count without keeping anything but the running count.
