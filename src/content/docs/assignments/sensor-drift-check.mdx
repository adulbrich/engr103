WRO tracks fine particle pollution, PM2.5, with a network of low-cost sensors spread across neighborhoods that a handful of expensive reference-grade monitors could never cover on their own. Every low-cost unit drifts with age and dust, so WRO co-locates a few of them next to a reference-grade monitor and checks each live reading before anyone treats it as real data. Your job as a junior engineer on the office's software team is to write the check that sorts a live reading into trusted or faulty before it reaches anyone's dashboard.

## The Problem

A reading nobody has checked cannot tell WRO anything useful. The office uses this network to watch how close a neighborhood sits to the EPA's PM2.5 National Ambient Air Quality Standard, revised in 2024 to an annual mean of 9.0 micrograms per cubic meter, with the 24-hour standard unchanged at 35 micrograms per cubic meter (EPA National Ambient Air Quality Standards, 2024 revision). Before any of that matters, each live reading has to clear a basic sanity check.

WRO's field loggers also keep a compact archive of every reading, for reporting later: one line per reading, three fields separated by commas, always in this fixed order: `station_id,code,reference_ugm3`. `station_id` is always exactly six characters, the station's short ID (for example `WRO-07`). `code` packs the sensor's own reading into a fixed three-character base-36 code, most significant character first, encoding the reading as a whole number of micrograms per cubic meter, rounded to the nearest whole unit; a shorted line has nothing valid to encode, so it is logged elsewhere and never written to this archive as a `code`. `reference_ugm3` is the co-located reference monitor's reading in the same units, written as a decimal, or the letters `NA`, the archive's only sentinel, when a station has no reference monitor installed. A deployment's agreement tolerance does not travel with each reading; it is set once when a station goes in and stays fixed after that.

For this exercise, the low-cost sensor is read live from the console, as text, the way the [Errors, Input, and Validation](/lectures/errors-input-and-validation/) lecture describes, rather than from an archive line. The provided harness already reads that live text and parses it, using exactly the `try`/`except` or `parse`-and-`match` idiom from the lecture, so text that does not parse at all (a blank line, a stray word) never reaches your function: the harness reports it as `unreadable` on its own. What does reach your function is a number, and a number can still be untrustworthy in more than one way, so the check sorts each parsed reading into a status code before anyone acts on it. `REFERENCE_UGM3` and `TOLERANCE_UGM3` are constants the harness already sets for this station, read from that station's own archive and configuration.

```python title="Provided in the harness: you do not write this"
reading_text = input("Live sensor reading (ug/m3): ")
try:
    reading = float(reading_text)
    if reading_status(reading, REFERENCE_UGM3, TOLERANCE_UGM3) == 0:
        print("trusted")
    else:
        print("rejected")
except ValueError:
    print("unreadable")
```

```rust title="Provided in the harness: you do not write this"
match reading_text.trim().parse::<f64>() {
    Ok(reading) => {

            println!("trusted");
        } else {
            println!("rejected");
        }
    }
    Err(_) => println!("unreadable"),
}
```

<WhatDiffers>
<Fragment slot="differs">
Both snippets reach the same `unreadable` outcome for garbage text, but by the two routes the errors lecture described. Python's `float` raises a `ValueError` the instant the text fails to parse, and the surrounding `try`/`except` catches it. Rust's `parse::<f64>()` never raises; it always finishes and hands back a `Result`, and the `match` reads that value and picks the `Ok` or `Err` arm. Either way, `reading_status` is only ever called once a reading has already parsed into a number.
</Fragment>
</WhatDiffers>

Write `reading_status(reading_ugm3, reference_ugm3, tolerance_ugm3)`, returning the status code for a parsed reading. What it must return, checking the conditions in this priority order:

1. Return `1` when `reading_ugm3` is below `0.0`. A reading below zero is physically impossible, and in practice a shorted sensor line reads negative, so this flags a hardware fault at the low end.
2. Otherwise, return `2` when `reading_ugm3` is above `500.0`. That is the sensor's own stated ceiling: the Plantower PMS5003 series data manual (version 2.3, 2016) lists an effective PM2.5 measurement range of 0 to 500 micrograms per cubic meter, and a reading above that ceiling means the sensor has railed high, a hardware fault the office logs separately.
3. Otherwise the reading sits inside the physically possible range, `0.0` to `500.0` inclusive. Compare it to the reference: the gap between the two readings is a size, and the pair agrees whenever that size is at or below `tolerance_ugm3`. Return `3` when they disagree, since that means at least one of the two sensors cannot be trusted.
4. Otherwise, return `0`. The reading is in range and agrees with the reference. This is the only trusted case.

The order matters: a reading is compared to the reference only after it has passed the physical-range check, so an out-of-range value is always reported as a range fault (`1` or `2`), never as a disagreement (`3`), even when it also happens to be far from the reference. The function returns a whole-number status code (`0`, `1`, `2`, or `3`). How you arrange the comparisons and what intermediate values you give names to along the way is entirely your decision.

## Paper Practice

Trace this program by hand, on paper. Build a variable table: for each call to `range_flag`, write the values held by its `value_ugm3` and `calibration_flagged` parameters and the value it returns, then the values bound to `a`, `b`, and `total`. Write the exact value the program prints.

```python title="trace_me.py"
def range_flag(value_ugm3, calibration_flagged):
    if calibration_flagged:
        return 1
    elif value_ugm3 > 500.0:
        return 2
    else:
        return 0

a = range_flag(650.0, False)
b = range_flag(650.0, True)
total = a + b
print(total)
```

<Reveal label="Reveal the completed trace">
The first call, `range_flag(650.0, False)`, binds `value_ugm3` to `650.0` and `calibration_flagged` to `False`. The chain checks `calibration_flagged` first: it is `False`, so that branch is skipped, not entered. The next condition, `value_ugm3 > 500.0`, is `True`, since `650.0` is greater than `500.0`, so the function returns `2` and the final `else` is never even looked at. That `2` is bound to `a`.

| Line | `value_ugm3` | `calibration_flagged` | returns | `a` | `b` | `total` |
|---|---|---|---|---|---|---|
| `a = range_flag(650.0, False)` | `650.0` | `False` | `2` | `2` | | |
| `b = range_flag(650.0, True)` | `650.0` | `True` | `1` | `2` | `1` | |
| `total = a + b` | | | | `2` | `1` | `3` |

The second call, `range_flag(650.0, True)`, checks `calibration_flagged` first again, and this time it is `True`, so the function returns `1` immediately; the `value_ugm3 > 500.0` condition is never evaluated at all, because the chain stops at the first branch that matches. That `1` is bound to `b`. Finally `total = a + b` computes `2 + 1`, and the program prints `3`.
</Reveal>
