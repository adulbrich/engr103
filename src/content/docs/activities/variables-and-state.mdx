This activity puts into practice the [Variables and State](/lectures/variables-and-state/) lecture. You will predict the final value of a variable after a chain of reassignments that each rebuild it from its own current value, hand-trace a two-variable swap through a temporary, and hunt down a compile error caused by trying to change a variable Rust will not let you change. By the end, you will be able to walk assignment's evaluate-then-bind steps across many lines by hand and predict a variable's stored value at any point in a program.

## Warm-up

A quick refresher before the three problems. Creating a variable attaches a name to a value, and using the name looks that value back up. Here are two variables created from bare literals and read back, in both languages.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="warmup.py"
width = 10
height = 4
print(width)
print(height)
```
</TabItem>
<TabItem label="Rust">
```rust title="warmup.rs"
fn main() {
    let width = 10;
    let height = 4;
    println!("{}", width);
    println!("{}", height);
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 warmup.py
```

```text frame="terminal" title="Output"
10
4
```

Rust prints the same two values. The one visible difference is that Rust needs the keyword `let` to create each name, where Python needs nothing but the name, an `=`, and a value. With those pieces fresh, the three problems below chain and rearrange assignments in ways a single line never shows.

## Predict the Final Value

Assignment is not equality: `total = total + 5` does not claim a number equals itself plus five, it evaluates the right side from the variable's current value and then rebinds the name. When the same variable is reassigned line after line, each step builds on the value the step before it left behind. The value you print at the end is easy to mispredict if you read `=` as a claim rather than an action, or if you reach back for a value an earlier line already overwrote. You commit to an answer first, then run the program to check it.

Read the program below and write down, on paper or in a comment, the exact value you expect the `print` to show. Do not run it yet. Walk each assignment in order: evaluate its right side from the current value of `total`, then rebind `total` to that result before moving to the next line. Watch the third line especially, where `total` appears twice on the right.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="predict.py"
total = 3
total = total + 5
total = total * total
total = total - 40
total = total * 2
print(total)
```
</TabItem>
<TabItem label="Rust">
```rust title="predict.rs"
fn main() {
    let mut total = 3;
    total = total + 5;
    total = total * total;
    total = total - 40;
    total = total * 2;
    println!("{}", total);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the real output and reconcile it with your prediction">
```bash title="Run the Python program"
python3 predict.py
```

```text frame="terminal" title="Output"
48
```

Rust prints the same `48`. Take the lines in order. Line 1 binds `total` to `3`. Line 2 evaluates `total + 5` from the current `3`, giving `8`, and rebinds `total` to `8`, so the starting `3` is gone. Line 3 is the step that trips people: `total * total` evaluates *both* copies of `total` from the same current value `8`, so it is `8 * 8`, which is `64`, not `8` times the old `3`. `total` is rebound to `64`. Line 4 evaluates `total - 40` from the current `64`, giving `24`. Line 5 evaluates `total * 2` from the current `24`, giving `48`, and that is what the `print` reads at the end. If you predicted `24` you likely stopped one line early; if you predicted a value near `40` you probably read `total * total` as leaving `total` unchanged instead of squaring it. Each line uses only the value the line before it produced, never a value an earlier line already discarded.
</Reveal>

## Trace the Swap

Swapping the values of two variables is a small task that goes wrong the instant you try to shortcut it, because the first assignment overwrites a value the second one still needs. The standard fix is a third variable, a temporary, that holds one value out of the way while the other is moved. Tracing this by hand, one variable at a time, is the surest way to see why the temporary is not optional. A **variable table** lists the value every variable holds after each line runs.

Trace the program below by hand. For each line, do both steps of the assignment: evaluate the right side from the variables' current values, then rebind the name on the left. Fill in the value of `a`, `b`, and `temp` after every line, then predict the two printed values.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="swap.py"
a = 7
b = 2
temp = a
a = b
b = temp
print(a)
print(b)
```
</TabItem>
<TabItem label="Rust">
```rust title="swap.rs"
fn main() {
    let mut a = 7;
    let mut b = 2;
    let temp = a;
    a = b;
    b = temp;
    println!("{}", a);
    println!("{}", b);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the completed table and the output">
Walk it one line at a time. Line 1 binds `a` to `7`. Line 2 binds `b` to `2`. Line 3 evaluates `a`, which is `7`, and binds `temp` to `7`: this is the copy that keeps the original `a` safe. Line 4 evaluates `b`, which is `2`, and rebinds `a` to `2`, discarding the `7` that used to be in `a`, which is fine because `temp` still holds it. Line 5 evaluates `temp`, which is still `7`, and rebinds `b` to `7`. Recording the value of each variable after each line gives the table:

| Line | Statement | `a` afterward | `b` afterward | `temp` afterward |
|---|---|---|---|---|
| 1 | `a = 7` | 7 | not yet set | not yet set |
| 2 | `b = 2` | 7 | 2 | not yet set |
| 3 | `temp = a` | 7 | 2 | 7 |
| 4 | `a = b` | 2 | 2 | 7 |
| 5 | `b = temp` | 2 | 7 | 7 |

The two `print` lines read whatever the variables hold at the end, which the table shows is `2` for `a` and `7` for `b`: the values started out `7` and `2` and are now swapped. Running the program confirms the trace, and both languages print the same two values because the assignment rules are identical and only the surrounding syntax differs:

```bash title="Run the Python program"
python3 swap.py
```

```text frame="terminal" title="Output"
2
7
```

The row that carries the whole trick is line 3. Without `temp`, line 4 would overwrite `a` with `b`'s value before anything preserved the old `a`, and the original `7` would be lost for good. In the Rust version, `a` and `b` are declared `let mut` because both are reassigned, while `temp` is a plain `let`: it is bound once on line 3 and never changed, so it needs no `mut`.
</Reveal>

## Find the Immutable Binding

Rust makes every variable immutable unless you add `mut`, so a plain `let` binding cannot be reassigned, and the compiler rejects the second assignment before the program ever runs. That is straightforward with one variable. It is a real diagnosis when several variables are in play and only one of them is at fault: the error names the culprit, but understanding why *that* line fails and the others do not means checking each declaration against what the program later does to it. You find the bug with the systematic method: read the error, form a hypothesis, test it.

The program below is meant to start a `length` at `10` and a `width` at `4`, grow the `length` by `5`, double the `width`, then print their product. It does not compile. Read it, predict which line the compiler will reject and why, then work out the one change that fixes it.

```rust title="dimensions.rs (will not compile)"
fn main() {
    let mut length = 10;
    let width = 4;
    length = length + 5;
    width = width * 2;
    let area = length * width;
    println!("{}", area);
}
```

<Reveal label="Reveal the diagnosis and the fix">
```bash title="Compile the Rust program"
rustc dimensions.rs
```

```text frame="terminal" title="Output"
error[E0384]: cannot assign twice to immutable variable `width`
 --> dimensions.rs:5:5
```

**Symptom.** There is no run at all; compiling stops with error `E0384` pointing at line 5, `width = width * 2;`, and it names `width` specifically, not `length` or `area`.

**Hypothesis.** The fix is not just "add `mut` somewhere", it is understanding why this exact line is the one that fails. Three variables are declared, and the compiler treats each according to how it was created and what the program does to it afterward:

- `length` is declared `let mut`, and line 4 reassigns it. A mutable binding is allowed to change, so that reassignment is fine.
- `width` is declared with a plain `let`, which makes it immutable, and line 5 tries to reassign it. The compiler recorded that `width` may never change, so it refuses the assignment. This is the one error.
- `area` is declared with a plain `let`, but it is never reassigned: it is bound once on line 6 and only read afterward. An immutable binding that is never changed is exactly what `let` is for, so it needs no `mut` and causes no error.

So the culprit is the one variable that is both immutable and reassigned: `width`. The fix is to allow the change at the point `width` is created, by adding `mut` right after its `let`. Leaving `area` as a plain `let` is correct, and adding `mut` to it would only earn an unused-mutability warning.

**Test.** Add `mut` to the `width` declaration so its binding may be reassigned:

```rust title="dimensions.rs (fixed)"
fn main() {
    let mut length = 10;
    let mut width = 4;
    length = length + 5;
    width = width * 2;
    let area = length * width;
    println!("{}", area);
}
```

```bash title="Compile and run the fixed program"
rustc dimensions.rs
./dimensions
```

```text frame="terminal" title="Output"
120
```

With `mut` on `width`, the compiler allows line 5: `width * 2` evaluates from the current `4` to `8`. Line 4 had already grown `length` from `10` to `15`, so `area` is `15 * 8`, which is `120`. The lesson is that immutable-by-default turns an accidental reassignment into an error caught at compile time, before a single line runs, and that finding it in a crowd of variables is a matter of matching each declaration against what the program later asks of it.
</Reveal>

## Write a Water Tank Level

A storage tank starts at `500` litres. Write a program that stores that starting level in one variable, then reassigns that same variable to subtract a `120` litre draw, then reassigns it again to subtract a `30` litre draw, then prints the final level.

<Reveal label="Reveal a sample solution">
More than one program can get this right; this is a sample solution, not the only one.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="tank.py"
level = 500
level = level - 120
level = level - 30
print(level)
```
</TabItem>
<TabItem label="Rust">
```rust title="tank.rs"
fn main() {
    let mut level = 500;
    level = level - 120;
    level = level - 30;
    println!("{}", level);
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 tank.py
```

```text frame="terminal" title="Output"
350
```

Rust prints the same `350`. `level` starts at `500`, drops to `380` after the first draw, then to `350` after the second, the same evaluate-then-bind rebinding the three problems above already walked through.
</Reveal>

## Bridge

These three reps feed the arithmetic-with-units-and-time family in recitation, where a value is stored, updated across several steps, and read back later, and one assignment taken out of order or one wrong current value quietly throws off the final answer. The evaluate-then-bind tracing you just did by hand is the guided first rung of that ladder.
