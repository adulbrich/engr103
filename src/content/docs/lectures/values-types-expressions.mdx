Suppose you ask a computer to compute 7 divided by 2. Is the answer 3, or is it 3.5? A person can answer either way depending on what the 7 and the 2 represent: a whole count of items splits differently than a precise measurement does. A computer cannot guess which one you mean. Before it can add, divide, or compare two pieces of data, it needs to know exactly what kind of data each one is.

This is true of almost everything a program touches: a whole number of students in a class, a price with cents, a yes-or-no answer to a question, a name typed by a user. Each of these is a different kind of thing, and a computer needs a name for that kind before it can work with it correctly.

## Values and Types

A program spends nearly all of its time holding, combining, and displaying small pieces of data. This section names that basic unit of data, names the label the computer attaches to it, and names the code that produces it.

### Values

A **value** is a single piece of data that a program works with: the number 7, the number 3.14, the truth of a statement, or a short piece of text. A value is the simplest thing a running program can hold or produce. When you write a value directly into your code, such as typing the number 7, that value is called a **literal**: a value written out exactly as it is, rather than computed from something else.

### Types

A **type** is a category that tells the computer what kind of value something is and what can be done with it. Knowing a value's type tells the computer how much space to use for it, how to display it, and which operations make sense on it: you can divide two numbers, but dividing two pieces of text makes no sense.

This lecture uses four types, the ones both Python and Rust make available from the very first line of code you write:

An **integer** is a whole number, with no fractional part, such as 7 or negative 3. A **float**, short for "floating-point number," is a number that can have a fractional part, such as 3.14. A **boolean** is a value that is only ever one of two things: true or false; it gets its name from the mathematician George Boole, who studied logic built from exactly two values. A **string** is a short piece of text, such as a word or a sentence, treated by the computer as data rather than as code to run.

### Expressions

An **expression** is a piece of code that produces a value when the computer runs it. The simplest possible expression is a literal on its own: the code `7` is already an expression, and running it produces the value 7. You can also build a larger expression out of smaller ones by combining values with **operators**, symbols such as `+` that take one or more values and produce a new one. A later section looks closely at operators; for now, know only this: combining values always builds a bigger expression, and every expression evaluates to a value, never to anything else.

Printing a value, which you saw in the previous lecture, works by first evaluating an expression down to a single value, then displaying that value in the terminal. Every example in this lecture follows that same pattern: write an expression, then print what it evaluates to.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Printing four kinds of values"
print(7)
print(3.14)
print(True)
print("hello")
```
</TabItem>
<TabItem label="Rust">
```rust title="Printing four kinds of values"
fn main() {
    println!("{}", 7);
    println!("{}", 3.14);
    println!("{}", true);
    println!("{}", "hello");
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Rust wraps every runnable line inside a `fn main() { ... }` function; Python does not. Rust prints with `println!` and a placeholder marker `{}` that stands for the value; Python prints directly with `print(...)`. Python spells its boolean values `True` and `False`, with a capital letter; Rust spells them `true` and `false`, all lowercase. A Rust literal can also carry an explicit type tag, such as `7i32` or `3.14f64`; this example leaves the tag off because Rust already assumes a whole-number literal is `i32` and a decimal literal is `f64` unless told otherwise. As covered in the [Data Representation and Memory](/lectures/data-representation) lecture, the `32` and `64` in those names are the number of bits Rust always sets aside for a value of that type.
</Fragment>
</WhatDiffers>

## Static Typing and Dynamic Typing

Every value has a type, but Python and Rust disagree about when that type gets checked. This difference is one of the biggest reasons the two languages feel different to write, and it shows up again in almost every later lecture.

### Static Typing

**Static typing** means a language works out the type of every value and checks that those types are used consistently before the program ever runs. Rust is statically typed: its compiler, the program that turns your source code into a runnable one, reads through your whole file and rejects it if a type does not fit where it is used, even in a line that would never actually execute. The check happens once, ahead of time, which is why it is called static.

### Dynamic Typing

**Dynamic typing** means a language decides whether a value's type makes sense for a given operation only at the moment that operation actually runs. Python is dynamically typed: it does not check the types used on a line of code until the computer actually reaches that line while running the program. If an earlier line has a problem, Python will not notice until it gets there.

You can see the difference directly. Adding a whole number to a decimal number is something Python allows without complaint, deciding on the fly that the answer should be a float:

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Adding a whole number and a decimal number"
print(3 + 2.5)
```
</TabItem>
<TabItem label="Rust">
```rust title="Adding a whole number and a decimal number"
fn main() {
    println!("{}", 7i32);
    println!("{}", 3.14f64);
    println!("{}", 3.0 + 2.5);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Python freely adds a whole number and a decimal number, resolving `3 + 2.5` to the float `5.5` the moment that line runs, without asking in advance whether the two types are allowed to mix. Rust decides each literal's type before the program runs, so this example writes each literal's type up front (`7i32`, `3.14f64`) and adds two same-typed floats instead.
</Fragment>
</WhatDiffers>

Rust will not accept the mixed-type version Python allows:

```rust title="Adding an integer literal to a float literal (will not compile)"
fn main() {
    println!("{}", 3 + 2.5); // error: cannot add a float to an integer (Rust will not compile this)
}
```

The compiler rejects this line before your program runs at all. That is what static typing means in practice: Rust confirms every type is used consistently while compiling, before your program takes its first step, while Python only confirms it line by line, while the program is already running.

## Operators and Operator Precedence

A single value on its own is not very useful; programs become powerful once values can be combined into new ones. This section names the symbol that does the combining and the rule that decides which combination happens first.

### Operators

An **operator** is a symbol that combines one or more values to produce a new value. The familiar arithmetic operators, `+`, `-`, `*`, and `/`, take two number values and produce a new number: `3 + 4` is an expression built from the operator `+` and the two values 3 and 4, and it evaluates to the value 7.

### Operator Precedence

When an expression contains more than one operator, the computer needs a rule for which operation happens first. **Operator precedence** is the set of rules a language uses to decide that order. Both Python and Rust use the same order you likely already learned for ordinary arithmetic: multiplication and division happen before addition and subtraction, and parentheses around part of an expression force that part to be evaluated first, overriding the usual order. Take `3 + 4 * 2`: multiplication happens first, so `4 * 2` is 8, then `3 + 8` is 11, in both languages. Wrapping `3 + 4` in parentheses instead forces that addition to happen first, so `(3 + 4) * 2` becomes `7 * 2`, which is 14, again in both languages.

This course tracks exactly which pieces of each language are available at each point in the term; the current list lives on the [language ladder](/reference/language-ladder) page, and this lecture stays within its first entry.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Order of operations, with and without parentheses"
print(3 + 4 * 2)
print((3 + 4) * 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="Order of operations, with and without parentheses"
fn main() {
    println!("{}", 3 + 4 * 2);
    println!("{}", (3 + 4) * 2);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Nothing about the arithmetic itself differs: the symbols `+`, `*`, and `(`...`)` are written the same way in both languages. Rust's only extra requirement is wrapping the two lines in `fn main() { ... }`.
</Fragment>
</WhatDiffers>

## Integer Versus Float Division

Division deserves its own closer look, because it is the one arithmetic operator whose exact answer often cannot be represented as a whole number.

### Integer Division

Dividing two whole numbers raises a question that addition, subtraction, and multiplication do not: what happens when the answer is not itself a whole number? **Integer division** is division between two whole numbers that produces a whole-number result instead of the exact, possibly fractional answer. Every language that does integer division has to pick its own rule for which whole number to produce, and Python and Rust pick different rules.

Python's `/` operator always produces a float, even when both values are whole numbers; it is designed to give the exact mathematical answer every time. Python has a separate operator, `//`, for integer division: it divides, then rounds down to the whole number below the exact answer.

Rust takes the opposite default. Its `/` operator performs integer division automatically whenever both values are whole numbers, discarding the fractional part. To get a precise, non-whole answer in Rust, at least one of the two values must already be a float. In neither language is this discarding a bug: it is a direct consequence of asking for a whole-number answer to a question that does not always have one.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Float division versus integer division"
print(7 / 2)
print(7 // 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="Float division versus integer division"
fn main() {
    println!("{}", 7 / 2);
    println!("{}", 7.0 / 2.0);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Python's plain `/` always gives the exact answer as a float: `7 / 2` is `3.5`. Its second operator, `//`, gives the whole-number version: `7 // 2` is `3`. Rust's plain `/` between two whole-number literals behaves like Python's `//`: `7 / 2` gives the whole number `3`, and the exact answer `3.5` needs both values written as floats, `7.0 / 2.0`. One more difference is easy to miss: for negative numbers, Python's `//` always rounds down, toward negative infinity, so `-7 // 2` gives `-4`; Rust's integer `/` always rounds toward zero instead, so `-7 / 2` gives `-3`.
</Fragment>
</WhatDiffers>

It is easy to write Python's `/` when you actually want a whole-number answer:

```python title="Division: / versus //"
print(9 / 4)   # 2.25, not 2: Python's / always gives a float
print(9 // 4)  # 2: // is the whole-number division you probably meant
```

## Evaluating Expressions by Hand

Reading an expression and working out its value in your head, or on paper, without running any code, is a skill worth building deliberately. It lets you predict what a program will do before you run it, catch a mistake in your own reasoning before it becomes a bug, and check a program's output against what you expected. Evaluating by hand means applying the same two rules from this lecture, in order: operator precedence decides which operation happens first, and each language's own division rule decides what kind of answer a division produces.

Take the expression `10 / 4 + 3 * 2`. Operator precedence says the multiplication and the division both happen before the addition, so you work out `10 / 4` and `3 * 2` first, then add the results. In Rust, `10 / 4` divides two whole numbers, so it discards the fractional part, giving `2`; `3 * 2` is `6`; adding them gives `8`. In Python, the same `10 / 4` is Python's float-producing division, so it gives `2.5`; `3 * 2` is still `6`; adding them gives `8.5`. The two languages read the exact same expression and, because of their different division rules, land on two different final values.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Evaluating 10 / 4 + 3 * 2 by hand"
print(10 / 4 + 3 * 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="Evaluating 10 / 4 + 3 * 2 by hand"
fn main() {
    println!("{}", 10 / 4 + 3 * 2);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Written out, the two expressions look identical. Python evaluates `10 / 4` as float division and prints `8.5`; Rust evaluates the same-looking `10 / 4` as integer division, since both 10 and 4 are whole-number literals, and prints `8`.
</Fragment>
</WhatDiffers>

## Takeaways

A value is a single piece of data, and every value has a type that fixes what the computer can do with it: an integer, a float, a boolean, or a string, in this lecture. A type also fixes how much memory a value costs to store, as the Data Representation and Memory lecture covered; that is why Python's arbitrary-precision `int` can grow without limit while Rust's `i32` and `f64` reserve a fixed 32 or 64 bits and stop at a largest representable value. An expression is any piece of code, from a single literal to a combination built with operators, that evaluates down to one such value. Python and Rust agree completely on what a value and a type are; they disagree on timing, checking types dynamically while a program runs versus statically before it runs, and that one disagreement is why Rust's compiler catches certain mistakes that Python would only discover later, mid-run. Operator precedence gives both languages the same order of operations you already know from arithmetic, so an expression with more than one operator evaluates the same way in either language, once you know each language's own rule for what dividing two whole numbers produces. Practicing hand evaluation, working out an expression's value before running it, turns all of these rules into a skill you can use to predict, and later debug, real programs. The next lecture builds directly on this one: it looks at how to give a value a name, so that it can be reused and changed instead of rewritten every time it is needed.
