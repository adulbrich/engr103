This activity puts into practice the [Loop Patterns](/lectures/loop-patterns/) lecture. You will predict the final value of an accumulator that walks a range, trace a nested loop by hand to count how many times its inner body runs, and fix a sentinel loop that quietly folds its stop value into the total. By the end, you will be able to read a loop, name which pattern it is, and say what it keeps across passes and what makes it stop.

## Warm-up

A quick refresher before the blocks. The accumulator has three parts in three places: you create the variable before the loop, update it on every pass, and read it after. Here is the smallest version, summing `1` through `3`, in both languages.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="warmup.py"
total = 0
for n in range(1, 4):
    total = total + n
print(total)
```
</TabItem>
<TabItem label="Rust">
```rust title="warmup.rs"
fn main() {
    let mut total = 0;
    for n in 1..4 {
        total = total + n;
    }
    println!("{}", total);
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 warmup.py
```

```text frame="terminal" title="Output"
6
```

The range `range(1, 4)` and `1..4` are half-open: they walk `1, 2, 3` and stop before `4`. So `total` climbs `0`, `1`, `3`, `6`, and the `print` after the loop reads `6`. With that skeleton fresh, the blocks below make the final value harder to guess.

## Block 1: Predict the Accumulator's Final Value

An accumulator's whole story is in one variable, but two easy slips make its final value hard to guess: the range stops one short of its top number, and here each pass adds `n` squared, not `n`. You commit to a value first, then run the program to check it.

Read the program below and write down, on paper or in a comment, the exact number you expect it to print. Do not run it yet. Trace `total` pass by pass: list which values `n` takes, square each one, and add it in.

```python title="predict.py"
total = 0
for n in range(1, 5):
    total = total + n * n
print(total)
```

<Reveal label="Reveal the real output and reconcile it with your prediction">
```bash title="Run the Python program"
python3 predict.py
```

```text frame="terminal" title="Output"
30
```

The range `range(1, 5)` is half-open, so `n` walks `1, 2, 3, 4` and never reaches `5`. Each pass adds `n * n`, so `total` climbs `0`, then `0 + 1` is `1`, then `1 + 4` is `5`, then `5 + 9` is `14`, then `14 + 16` is `30`. After the last pass the loop ends and `print` reads `30`.

Two predictions are the common misses. If you wrote `55`, you almost certainly included `n` of `5`, adding `25` to `30`: the range stops before its top number, so `5` never arrives. If you wrote `10`, you added `n` itself instead of `n` squared, `1 + 2 + 3 + 4`. The Rust version walks the same range `1..5` and adds `n * n`, so it prints `30` as well.
</Reveal>

## Block 2: Trace the Grid and Count the Passes

A nested loop runs its inner body once for every combination of the outer and inner variables, so the pass count is the product of the two ranges, not their sum. This program adds a counter into the inner body of a multiplication table, and you predict its final count by hand before running it.

```python title="table.py"
count = 0
for row in range(1, 4):
    for col in range(1, 5):
        count = count + 1
        print(row * col, end="\t")
    print()
print("Cells:", count)
```

Trace the program above on paper. The outer loop walks `row` over `1, 2, 3`, and for each row the inner loop walks `col` over `1, 2, 3, 4`. Follow these steps.

<Steps>

1. Set `count` to `0` and `row` to `1`. Walk `col` over `1, 2, 3, 4`, adding `1` to `count` each time, and write down the four products `row * col`.

2. Move to `row` of `2`, then `row` of `3`, doing the same each time.

3. Write down the value of `count` after the last pass, and the grid of products you produced.

</Steps>

<Reveal label="Reveal the completed trace, the grid, and the pass count">
The inner body runs four times per row, once for each column, and there are three rows, so it runs <Latex formula="3 \times 4 = 12" /> times in all. Trace `count` row by row: it enters `row` of `1` at `0` and leaves it at `4`; `row` of `2` lifts it from `4` to `8`; `row` of `3` lifts it from `8` to `12`. The products form the table.

```bash title="Run the Python program"
python3 table.py
```

```text frame="terminal" title="Output"
1	2	3	4
2	4	6	8
3	6	9	12
Cells: 12
```

The Rust version nests the same two ranges and prints the same grid and `Cells: 12`. Had the grid been square, say `3` by `3`, the count `9` would also read as `3` squared and hide the rule; the non-square `3` by `4` makes it plain that the inner body runs once per cell and the pass counts multiply.
</Reveal>

## Block 3: Fix the Sentinel That Counts Itself

A sentinel loop reads values until a designated stop value appears, and the order of its two steps is not free to rearrange: it must check for the sentinel before treating the value as data. The program below reads whole numbers and sums them until it reads `-1`, but it prints the wrong total. You find the bug with the systematic method: read the symptom, form a hypothesis, test it.

The program is meant to sum the numbers before the sentinel. For the input `3`, `5`, `2`, `-1`, the correct total is `10`. Run it with that input, see what it actually prints, then work out why the value is wrong and how one change fixes it.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="sentinel.py"
total = 0
while True:
    number = int(input())
    total = total + number
    if number == -1:
        break
print("Total:", total)
```
</TabItem>
<TabItem label="Rust">
```rust title="sentinel.rs"
use std::io;

fn main() {
    let mut total = 0;
    loop {
        let mut line = String::new();
        io::stdin().read_line(&mut line).expect("failed to read line");
        let number: i32 = line.trim().parse().expect("please enter a whole number");
        total = total + number;
        if number == -1 {
            break;
        }
    }
    println!("Total: {}", total);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the diagnosis and the fix">
```bash title="Run the buggy Python program"
printf '3\n5\n2\n-1\n' | python3 sentinel.py
```

```text frame="terminal" title="Output"
Total: 9
```

**Symptom.** There is no error message; the program runs and prints `Total: 9`, but the sum of `3`, `5`, and `2` should be `10`. The wrong number is the only signal you get.

**Hypothesis.** The result is short by exactly `1`, and `1` is what you get by adding the sentinel `-1` into the total: `3 + 5 + 2 + (-1)` is `9`. So the guess is an ordering bug. The body runs `total = total + number` before it checks `if number == -1`, so on the pass that reads `-1` the value is folded into the total before the `break` fires. The sentinel is being treated as data.

**Test.** Move the sentinel check ahead of the update, so a value that stops the loop is never added:

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="sentinel.py (fixed)"
total = 0
while True:
    number = int(input())
    if number == -1:
        break
    total = total + number
print("Total:", total)
```
</TabItem>
<TabItem label="Rust">
```rust title="sentinel.rs (fixed)"
use std::io;

fn main() {
    let mut total = 0;
    loop {
        let mut line = String::new();
        io::stdin().read_line(&mut line).expect("failed to read line");
        let number: i32 = line.trim().parse().expect("please enter a whole number");
        if number == -1 {
            break;
        }
        total = total + number;
    }
    println!("Total: {}", total);
}
```
</TabItem>
</Tabs>

```bash title="Run the fixed Python program"
printf '3\n5\n2\n-1\n' | python3 sentinel.py
```

```text frame="terminal" title="Output"
Total: 10
```

```bash title="Compile and run the fixed Rust program"
rustc sentinel.rs
printf '3\n5\n2\n-1\n' | ./sentinel
```

```text frame="terminal" title="Output"
Total: 10
```

The fix is to swap the order of two lines, so the check for the sentinel comes before the addition. Note that a sentinel of `0` would have hidden this bug, because folding `0` into a sum changes nothing; the non-zero sentinel `-1` is what makes the mistake show as a wrong total.
</Reveal>

## Bridge

These three reps feed the recitation family that runs a loop to build up a value or a grid and has to stop at exactly the right moment: an accumulator whose final value depends on which items the range includes, a nested loop whose inner body runs once per cell, and a sentinel read that must turn the stop value away before it reaches the total. The hand-tracing and the one-line fix you just practiced are the guided first rung of that ladder.
