Good style does not change what your code does. It changes how easily a person can read it. In this course a person will read your code often: a teaching assistant grading it, a partner working beside you, and you yourself, coming back to a program a week after you wrote it. Code that is clean and consistent is code that is easy to read, easy to check, and easy to fix.

This page collects the style rules ENGR 103 uses in Python and Rust. Most of the rules exist for one reason: readability. When a rule feels like extra work, remember that the reader you help most is future you.

## The Golden Rule

Be consistent, and write for a first-year reader. If you name one variable `total_score`, do not name the next one `totScr`. If you put a blank line between two functions, put a blank line between every pair of functions. A reader learns your habits as they read; consistent habits let them predict what comes next, so they can think about your logic instead of your formatting.

The good news is that most of this consistency can be handled for you by a tool. The last section of this page shows how to set up a formatter that fixes spacing, indentation, and line breaks every time you save. Learn the rules first, so you understand what the tool is doing, then let the tool do it.

## Naming

A name is the first thing a reader sees, so a good name saves them from reading the rest. Both Python and Rust share the same three naming rules in this course.

- Use `snake_case` for variables and functions: lowercase words joined by underscores, like `total_score` or `average_speed`.
- Use `UPPER_CASE` for constants: capital letters with underscores, like `MAX_STUDENTS` or `SPEED_LIMIT`.
- Choose descriptive names. A name should say what the value is or what the function does.

Prefer a clear name over a short one. `radius` reads better than `r`, and `student_count` reads better than `n`. A name that describes its value removes the need for a comment that would have explained it.

Use one name for one idea. If a value is the user's score, call it `score` everywhere. Do not call it `score` in one place and `points` in another; a reader cannot tell whether the two names mean the same thing, so they have to stop and check.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Descriptive names"
SPEED_LIMIT = 65

def average_speed(total_distance, total_time):
    return total_distance / total_time
```
</TabItem>
<TabItem label="Rust">
```rust title="Descriptive names"
const SPEED_LIMIT: i32 = 65;

fn average_speed(total_distance: f64, total_time: f64) -> f64 {
    return total_distance / total_time;
}
```
</TabItem>
</Tabs>

Notice that the same three rules produce almost the same names in both languages. The `snake_case` functions, the `snake_case` parameters, and the `UPPER_CASE` constant all look the same. Rust adds a type to each parameter and to the return, and Python does not; the naming style is shared.

<Aside type="tip" title="Names the tools expect">
Both languages' standard tools already assume these conventions. Rust's compiler prints a warning if you write a function or variable in anything but `snake_case`, or a `const` in anything but `UPPER_CASE`. Python's linter, `ruff`, flags the same patterns. Following the conventions keeps your tools quiet.
</Aside>

## Layout and Formatting

Layout is the shape of your code on the page: where the indentation goes, how long a line is, and where the blank lines fall. A consistent shape lets a reader find things without searching.

**Indentation.** Use four spaces per level in both languages. Do not use tab characters. Set your editor to insert spaces when you press the Tab key. In Python, indentation is not optional: it is how the language knows which lines belong to a function or a loop. In Rust the curly braces mark those blocks, but you still indent four spaces inside them so the structure is easy to see.

**Line length.** Keep lines short enough to read without scrolling sideways. The tools set a sensible default for you: `black` and `ruff` wrap Python at 88 columns, and `rustfmt` wraps Rust at 100 columns. You do not have to count characters yourself; the formatter does it. Just avoid writing one enormous line that the formatter then has to break in an awkward place.

**Spacing.** Put one space around operators and one space after each comma. Write `a + b`, not `a+b`, and `average(x, y)`, not `average(x,y)`. The spaces separate the pieces so the eye can find them.

**Blank lines.** Put a blank line between two functions, and use blank lines inside a function to group steps that belong together. Do not scatter blank lines at random; a blank line should mean "a new step starts here."

Here is a small function formatted the way this course expects, in both languages.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Clean layout"
def rectangle_area(width, height):
    area = width * height
    return area

def rectangle_perimeter(width, height):
    perimeter = 2 * (width + height)
    return perimeter
```
</TabItem>
<TabItem label="Rust">
```rust title="Clean layout"
fn rectangle_area(width: f64, height: f64) -> f64 {
    let area = width * height;
    return area;
}

fn rectangle_perimeter(width: f64, height: f64) -> f64 {
    let perimeter = 2.0 * (width + height);
    return perimeter;
}
```
</TabItem>
</Tabs>

The Python blocks end with a colon and an indented body. The Rust blocks use curly braces, with the opening brace on the same line as the function signature and the closing brace on its own line. You do not have to remember the fine details of where a brace goes: `rustfmt` places it for you.

## Comments

A comment explains something the code cannot say on its own. The best comment answers the question "why," not "what." A reader can already see *what* a line does; what they often cannot see is *why* you wrote it that way.

Do not comment the obvious. A comment like `# add one to count` above `count = count + 1` only repeats the code and adds nothing. Save comments for a formula that is not obvious, a rule from the assignment, or a choice a reader might question.

Each language has a short comment marker for a single line: `#` in Python, `//` in Rust. Each also has a way to describe a whole function. In Python that is a **docstring**, a string on the first line of the function body, written in triple quotes. In Rust that is a **doc comment**, written with `///` on the lines just above the function.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Documenting a function"
def celsius_to_fahrenheit(celsius):
    """Convert a Celsius temperature to Fahrenheit."""
    # Multiply by 9/5, then shift the freezing point to 32.
    return celsius * 9 / 5 + 32
```
</TabItem>
<TabItem label="Rust">
```rust title="Documenting a function"
/// Convert a Celsius temperature to Fahrenheit.
fn celsius_to_fahrenheit(celsius: f64) -> f64 {
    // Multiply by 9/5, then shift the freezing point to 32.
    return celsius * 9.0 / 5.0 + 32.0;
}
```
</TabItem>
</Tabs>

One short description of what the function does, plus a note on the one line that is not obvious, is enough. If a function needs a long comment to explain what it does, that is often a sign the function is doing too much, which the next section addresses.

## Functions

A function should do one thing. If you can describe a function's job with a single short sentence, it is probably the right size. If your description needs the word "and" two or three times, the function is probably doing too much, and you should split it into smaller functions.

Small functions are easier to name, easier to read, and easier to reuse. They also keep your indentation shallow. Deeply nested code, an `if` inside a loop inside another `if`, is hard to follow because the reader has to hold every condition in their head at once. Pulling an inner block out into its own function flattens the nesting and gives that block a name.

Write an explicit `return` when a function produces a value. Rust also lets you return a value by writing it as the last line with no `return` keyword and no semicolon, called a trailing expression, and you will meet that form in real Rust code. This course writes an explicit `return` so the point where the value is handed back is easy to see.

Compare a cluttered function with a clean one. Both compute the same thing.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Cluttered: too much in one function"
def report(width, height):
    a = width * height
    if a > 0:
        if width == height:
            print("Square area:", a)
        else:
            print("Rectangle area:", a)
    return a
```
</TabItem>
<TabItem label="Rust">
```rust title="Cluttered: too much in one function"
fn report(width: f64, height: f64) -> f64 {
    let a = width * height;
    if a > 0.0 {
        if width == height {
            println!("Square area: {}", a);
        } else {
            println!("Rectangle area: {}", a);
        }
    }
    return a;
}
```
</TabItem>
</Tabs>

This function computes an area, tests for a square, and prints, all at once, and it nests two `if` blocks to do it. Splitting the calculation and the square test into their own functions makes each piece short and clear.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Clean: one job per function"
def rectangle_area(width, height):
    return width * height

def is_square(width, height):
    return width == height
```
</TabItem>
<TabItem label="Rust">
```rust title="Clean: one job per function"
fn rectangle_area(width: f64, height: f64) -> f64 {
    return width * height;
}

fn is_square(width: f64, height: f64) -> bool {
    return width == height;
}
```
</TabItem>
</Tabs>

Each function now has one job and a name that states it. The nesting is gone, and either function can be reused on its own.

## Language-Specific Notes

The rules above apply to both languages. A few points apply to only one.

### Python

Python's community style guide is called PEP 8, and the rules on this page follow it: four-space indentation, `snake_case` names, `UPPER_CASE` constants, and spaces around operators. The formatter `black` and the linter `ruff` both enforce PEP 8 for you, so you rarely need to read it directly.

This course writes Python **without type annotations**. You will not write `def area(radius: float) -> float`. Leaving the types off is a deliberate choice for a first course: it keeps the syntax simple while you learn the ideas. Do not add type hints to your Python, even if a tool or an AI assistant suggests them.

Use f-strings to build text from values. Writing `f"Area: {area}"` is clearer than joining pieces with `+`, and it is the style this course prefers.

Avoid one-letter names like `x`, `n`, or `t` for values that have a real meaning. A loop counter can be short, but a value that represents a student's score should be called `score`.

### Rust

Keep your Rust `rustfmt`-clean: run the formatter and let it decide spacing, indentation, and line breaks. Code that is already formatted is easier for a partner or a grader to read, because it looks like every other Rust file they have seen.

Create a variable with `let`, and add `mut` only when the variable really needs to change: `let mut count = 0`. Reaching for `mut` by default hides which values are meant to stay fixed. Leave a variable immutable unless you have a reason not to.

Rust has a second linter, `clippy`, that suggests clearer or more idiomatic ways to write something. When `clippy` points at a line, read its suggestion: it often teaches a cleaner pattern than the one you wrote. You do not have to accept every suggestion, but you should understand each one.

<Aside type="note" title="Explicit return in this course">
Experienced Rust programmers often drop the final `return` and let the last expression be the value. That is valid Rust and you will see it everywhere. This course still writes the explicit `return` in its examples so that beginners can see exactly where a value leaves a function. Either form is correct.
</Aside>

## Formatters and Linters

A **formatter** rewrites your code into a standard shape: it fixes indentation, spacing, and line breaks without changing what the code does. A **linter** reads your code and points out likely mistakes and unclear patterns, such as an unused variable or a needlessly complex expression. Together they handle most of the consistency this page asks for, so you can spend your attention on logic.

Set up format-on-save in your editor and you will almost never have to think about layout again: every time you save, your code snaps into the standard shape.

### Python: black and ruff

`black` is a formatter, and `ruff` is a fast linter that can also format. Install both with `pip`.

```bash title="Install black and ruff"
pip install black ruff
```

Format a file with `black`, and check it for problems with `ruff`.

```bash title="Format and lint a Python file"
black my_program.py
ruff check my_program.py
```

`ruff` can format too, if you prefer one tool for both jobs. `ruff format` follows the same style as `black`.

```bash title="Format with ruff instead"
ruff format my_program.py
```

### Rust: rustfmt and clippy

`rustfmt` is the formatter and `clippy` is the linter. Both come with Rust; add them with `rustup` if they are missing.

```bash title="Add rustfmt and clippy"
rustup component add rustfmt clippy
```

In a Cargo project, run them with `cargo`.

```bash title="Format and lint a Cargo project"
cargo fmt
cargo clippy
```

If you are compiling a single file with `rustc`, format that file directly with `rustfmt`.

```bash title="Format a single Rust file"
rustfmt my_program.rs
```

### Editor Setup

Every editor below can run these tools automatically when you save. The idea is the same in each: install the language support, turn on format-on-save, and point Python at `ruff` (or `black`) and Rust at `rustfmt`.

#### VS Code

Install three extensions from the marketplace: **Python** (`ms-python.python`), **Ruff** (`charliermarsh.ruff`), and **rust-analyzer** (`rust-lang.rust-analyzer`). Then add this to your `settings.json`.

```json title="VS Code settings.json"
{
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff",
    "editor.formatOnSave": true,
    "editor.codeActionsOnSave": {
      "source.fixAll.ruff": "explicit",
      "source.organizeImports.ruff": "explicit"
    }
  },
  "[rust]": {
    "editor.defaultFormatter": "rust-lang.rust-analyzer",
    "editor.formatOnSave": true
  }
}
```

This formats Python with `ruff` and Rust with `rustfmt` (through rust-analyzer) every time you save.

#### Zed

Zed has built-in language support: it uses `ruff` for Python and `rust-analyzer` for Rust once those tools are installed on your system. Turn on format-on-save per language in `settings.json`.

```json title="Zed settings.json"
{
  "languages": {
    "Python": {
      "format_on_save": "on",
      "language_servers": ["ruff"],
      "formatter": {
        "language_server": { "name": "ruff" }
      }
    },
    "Rust": {
      "format_on_save": "on"
    }
  },
  "lsp": {
    "rust-analyzer": {
      "initialization_options": {
        "check": { "command": "clippy" }
      }
    }
  }
}
```

The `lsp` block also tells rust-analyzer to run `clippy` when it checks your Rust code, so you see lint warnings as you work.

#### Vim / Neovim

The simplest setup uses the [conform.nvim](https://github.com/stevearc/conform.nvim) plugin to format on save. Point Python at `ruff_format` and Rust at `rustfmt`.

```lua title="Neovim: format on save with conform.nvim"
require("conform").setup({
  formatters_by_ft = {
    python = { "ruff_format" },
    rust = { "rustfmt" },
  },
  format_on_save = {
    timeout_ms = 500,
    lsp_format = "fallback",
  },
})
```

If you would rather not add a plugin, and you already have a language server running, you can format through the built-in LSP on every save with one autocommand.

```lua title="Neovim: format on save with the built-in LSP"
vim.api.nvim_create_autocmd("BufWritePre", {
  pattern = { "*.py", "*.rs" },
  callback = function()
    vim.lsp.buf.format()
  end,
})
```

For linting, run `ruff` and `clippy` from the terminal, or connect them through a language-server plugin such as `nvim-lspconfig` if you want warnings inline.

<Aside type="tip" title="Let the tool do the work">
Once format-on-save is on, stop hand-adjusting spacing and line breaks. Write your logic, save, and let the formatter shape the file. Your job is clear names, small functions, and comments that explain why; the tool handles the rest.
</Aside>
