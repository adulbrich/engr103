The launch window is the short span when the burn can begin, and Mission Control needs a small console readout before it opens. The readout carries three things: the countdown split into whole minutes and the leftover seconds, the fuel load once a safety margin is added on top of the base propellant, and the number of automated supply runs the station must fly to erase a fixed mass deficit before departure. The habitat carries a crew of four. Your job as flight software crew is to complete the program that prints these numbers for the console.

## How This Assignment Works

You work **test first**, the way flight software is really written: you read the problem, decide what correct behavior looks like by writing your own test cases, plan the program in pseudocode, and only then write the code. You have not learned to write your own functions yet, so the contract is the program's **printed output**: the automated grader runs your program and compares the lines it prints to the expected lines. The problem is solvable in Python or Rust, whichever you prefer, against the same expected output. The order is fixed: design your tests, write your pseudocode, then complete the program. After that comes an optional extra-credit stretch, a short paper trace, and a two-sentence reflection.

## What to Submit

You submit in two places. Mechanics are in [Running and Submitting Your Code](/practicalities/starter-repo-and-check/); each section below also repeats what it asks for.

- **A single PDF on Canvas** holding everything that is not code: your **acceptance tests**, your **pseudocode**, your **paper trace**, and your **reflection**.
- **Your code on Gradescope**: the completed program, plus the extra-credit surplus program if you attempt the summit.

## The Problem

The console readout is built from six input values the starter program sets for you: the countdown length in seconds, the base propellant mass, the margin percent, the mass deficit the station must erase, the usable mass one supply run delivers, and the mass one run spends to launch. A single supply run delivers its usable mass but spends some of its own mass to launch, so a run nets only the difference between the two.

The number of supply runs is a break-even calculation, and Mission Control has already solved the break-even relation for you. Writing `deficit` for the mass deficit, `delivered` for the mass one run delivers, and `cost` for the mass one run spends to launch, the exact break-even point is:

<Latex formula="r = \dfrac{\text{deficit}}{\text{delivered} - \text{cost}}" inline={false} />

Here <Latex formula="r" /> is the exact, possibly fractional, number of runs whose combined net mass would meet the deficit precisely, and `delivered - cost` is the net mass a single run adds. The console does not need this fractional <Latex formula="r" />; it needs the number of complete runs the crew must actually fly, because a partial run cannot be flown.

**What your program must print.** Print exactly four lines, one whole number per line, in this order and nothing else on any line:

1. The whole minutes in the countdown, where there are `60` seconds in a minute.
2. The leftover seconds after those whole minutes.
3. The fueled mass: the base propellant plus a margin of the given percent of the base propellant. Every value here is a whole number.
4. The number of complete supply runs needed to erase the deficit. A partial run cannot be flown and does not count toward the deficit.

We give you **one** worked example to show the format. With `countdown_seconds = 500`, `base_fuel_kg = 1000`, `margin_percent = 15`, `deficit_kg = 1000`, `delivered_kg = 200`, and `cost_kg = 50`, the program prints:

```text frame="terminal" title="Output"
8
20
1150
7
```

**Assumptions and edge cases.** Every input is a whole number. `countdown_seconds` is zero or greater. `margin_percent` is zero or greater, and a margin of `0` must leave the base propellant unchanged. For every graded set of inputs, the margin itself, the given percent of the base propellant, works out to a whole number of kilograms. `delivered_kg` is greater than `cost_kg`, so the net a run adds is a positive whole number, and `deficit_kg` is a positive whole number. The grader may replace the six input values, so compute every printed number from the named variables and never hard-code a result such as `8` or `7`.

<Aside type="danger" title="HAB drafted a rule for the supply runs. Sign off on it, or reject it.">
HAB, the habitat's assistant, offers this: "The supply runs are just the deficit divided by the net a run adds. Whole-number division already throws away the fraction for you, so take `deficit_kg` divided by the net per run and read off that whole number. There is nothing left to round." Test HAB's rule against the requirement above before you rely on it, and let your test cases settle the question.
</Aside>

<Reveal label="Optional hint for the supply-run count. Skip it if you already have a plan.">
This hint is optional, and you may ignore it entirely. Work a case where the division does not come out even, and ask yourself what has to happen to the count when a remainder is left over. Then remember that you are free to do arithmetic before you divide: think about what adding something to the top of the division, before it runs, could do to absorb that leftover, without changing the answer in a case that divides evenly.
</Reveal>

## Step 1: Write Your Acceptance Tests

Before writing any code, decide what correct behavior looks like. Write a set of test cases as a plain table of rows: the six input values, and the four lines you expect the program to print. Do not use `assert` yet; a table of rows is what this step wants. For each row, work out the four printed numbers by hand from the requirements.

Your table must include, and label, at least these cases:

- The worked example above, as a starting check.
- One case where the net a run adds divides the deficit **evenly**, so the exact break-even point lands on a whole number.
- One case where it does **not** divide evenly, so the exact break-even point falls between two whole numbers.
- One more case of your own, whose four lines you compute fully by hand, including a `margin_percent` of `0`.

While you design these, think about what HAB claimed: a good set of tests would catch a rule that never adds the extra run when one is needed.

**Submit your test table in your PDF on Canvas.**

## Step 3: Write Your Code

Complete the provided program so it prints the four lines, in Python or Rust, following your own pseudocode. The starter sets the six input variables and prints the four result variables; you replace each `0` with the right computation. ## Paper Practice

Trace this program by hand, on paper. It reassigns one variable in place, the pattern from the [Variables and State](/lectures/variables-and-state/) lecture. Build a variable table showing the value of `level` after each line runs, and write the two values the program prints.

```python title="tank.py"
level = 500
level = level - 120
print(level)
level = level - 30
print(level)
```
