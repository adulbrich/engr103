Touchdown is confirmed, and the rover is cleared to drive down the ramp for its first traverse across the landing site. The ramp deployment itself took forty-three seconds. Before the wheels turn, the crew wants to know how much charge the parked rover's solar array will have banked over the coming sols, so they can decide whether to hold and let it gather more before committing to the drive. Your job as the flight-software crew member on shift is to write the function that projects that banked charge. HAB has already offered its own idea for how to compute it; do not trust that idea until you have checked it yourself.

## How This Assignment Works

You work **test first**, the way flight software is really written: you read the problem, decide what correct behavior looks like by writing your own test cases, plan the code in pseudocode, and only then write the code. The problem is solvable in Python or Rust, whichever you prefer. The program's `main`, its console input and output, and the local test runner are already written; you write the one function named below, and the automated grader calls it directly with values it chooses, reading only what you `return`. The order is fixed: design your tests, write your pseudocode, then write your function. After that comes an optional extra-credit stretch, a short paper trace, and a two-sentence reflection.

## The Problem

While the rover sits parked in the sun, mission modeling treats its stored charge as growing by a fixed percentage of its current level each sol. Because the gain each sol is a percentage of the current charge, the charge compounds: a larger reserve gathers a larger gain the next sol. A `growth_percent` of `25` means the charge ends each sol `1.25` times as large as it started that sol, so `25` percent of the current level is added on. The crew hands you a starting charge, that growth percentage, and a number of whole sols the rover will sit parked, and wants back the charge it projects to have banked at the end.

Write `solar_charge_after(start_charge, growth_percent, sols)`, returning the projected stored charge in watt-hours after `sols` whole sols of this compounding growth, as a float. Each sol the charge grows by `growth_percent` percent of its current level. A `sols` of `0` means no sols have passed, so the charge is returned unchanged. There is no exponentiation operator on the language ladder, so you cannot raise a factor to the `sols` power; the number of sols also varies from call to call, so you cannot write the growth out by hand.

The function returns a float. How you carry the charge across the sols, and what intermediate values you give names to along the way, is entirely your decision.

We give you **one** worked example to show the format. With a starting charge of `100.0` watt-hours growing `25.0` percent each sol for `3` sols, the charge reaches `125.0` after the first sol, `156.25` after the second, and `195.3125` after the third:

|---|---|

**Assumptions and edge cases.** `start_charge` and `growth_percent` are floats, zero or greater. `sols` is a whole number, zero or greater. Handle a `sols` of `0`, where no growth applies and the charge is returned unchanged, and a `growth_percent` of `0.0`, where each sol leaves the charge exactly where it was and nothing is gained.

## Paper Practice

Trace this program by hand, on paper. It uses the running-product accumulator from the [Loop Patterns](/lectures/loop-patterns/) lecture. Build a variable table with a row for each pass of the `while` loop, tracking `n` at the start of the pass and `charge` after it. Write the exact value the program prints.

```python title="trace_me.py"
charge = 64.0
factor = 1.5
n = 1
while n <= 3:
    charge = charge * factor
    n = n + 1
print(charge)
```

<Reveal label="Reveal the completed trace">
Each pass multiplies `charge` by the fixed `factor`, compounding it, and then advances `n`.

| Pass | `n` at start of pass | `charge` after |
|---|---|---|
| 1 | `1` | `96.0` |
| 2 | `2` | `144.0` |
| 3 | `3` | `216.0` |

After the third pass, `n` becomes `4`, and the condition `n <= 3` is false, so the loop ends. The program prints `216.0`. The same program written in Rust prints its whole-valued `f64` without the trailing zero, `216`.
</Reveal>

Photograph your trace and include it in your PDF on Canvas. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.
