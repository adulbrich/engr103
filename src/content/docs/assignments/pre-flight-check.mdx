Before the launch window opens, the crew runs a pre-flight check: bring up the instrument panel, confirm the cargo manifest, and read the status word off the bus. This is your first coding assignment, and it sits at the foundation of everything that follows, so the panel program is handed to you nearly complete. You have only just seen how a program runs and how values are stored, so your job is to fill in the readings the panel is missing. HAB has offered its own version of one reading, so check that before it goes on the board.

## How This Assignment Works

You work **test first**, the way flight software is really written: you read the problem, decide what correct output looks like by writing your own test rows, plan the program in pseudocode, and only then finish the code. You have not learned variables or functions yet, so the panel program comes as a **complete, runnable file with marked `TODO` lines**; you replace each placeholder with the literal or arithmetic expression that produces the reading described. The automated grader runs your program and compares its printed output, line by line, against the expected output. Solve it in Python or Rust, whichever you prefer; both are checked against the same panel.

Two rules hold for every reading here, and both come straight from the [Data Representation and Memory](/lectures/data-representation/) lecture. First, an expression may not mix a whole number with a decimal number: Rust refuses to compile `3 + 2.5`, so any reading that needs a fraction must be written with **every** number as a float (for example `100.5`, not `100`). Second, to get a real fraction from division you must divide floats, because dividing two whole numbers is a separate rule you have not met yet.

## What to Submit

You submit in two places. The mechanics are in [Running and Submitting Your Code](/practicalities/starter-repo-and-check/); each section below also repeats what it asks for.

- **A single PDF on Canvas** holding everything that is not code: your **acceptance tests**, your **pseudocode**, your **paper reduction**, and your **reflection**.
- **Your code on Gradescope**: the completed panel program, plus the summit program if you attempt it.

## The Problem

The pre-flight panel prints one reading per line, in a fixed order. The label and the main-bus power flag are already written for you; you fill in the five readings below them. The cargo manifest records that each pallet is rated to carry `20` units, though the panel never prints that rating.

Your finished program must print exactly seven lines, in this order:

1. The panel label, the text `PRE-FLIGHT` (already written).
2. The main-bus power flag, the boolean value for "online" (already written).
3. The crew count: `3` flight crew plus `1` mission specialist. This is a whole number.
4. The cabin pressure in kilopascals: the average of the two sensor readings `100.5` and `102.0`. This is a decimal number, so write both readings and the divisor as floats.
5. The status word, written directly as the binary literal `0b101010`, printed as its value.
6. The manifest total: a base of `6` units, plus `5` pallets carrying `8` units each, minus the `2` units reserved on each of those `5` pallets. All whole numbers.
7. The combined status code: the life-support code `0b1010`, plus the power code `0b110` counted once for each of the `2` power buses, minus the `0b11` units held in reserve. Write the three codes as binary literals and combine them with arithmetic.

Do not type the final numbers directly. Each reading must be written as the literal or the arithmetic expression that produces it.

Keep whole numbers and decimals apart within a single expression, and remember that the manifest total and the combined status code each mix multiplication with addition and subtraction, so the order the operators run in decides the answer.

## Step 1: Write Your Acceptance Tests

Before finishing any code, decide what correct output looks like. Write a set of test rows, as a plain table: one row per panel line, each naming the reading (the scenario) and the exact text you expect that line to print. Do not use `assert` yet; a table of rows is what this step wants. Work out each expected value by hand from the requirements, not by running the program.

Your table must include, and label, at least these rows:

- The worked reading above, `101.25`, as a starting check.
- The two precedence-sensitive lines, the manifest total and the combined status code, each reduced fully by hand one operator at a time, so your row shows the value a correct precedence gives. These are the rows HAB's claim would get wrong.
- The power-flag line, noting that its printed text is not the same in both languages.

Think about HAB's claim while you build this table: a row worked out with the right precedence is exactly what catches a reading that added before it multiplied.

**Submit your test table in your PDF on Canvas.**

## Paper Practice

Reduce this expression by hand, on paper, one operator at a time, and write the single value it comes out to. It is all whole numbers, and it includes a binary literal and a set of parentheses, the same precedence and literal rules the panel readings turn on.

```text title="Reduce this expression"
3 * 4 - 2 * (0b101 - 1) + 6
```

<Reveal label="Reveal the reduction">
```text title="Reducing 3 * 4 - 2 * (0b101 - 1) + 6"
3 * 4 - 2 * (0b101 - 1) + 6
3 * 4 - 2 * (5 - 1) + 6       (0b101 is the whole number 5)
3 * 4 - 2 * 4 + 6            (the parentheses reduce first: 5 - 1 is 4)
12 - 8 + 6                   (both products form before the + and -: 3 * 4 is 12, 2 * 4 is 8)
10                          (left to right: 12 - 8 is 4, then 4 + 6 is 10)
```

Parentheses reduce first, then multiplication and division before addition and subtraction, and operators of equal standing run left to right.
</Reveal>

Photograph your reduction and include it in your PDF on Canvas. This part is graded on completion, not correctness, so reduce it yourself first, then open the reveal to check.
