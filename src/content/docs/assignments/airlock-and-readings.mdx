The surface airlock is the one hatch between the crew and an atmosphere that would kill them in under a minute, so its flight software never acts on a single sensor reading without checking it first. The outer hatch takes forty-five seconds to fully cycle once it starts, which is exactly why the software has to be certain before it commits: the primary pressure sensor is read live, and a live reading can be untrustworthy in more than one way at once. Your job on the flight software crew is to write the check that sorts each live reading into trusted or faulty before anyone acts on it. HAB has already offered its own rule for part of that check, and the flight rule is simple: no HAB advice runs unverified.

## The Problem

The primary pressure sensor is read live from the console, as text, the way the [Errors, Input, and Validation](/lectures/errors-input-and-validation/) lecture describes. The provided harness already reads that line and parses it, using exactly the `try`/`except` or `parse`-and-`match` idiom from the lecture, so text that does not parse at all (a blank line, a stray word) never reaches your function: the harness reports it as `unreadable` on its own. What does reach your function is a number, and a number can still be untrustworthy in more than one way, so flight software sorts each parsed reading into a status code before it acts. `BACKUP_KPA` and `TOLERANCE_KPA` are constants the harness already sets from the backup sensor's own line.

```python title="Provided in the harness: you do not write this"
reading_text = input("Live sensor reading (kPa): ")
try:
    reading = float(reading_text)
    if reading_status(reading, BACKUP_KPA, TOLERANCE_KPA) == 0:
        print("trusted")
    else:
        print("rejected")
except ValueError:
    print("unreadable")
```

```rust title="Provided in the harness: you do not write this"
match reading_text.trim().parse::<f64>() {
    Ok(reading) => {
        if reading_status(reading, BACKUP_KPA, TOLERANCE_KPA) == 0 {
            println!("trusted");
        } else {
            println!("rejected");
        }
    }
    Err(_) => println!("unreadable"),
}
```

<WhatDiffers>
<Fragment slot="differs">
Both snippets reach the same `unreadable` outcome for garbage text, but by the two routes the errors lecture described. Python's `float` raises a `ValueError` the instant the text fails to parse, and the surrounding `try`/`except` catches it. Rust's `parse::<f64>()` never raises; it always finishes and hands back a `Result`, and the `match` reads that value and picks the `Ok` or `Err` arm. Either way, `reading_status` is only ever called once a reading has already parsed into a number.
</Fragment>
</WhatDiffers>

Write `reading_status(reading_kpa, backup_kpa, tolerance_kpa)`, returning the status code for a parsed reading. What it must return, checking the conditions in this priority order:

1. Return `1` when `reading_kpa` is below `0.0`. A pressure below zero is physically impossible, and in practice a shorted sensor line reads negative, so this flags a hardware fault at the low end.
2. Otherwise, return `2` when `reading_kpa` is above `200.0`. A reading above the vestibule sensor's physical ceiling means the sensor has railed high, a different hardware fault the crew log records separately.
3. Otherwise the reading sits inside the physically possible range, `0.0` to `200.0` inclusive, so compare it to the backup: return `3` when the reading and the backup disagree by more than the allowed slack, meaning at least one of the two sensors cannot be trusted.
4. Otherwise, return `0`. The reading is in range and agrees with the backup. This is the only trusted case.

The order matters: a reading is compared to the backup only after it has passed the physical-range check, so an out-of-range value is always reported as a range fault (`1` or `2`), never as a disagreement (`3`), even when it also happens to be far from the backup. Two sensors agree when the size of the gap between them is `tolerance_kpa` or less; a gap larger than `tolerance_kpa` is a disagreement. A gap exactly equal to `tolerance_kpa` still counts as agreeing, so it returns `0`, not `3`. The function returns a whole-number status code (`0`, `1`, `2`, or `3`). How you arrange the comparisons and what intermediate values you give names to along the way is entirely your decision.

Your table must include, and label, at least these cases:

- A disagreement case, in range but too far from the backup, that returns `3`.

## Paper Practice

Trace this program by hand, on paper. Build a variable table: for each call to `status_code`, write the values held by its `pressure_kpa` and `override_engaged` parameters and the value it returns, then the values bound to `a`, `b`, and `total`. Write the exact value the program prints.

```python title="trace_me.py"
def status_code(pressure_kpa, override_engaged):
    if override_engaged:
        return 1
    elif pressure_kpa < 90.0:
        return 0
    else:
        return 2

a = status_code(75.0, False)
b = status_code(75.0, True)
total = a + b
print(total)
```

<Reveal label="Reveal the completed trace">
The first call, `status_code(75.0, False)`, binds `pressure_kpa` to `75.0` and `override_engaged` to `False`. The chain checks `override_engaged` first: it is `False`, so that branch is skipped, not entered. The next condition, `pressure_kpa < 90.0`, is `True`, since `75.0` is less than `90.0`, so the function returns `0` and the final `else` is never even looked at. That `0` is bound to `a`.

| Line | `pressure_kpa` | `override_engaged` | returns | `a` | `b` | `total` |
|---|---|---|---|---|---|---|
| `a = status_code(75.0, False)` | `75.0` | `False` | `0` | `0` | | |
| `b = status_code(75.0, True)` | `75.0` | `True` | `1` | `0` | `1` | |
| `total = a + b` | | | | `0` | `1` | `1` |

The second call, `status_code(75.0, True)`, checks `override_engaged` first again, and this time it is `True`, so the function returns `1` immediately; the `pressure_kpa < 90.0` condition is never evaluated at all, because the chain stops at the first branch that matches. That `1` is bound to `b`. Finally `total = a + b` computes `0 + 1`, and the program prints `1`.
</Reveal>
