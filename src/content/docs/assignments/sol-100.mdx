Sol 100 has arrived: the habitat's hundredth full day on the Martian surface, and Mission Control wants a complete status report, not just another routine readout. All day, every system in the habitat, water, oxygen, power, and the rest, has been reporting its levels over the internal telemetry bus as short text lines, and the bus, still noisy in the wake of the conjunction, garbles some of those lines on the way. Mission Control has already logged that the solar arrays produced 4 percent more power than yesterday. Two jobs fall to you as the flight-software crew member on shift: turn each incoming line into a line of the status report, recording the good readings into the sol's running manifest as they arrive, and, at the end of the sol, archive that manifest into a permanent copy for the mission log that Sol 101 can never disturb.

## How This Assignment Works

You work **test first**, the way flight software is really written: you read the problem, decide what correct behavior looks like by writing your own test cases, plan the code in pseudocode, and only then write the code. The problem is solvable in Python or Rust, whichever you prefer. The program's `main`, its console input and output, and the local test runner are already written; you write the two functions named below, plus any helpers you choose to create inside your solution, and you may work each function in a different language. The two functions have two different contracts, so the grader checks them two different ways. For `log_reading`, the grader calls your function with a manifest and a line it chooses, reads the report line you `return`, and then inspects the caller's own manifest afterward, exactly the way the [Sharing and Mutation](/lectures/sharing-and-mutation/) lecture showed a function change a list its caller kept. For `archive_manifest`, the grader reads the list you `return`, then logs one more reading into the original manifest and confirms the list you already returned did not change with it. The order is fixed: design your tests, write your pseudocode, then write your functions. After that comes an optional summit stretch, a short paper trace, a one-page accessibility and equity critique, and a two-sentence reflection.

## The Problem

Every reading arrives from the telemetry bus as one raw text line. A healthy line names the system that sent it and the level it measured, joined by a colon, like `water:812`. A garbled line can look like almost anything: the colon dropped, the name mangled, stray characters in the middle of the number. Each system also has its own safe band, and Mission Control hands your function that band alongside the line, as a low and a high bound. Flight software has to sort every incoming line into one of three outcomes for the report: a garbled line is rejected, a healthy reading outside its safe band raises an alert, and a healthy reading inside the band is logged into the sol's running manifest. Then, once the sol is closed out, the report needs a permanent, separate copy of that manifest for the mission log, a copy that stays exactly as Sol 100 left it no matter what Sol 101 later logs into the live manifest.

These are two independent jobs, and you write one function for each.

1. `log_reading(manifest, line, low, high)` must first decide whether `line` is a **valid reading**. A valid reading has exactly three parts in this order, with nothing else anywhere in the line: a system name made of one or more lowercase letters `a` through `z`, then a single colon, then a level made of one or more digit characters `0` through `9`. When `line` is not a valid reading, the function must return exactly the string `REJECTED` and leave `manifest` completely unchanged.
2. When `line` is a valid reading, its level spells a whole-number value. If that value is inside the safe band (greater than or equal to `low` and less than or equal to `high`, with both ends of the band inside), the function must append the entry `name:value` to the end of `manifest`, with the value written as a plain number, and return the report line `LOGGED name value`, its three pieces separated by single spaces. If the value is outside the band, the function must leave `manifest` completely unchanged and return the report line `ALERT name value`, in the same format.
3. `archive_manifest(manifest)` must build and return a new list holding the same entries currently in `manifest`, in the same order. The returned list must be independent of `manifest`: any reading logged into `manifest` after the call must never appear in the list you already returned.

`log_reading` returns its report line as a string and changes the caller's `manifest` only in the one logged case; `archive_manifest` returns a list and changes nothing. How each function does its job, and what intermediate values you give names to along the way, is entirely your decision.

We give you **one** worked example to show the format. Starting from a `manifest` holding `["power:640"]`, and a water system whose safe band runs from `500` through `900`:

| Call | Result |
|---|---|
| `log_reading(manifest, "water:812", 500, 900)` | returns `"LOGGED water 812"`; `manifest` becomes `["power:640", "water:812"]` |
| `archive_manifest(manifest)` | returns `["power:640", "water:812"]`, a separate list; logging another reading into `manifest` afterward leaves that returned list at `["power:640", "water:812"]` |

**Assumptions and edge cases.** `line` may be any string at all, including the empty string; only a line with the exact three-part shape above is a valid reading. `low` and `high` are whole numbers, and `low` is guaranteed to be no greater than `high`. A valid level may be written with leading zeros, and they do not change the value it spells: a line `oxygen:007` carries the value `7`, so the entry and the report line both show `7`. A valid level never has more than six digits, so it always fits in an ordinary whole number. `manifest` may already hold any number of entries, including none. For `log_reading`, handle both boundary levels (a value exactly at `low` or exactly at `high` is logged), a valid reading outside the band on each side, a line with no colon, a line with an empty name or an empty level, and a level containing a character that is not a digit. For `archive_manifest`, handle the empty manifest: the returned archive is an empty list, and it must stay empty even after the live manifest later gains an entry.

<WhatDiffers>
<Fragment slot="differs">
The two languages disagree in two places here, and both are real. First, how a list reaches a function: in Python a list is shared the moment you pass it, so a plain `.append` inside the function changes the caller's `manifest` with no annotation anywhere, while Rust spells the two intentions in the types, `&mut Vec<String>` for the function that changes the caller's list and `&Vec<String>` with an owned `Vec<String>` return for the one that builds its own. Second, how the string work reports trouble: Python's `find` hands back `-1` when it cannot find what you asked for, and `int` raises an error on text that is not a number, while Rust's `find` returns an `Option` and `parse` returns a `Result`, values you inspect rather than errors you catch.
</Fragment>

## Paper Practice

Trace this program by hand, on paper. It is the aliasing pattern from the [Sharing and Mutation](/lectures/sharing-and-mutation/) lecture: `shadow` is set to `primary`, which gives the one list a second name rather than making a second list. Build a variable table with a row for each line, tracking what `primary` and `shadow` each hold after that line runs. Then write the exact two values the program prints.

```python title="trace_me.py"
def add_sample(readings, value):
    readings.append(value)

primary = [100, 98]
shadow = primary
add_sample(primary, 101)
print(primary)
print(shadow)
```

<Reveal label="Reveal the completed trace">
The line `shadow = primary` does not copy the list; it makes `shadow` a second name for the very same list object, so anything that changes one is seen through the other.

| Line | `primary` after | `shadow` after |
|---|---|---|
| `primary = [100, 98]` | `[100, 98]` | (not yet bound) |
| `shadow = primary` | `[100, 98]` | `[100, 98]` (same list, second name) |
| `add_sample(primary, 101)` | `[100, 98, 101]` | `[100, 98, 101]` |

`add_sample` appends `101` to the one shared list, so the change shows through both names. The program prints `[100, 98, 101]`, then `[100, 98, 101]` again. Rust prints a `Vec<i32>` the same way, `[100, 98, 101]`, with no display difference here since every value is a whole number, never a float.
</Reveal>

Photograph your trace and include it in your PDF on Canvas. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.

## Accessibility and Equity Critique

This part is not code. Write about one page (roughly 300 to 500 words) critiquing the accessibility and equity limitations of a real computational tool you actually use or have encountered, something people rely on today: a phone app, a website, a piece of assistive technology, a search engine, a hiring or screening algorithm, a fitness tracker, a voice assistant, a mapping app, a school or workplace platform. Pick a real, specific tool, not a hypothetical one and not anything from the Mission Ares story.

Your one page must address all three of these:

1. **Who is the tool built around.** Describe the "default" user the tool seems to assume: their abilities, their language, their income, their hardware, their situation. Be specific about what leads you to that description, drawn from how the tool actually behaves.
2. **Who it leaves out, and how.** Name one concrete accessibility or equity limitation: a group of people the tool underserves, excludes, or actively harms, and the specific mechanism, a design choice, an assumption baked into the software, a cost, a requirement, that produces that limitation. Vague statements like "it could be more inclusive" are not enough; name the mechanism.
3. **What closing the gap would take.** Describe one real change that would narrow the limitation you named, and name the trade-off it carries, more engineering effort, added cost, a slower feature, a different design entirely. A fix with no trade-off at all is a sign you have not looked closely enough.

This critique is graded on completion, evaluated on whether it genuinely engages with all three points about a real tool, not on whether the instructor agrees with your conclusions. It is not shared with anyone but the instructor.
