This activity puts into practice the [Collections I: Lists and Vectors](/lectures/collections-i/) lecture. You will predict what a list looks like after you push an element and overwrite another and what its elements sum to, compare how Python and Rust reach the last element and walk the sequence, and hunt down an out-of-bounds index that stops a program cold. By the end, you will be able to trace a growing sequence by hand and read the exact error a bad index produces in each language.

## Warm-up

A quick refresher before the blocks. A list, called a vector in Rust, is an ordered run of values you create as a literal, reach into by position starting from zero, and measure with a length. Here are those three pieces, in both languages.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="warmup.py"
nums = [10, 20, 30]
print(nums)
print(nums[0])
print(len(nums))
```
</TabItem>
<TabItem label="Rust">
```rust title="warmup.rs"
fn main() {
    let nums = vec![10, 20, 30];
    println!("{:?}", nums);
    println!("{}", nums[0]);
    println!("{}", nums.len());
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 warmup.py
```

```text frame="terminal" title="Output"
[10, 20, 30]
10
3
```

Rust prints the same three lines, using `{:?}` to show the whole vector and `nums.len()` as a method after the dot rather than the `len(nums)` function. With those pieces fresh, the blocks below grow, walk, and break a sequence.

## Block 1: Predict the List and the Sum

Pushing an element and overwriting one by index both change a list in place, and a sum over the result is easy to get wrong if you lose track of either change. You commit to an answer first, then run the program to check it.

Read both programs below and write down, on paper or in a comment, three things: the length the program prints, the exact final list, and the total its loop prints. Do not run them yet. Trace the list one line at a time: start from the literal, apply the push, apply the index assignment, then add the elements up. Predict for both languages, and notice whether your two answers agree.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="predict.py"
nums = [1, 2, 3]
nums.append(4)
nums[0] = 10
print(len(nums))
total = 0
for x in nums:
    total = total + x
print(nums)
print(total)
```
</TabItem>
<TabItem label="Rust">
```rust title="predict.rs"
fn main() {
    let mut nums = vec![1, 2, 3];
    nums.push(4);
    nums[0] = 10;
    println!("{}", nums.len());
    let mut total = 0;
    for x in &nums {
        total = total + x;
    }
    println!("{:?}", nums);
    println!("{}", total);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the real output and reconcile it with your prediction">
```bash title="Run the Python program"
python3 predict.py
```

```text frame="terminal" title="Output"
4
[10, 2, 3, 4]
19
```

```bash title="Compile and run the Rust program"
rustc predict.rs
./predict
```

```text frame="terminal" title="Output"
4
[10, 2, 3, 4]
19
```

The list starts as `[1, 2, 3]`. Appending `4` puts it after the last element, making `[1, 2, 3, 4]`, so the length is now `4`. Assigning `nums[0] = 10` overwrites the element at position 0, the `1`, with `10`, leaving the rest untouched, so the list is `[10, 2, 3, 4]`. The loop then adds the elements in order: `0 + 10` is `10`, then `12`, then `15`, then `19`. If you predicted a total of `10` for the sum, you likely added the original `1` instead of the `10` that overwrote it, or dropped the pushed `4`.

Both languages print the identical three lines, and that is the point: append, index assignment, and the accumulate loop behave the same in each. The only difference is that Rust requires `let mut` on a vector you change, and writes the push as `nums.push(4)` and the walk as `for x in &nums`.
</Reveal>

## Block 2: Reaching the End, Two Languages

Both languages reach the last element of a sequence and walk every element, and they write each of those two things differently. Studying the renderings side by side is how you keep Python's shortcut and Rust's explicit form straight instead of blurring them. You read both tabs and name what genuinely changes and what stays fixed.

Study the two programs below. Each prints the last element of the same three-value sequence, then walks the whole thing from first to last. Before opening the reveal, write down the four lines you expect each program to print, then name one thing that is truly different between the languages and one thing that is the same.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="last.py"
nums = [10, 20, 30]
print(nums[-1])
for x in nums:
    print(x)
```
</TabItem>
<TabItem label="Rust">
```rust title="last.rs"
fn main() {
    let nums = vec![10, 20, 30];
    println!("{}", nums[nums.len() - 1]);
    for x in &nums {
        println!("{}", x);
    }
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the outputs and what differs">
```bash title="Run the Python program"
python3 last.py
```

```text frame="terminal" title="Output"
30
10
20
30
```

```bash title="Compile and run the Rust program"
rustc last.rs
./last
```

```text frame="terminal" title="Output"
30
10
20
30
```

<WhatDiffers>
<Fragment slot="differs">
Python reaches the last element with a negative index, `nums[-1]`, which counts one back from the end. Rust has no negative index, so it computes the last position by hand as `nums[nums.len() - 1]`, one less than the length. Iterating differs too: Python writes `for x in nums`, while Rust writes `for x in &nums`, the leading `&` letting the loop read the elements without taking the vector away so `nums` stays usable afterward. What stays fixed is that both index from zero, both produce the same last element `30`, and both walk the elements in the same first-to-last order.
</Fragment>
</WhatDiffers>
</Reveal>

## Block 3: Find the Out-of-Bounds Index

Reaching for a position a sequence does not have is the classic mistake with any list, and it stops the program at that instant rather than printing a wrong value. The program below means to print the last element but reaches one position too far. You find the bug with the systematic method: read the error, form a hypothesis, test it.

Each program builds a three-element sequence, stores its length in `n`, and tries to print the element at position `n`. Run it, read the error it produces, then work out why position `n` is wrong and how one change fixes it.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="bounds.py"
nums = [10, 20, 30]
n = len(nums)
print(nums[n])
```
</TabItem>
<TabItem label="Rust">
```rust title="bounds.rs"
fn main() {
    let nums = vec![10, 20, 30];
    let n = nums.len();
    println!("{}", nums[n]);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the diagnosis and the fix">
```bash title="Run the buggy Python program"
python3 bounds.py
```

```text frame="terminal" title="Output"
Traceback (most recent call last):
  File "bounds.py", line 3, in <module>
    print(nums[n])
          ~~~~^^^
IndexError: list index out of range
```

```bash title="Compile and run the buggy Rust program"
rustc bounds.rs
./bounds
```

```text frame="terminal" title="Output"
thread 'main' panicked at bounds.rs:4:24:
index out of bounds: the len is 3 but the index is 3
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**Symptom.** Neither program prints a number. Python halts with an `IndexError: list index out of range`, and Rust panics with `index out of bounds: the len is 3 but the index is 3`. Both name the problem: the index is out of bounds.

**Hypothesis.** A three-element sequence has positions 0, 1, and 2, so the last valid index is `2`, one less than the length. The program uses `n`, which is `3`, so it reaches for position 3, one past the last element, which does not exist. This is an off-by-one: the length is a count of elements, not the index of the last one.

**Test.** Reach for `n - 1` instead, the last valid position:

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="bounds.py (fixed)"
nums = [10, 20, 30]
n = len(nums)
print(nums[n - 1])
```
</TabItem>
<TabItem label="Rust">
```rust title="bounds.rs (fixed)"
fn main() {
    let nums = vec![10, 20, 30];
    let n = nums.len();
    println!("{}", nums[n - 1]);
}
```
</TabItem>
</Tabs>

```bash title="Run the fixed Python program"
python3 bounds.py
```

```text frame="terminal" title="Output"
30
```

Rust prints the same `30`. The fix is a single `- 1`, turning the length into the last valid index. The lesson is that both languages catch a bad index at run time and stop, Python with an `IndexError` and Rust with a panic, so a length used where the last index belongs shows up loudly instead of reading the wrong value.
</Reveal>

## Bridge

These three reps feed the recitation family that encodes, decodes, or cleans a sequence one element at a time, walking a string or a list from front to back and building a new sequence as it goes. Growing a list with a push, reaching its elements by a valid index, and catching the off-by-one that reads past the end are the exact moves that family runs on longer sequences, and the hand-tracing you just practiced is the guided first rung of that ladder.
