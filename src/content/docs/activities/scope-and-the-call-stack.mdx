This activity puts into practice the [Scope and the Call Stack](/lectures/scope-and-the-call-stack/) lecture. You will trace by hand how a call stack pushes and pops a frame for each function call in a three-function chain, predict how two nested Rust blocks that each shadow a name print differently from Python's single function scope, and diagnose the different scope trap each language springs on the same discount function. By the end, you will be able to say which frame any variable lives in, how long it lasts, and why reaching for a name outside its scope fails in each language.

## Warm-up

A quick refresher before the sections. A variable created inside a function is a local variable: it lives in that function's own storage and is visible only inside the function's body. A function can also take a parameter and hand a value back with `return`. Here is one of each, in both languages.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="warmup.py"
def greet():
    name = "duck"
    print(name)

greet()

def area(side):
    return side * side

print(area(3))
```
</TabItem>
<TabItem label="Rust">
```rust title="warmup.rs"
fn greet() {
    let name = "duck";
    println!("{}", name);
}

fn area(side: i32) -> i32 {
    return side * side;
}

fn main() {
    greet();
    println!("{}", area(3));
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 warmup.py
```

```text frame="terminal" title="Output"
duck
9
```

Rust prints the same two lines. With a local variable, a parameter, and a return value fresh, the sections below follow those variables into and out of the stack frames that hold them.

## Trace a Three-Function Call Chain

When one function calls another, both are partway through running at once, each with its own variables. Add a third link to the chain and three frames stack up before any of them returns, so tracing by hand is the only way to keep straight which frame holds each variable and when it appears and disappears.

The program below converts seconds to days through a chain of three functions: `to_days` calls `to_hours`, which calls `to_minutes`. Trace `to_days(216000)` on paper. At each step, write down which frames are on the stack, from the bottom up, and the value of every variable in each frame. Watch the return value flow back up the chain, one frame at a time. Do not run it yet.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="trace.py"
def to_minutes(seconds):
    result = seconds / 60
    return result

def to_hours(seconds):
    result = to_minutes(seconds) / 60
    return result

def to_days(seconds):
    result = to_hours(seconds) / 24
    return result

print(to_days(216000))
```
</TabItem>
<TabItem label="Rust">
```rust title="trace.rs"
fn to_minutes(seconds: f64) -> f64 {
    let result = seconds / 60.0;
    return result;
}

fn to_hours(seconds: f64) -> f64 {
    let result = to_minutes(seconds) / 60.0;
    return result;
}

fn to_days(seconds: f64) -> f64 {
    let result = to_hours(seconds) / 24.0;
    return result;
}

fn main() {
    println!("{}", to_days(216000.0));
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the completed call-stack trace">
<Steps>

1. The program calls `to_days(216000)`. The argument `216000` is copied into `to_days`'s parameter `seconds`, and `to_days`'s frame is pushed. Stack, bottom to top: `to_days` with `seconds = 216000`.

2. Computing `to_hours(seconds) / 24` begins by calling `to_hours(216000)`. `216000` is copied into `to_hours`'s own parameter `seconds`, and a second frame is pushed on top. `to_days`'s frame waits beneath, unchanged. Stack: `to_days` with `seconds = 216000`; `to_hours` with `seconds = 216000`.

3. Computing `to_minutes(seconds) / 60` begins by calling `to_minutes(216000)`. `216000` is copied into `to_minutes`'s own parameter `seconds`, and a third frame is pushed on top. Now three frames are on the stack at once. Stack: `to_days` with `seconds = 216000`; `to_hours` with `seconds = 216000`; `to_minutes` with `seconds = 216000`.

4. Inside `to_minutes`, `result = seconds / 60` computes `3600.0` and stores it in a box in `to_minutes`'s own frame. Stack: `to_days` with `seconds = 216000`; `to_hours` with `seconds = 216000`; `to_minutes` with `seconds = 216000`, `result = 3600.0`.

5. `return result` hands `3600.0` back. `to_minutes`'s frame is popped, taking its `seconds` and `result` with it, and control returns to `to_hours`. Stack: `to_days` with `seconds = 216000`; `to_hours` with `seconds = 216000`.

6. Back in `to_hours`, `to_minutes(seconds)` was `3600.0`, so `3600.0 / 60` is `60.0`, stored in `to_hours`'s own `result`. Stack: `to_days` with `seconds = 216000`; `to_hours` with `seconds = 216000`, `result = 60.0`.

7. `return result` hands `60.0` back. `to_hours`'s frame is popped in turn, and control returns to `to_days`. Stack: `to_days` with `seconds = 216000`.

8. Back in `to_days`, `to_hours(seconds)` was `60.0`, so `60.0 / 24` is `2.5`, stored in `to_days`'s own `result`. Stack: `to_days` with `seconds = 216000`, `result = 2.5`.

9. `to_days` returns `2.5`; its frame is popped, and `print` shows the value. The stack is empty again.

</Steps>

Run it to confirm the value the trace lands on:

```bash title="Run the Python program"
python3 trace.py
```

```text frame="terminal" title="Output"
2.5
```

Rust prints the same `2.5`. Three `seconds` boxes, one in each frame, sat on the stack at the same time in step 3, all holding `216000`, yet they were separate boxes in separate frames: popping `to_minutes` at step 5 and `to_hours` at step 7 discarded each copy without disturbing the ones below. The answer reached `to_days` only through the value each call returned, never by one frame reaching into another.
</Reveal>

## Predict the Nested Shadowing

Rust's block scope and shadowing combine here at two levels of nesting, set against Python's single function-wide scope, and the last two lines Rust prints are the ones that catch people out. You commit to a full prediction first.

Both functions below start `n` at `2`, then build it up with `+ 3` and `* 2`. In Rust each step happens inside its own nested `{ }` block; in Python the steps run one after another with no blocks at all. Write down every line each program prints, in order, before opening the reveal. Pay attention to what the last two lines print in each.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="predict.py"
def layers():
    n = 2
    print(n)

    n = n + 3
    print(n)

    n = n * 2
    print(n)

    print(n)
    print(n)

layers()
```
</TabItem>
<TabItem label="Rust">
```rust title="predict.rs"
fn layers() {
    let n = 2;
    println!("{}", n);

    {
        let n = n + 3;
        println!("{}", n);

        {
            let n = n * 2;
            println!("{}", n);
        }

        println!("{}", n);
    }

    println!("{}", n);
}

fn main() {
    layers();
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the real output of each language">
```bash title="Run the Python program"
python3 predict.py
```

```text frame="terminal" title="Output"
2
5
10
10
10
```

```bash title="Compile and run the Rust program"
rustc predict.rs
./predict
```

```text frame="terminal" title="Output"
2
5
10
5
2
```

<WhatDiffers>
<Fragment slot="differs">
Both print five lines, and the first three lines match: `2`, then `5`, then `10`. Python has one variable `n` for the whole function. Each `n = ...` reassigns that same box, so after `n = n * 2` the box holds `10` and stays there; the last two `print(n)` lines both read that same box and print `10`, `10`. Rust's two `let n = ...` lines each sit inside a nested `{ }` block, so each creates a new variable that shadows the one outside it only until its own block's closing brace. The inner `let n = n * 2` uses the middle block's `n` of `5` to make `10`; when its block ends, that box is dropped and the name refers to the middle `n` again, still `5`. When the middle block ends too, that box is dropped and the name refers to the outer `n`, still `2`. So Rust prints `5` then `2` as it unwinds back out through the two blocks. Neither outer `n` was ever changed, because each `let` adds a new box rather than overwriting an existing one.
</Fragment>
</WhatDiffers>

If you predicted `10`, `10` for Rust's last two lines, you read the inner `let`s as reassigning one shared `n` the way Python does, instead of shadowing it inside a block that ends. If you predicted `5` or `2` for Python's last two lines, you treated its blockless reassignments as if they opened scopes that could close: Python cannot, since a name assigned anywhere in a function belongs to that whole function, with nothing to revert to.
</Reveal>

## Diagnose the Scope Trap

The same discount function, written naturally in each language, springs a different scope trap. Python and Rust catch the mistake at different times and with different messages, so you diagnose each with the systematic method: read the error, form a hypothesis, test the fix.

Each program below is meant to subtract a discount from a starting total of `100` and print the result. Neither does. Run the version for your language, read the error it produces, and work out the one change that fixes it.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="debug.py"
total = 100

def apply_discount(amount):
    total = total - amount
    return total

print(apply_discount(30))
```
</TabItem>
<TabItem label="Rust">
```rust title="debug.rs (will not compile)"
fn apply_discount(amount: i32) -> i32 {
    {
        let total = 100 - amount;
    }
    return total;
}

fn main() {
    println!("{}", apply_discount(30));
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the diagnosis, the exact errors, and the fix">
```bash title="Run the buggy Python program"
python3 debug.py
```

```text frame="terminal" title="Output"
Traceback (most recent call last):
  File "debug.py", line 7, in <module>
    print(apply_discount(30))
          ~~~~~~~~~~~~~~^^^^
  File "debug.py", line 4, in apply_discount
    total = total - amount
            ^^^^^
UnboundLocalError: cannot access local variable 'total' where it is not associated with a value
```

```bash title="Compile the buggy Rust program"
rustc debug.rs
```

```text frame="terminal" title="Output"
error[E0425]: cannot find value `total` in this scope
 --> debug.rs:5:12
```

**Symptom.** Both programs name `total` where its scope does not reach, but the two languages trip on it for different reasons. Python runs until it enters `apply_discount`, then raises an `UnboundLocalError` on the line that reads `total`. Rust never runs at all: the compiler rejects `return total` before building an executable, reporting `E0425`.

**Hypothesis, Python.** Assigning `total` anywhere in `apply_discount` makes `total` a local variable for the whole function, even on the lines above the assignment. So `total - amount` on the right side reads that local, which has not been given a value yet, and Python stops. The module-level `total = 100` is a separate global box that the function's own local `total` hides for the entire body, so the function never sees the `100`.

**Hypothesis, Rust.** `total` is declared with `let` inside a bare `{ }` block. Its box is dropped the moment the block's closing brace passes, so by the time `return total` runs, one line later, the name points at a box that no longer exists. The value was computed correctly inside the block and then thrown away when the block ended.

**Test.** Give each function the value through the one channel that survives, a parameter and a return, rather than reaching for a name outside its scope. In Python, pass the starting total in and return the difference. In Rust, lift the `let` out of the block so `total` lives for the rest of the function:

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="debug.py (fixed)"
total = 100

def apply_discount(current, amount):
    return current - amount

print(apply_discount(total, 30))
```
</TabItem>
<TabItem label="Rust">
```rust title="debug.rs (fixed)"
fn apply_discount(amount: i32) -> i32 {
    let total = 100 - amount;
    return total;
}

fn main() {
    println!("{}", apply_discount(30));
}
```
</TabItem>
</Tabs>

```bash title="Run the fixed Python program"
python3 debug.py
```

```text frame="terminal" title="Output"
70
```

Rust compiles and prints the same `70`. In Python, adding `global total` inside the function would also silence the error, but it would reintroduce exactly the shared-global antipattern the lecture warned against; passing the value in as a parameter keeps the function's dependency visible in its own signature instead. In Rust, the fix simply keeps `total` alive past the point it is read, since a variable cannot outlive the block that declares it.
</Reveal>

## Write a Function That Calls Another Function

Write `double(n)`, which returns `n` times `2`, and `quadruple(n)`, which returns four times `n` by calling `double` twice, once on `n` and once on the result. Do not compute `n * 4` directly in `quadruple`: it must call `double` inside itself. Print `quadruple(5)`.

<Reveal label="Reveal a sample solution">
More than one correct solution exists; this is a sample.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="quadruple.py"
def double(n):
    return n * 2

def quadruple(n):
    return double(double(n))

print(quadruple(5))
```
</TabItem>
<TabItem label="Rust">
```rust title="quadruple.rs"
fn double(n: i32) -> i32 {
    return n * 2;
}

fn quadruple(n: i32) -> i32 {
    return double(double(n));
}

fn main() {
    println!("{}", quadruple(5));
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 quadruple.py
```

```text frame="terminal" title="Output"
20
```

Rust prints the same `20`. `quadruple`'s frame calls `double` twice in turn: each call pushes and pops its own frame before `quadruple` uses the returned value, first doubling `5` to `10`, then doubling `10` to `20`.
</Reveal>

## Bridge

These three reps feed the recitation family where a value is converted through a chain of small functions to reach a result in different units of measure or time, with each function keeping its own parameters and local variables. Tracing which frame holds each variable, and reading a result only through the value a function returns rather than reaching for a name outside its scope, is exactly the discipline that family rewards, and the guided first rung of it is what you just practiced by hand.
