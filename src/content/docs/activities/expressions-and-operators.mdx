## Reduce a Mixed Expression Step by Step

The lecture reduced `10 / 4 + 3 * 2`, an expression with two operators past the addition. This one has four: it combines precedence, the modulo operator `%`, and division all at once, so you cannot eyeball the answer. Precedence decides the order, `%` divides and keeps the remainder, and the same `/` lands on a different value in each language. You commit to an answer first, then run the program to check it.

Read the program below and write down, on paper or in a comment, the exact value you expect it to print in each language. Do not run it yet. Reduce the expression one operator at a time: `%`, `*`, and `/` all outrank `+` and `-`, so they go first, left to right; only then do the addition and subtraction, also left to right. Remember that Python's `/` produces a float while Rust's `/` between two whole numbers truncates. Predict both values before opening the reveal.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="predict.py"
print(10 % 3 + 2 * 4 - 6 / 4)
```
</TabItem>
<TabItem label="Rust">
```rust title="predict.rs"
fn main() {
    println!("{}", 10 % 3 + 2 * 4 - 6 / 4);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the real outputs and reconcile them with your prediction">
```bash title="Run the Python program"
python3 predict.py
```

```text frame="terminal" title="Output"
7.5
```

```bash title="Compile and run the Rust program"
rustc predict.rs
./predict
```

```text frame="terminal" title="Output"
8
```

The two languages run the exact same steps in the exact same order, and only the single division `6 / 4` splits them. Precedence reduces `%`, `*`, and `/` before `+` and `-`, left to right, so `10 % 3` goes first, then `2 * 4`, then `6 / 4`; the leftover `+` and `-` reduce last, left to right.

In Python, `10 % 3` is `1` (the remainder of ten divided by three), `2 * 4` is `8`, and `6 / 4` is the exact float `1.5`, because Python's `/` always produces a float:

```text title="Reducing 10 % 3 + 2 * 4 - 6 / 4 in Python"
10 % 3 + 2 * 4 - 6 / 4
1 + 2 * 4 - 6 / 4        (10 % 3 is the remainder 1)
1 + 8 - 6 / 4            (2 * 4 is 8)
1 + 8 - 1.5             (6 / 4 is float division: 1.5)
9 - 1.5                 (1 + 8, leftmost of the equal-ranked + and -)
7.5                     (9 - 1.5)
```

In Rust, `10 % 3` is `1` and `2 * 4` is `8` just the same, but `6 / 4` divides two whole-number literals, so it is integer division and truncates `1.5` down to `1`:

```text title="Reducing 10 % 3 + 2 * 4 - 6 / 4 in Rust"
10 % 3 + 2 * 4 - 6 / 4
1 + 2 * 4 - 6 / 4        (10 % 3 is the remainder 1)
1 + 8 - 6 / 4            (2 * 4 is 8)
1 + 8 - 1               (6 / 4 is integer division: truncates 1.5 to 1)
9 - 1                   (1 + 8)
8                       (9 - 1)
```

If you predicted `8` for Python, you almost certainly truncated `6 / 4` to a whole number, which is the Rust rule, not Python's. If you predicted anything with the addition and subtraction reaching past `%`, `*`, or `/`, precedence was the slip: the three high-ranked operators always reduce before the `+` and the `-`, no matter where they sit in the line.
</Reveal>

## The Negative Case Where the Languages Split

For a positive numerator, Python's `//` and Rust's `/` agree: both make `7 / 2` into `3`, so the two rules look interchangeable. They are not. They split the moment the numerator goes negative, and the modulo remainder splits with them. Studying the negative case side by side is how you keep the two rules straight instead of blurring them into one. You read both tabs and name what genuinely changes and what stays fixed.

Study the two programs below. Each divides `-7` by `2` as a whole-number division and then takes the modulo remainder. Before opening the reveal, write down the four values you expect, then name one thing that is truly different between the languages and one thing that is the same.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="divide.py"
print(-7 // 2)
print(-7 % 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="divide.rs"
fn main() {
    println!("{}", -7 / 2);
    println!("{}", -7 % 2);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the outputs and what differs">
```bash title="Run the Python program"
python3 divide.py
```

```text frame="terminal" title="Output"
-4
1
```

```bash title="Compile and run the Rust program"
rustc divide.rs
./divide
```

```text frame="terminal" title="Output"
-3
-1
```

<WhatDiffers>
<Fragment slot="differs">
The exact answer of dividing `-7` by `2` is `-3.5`, sitting between `-4` and `-3`, and the two languages round it opposite ways. Python's `//` floors toward negative infinity, taking the largest whole number not exceeding `-3.5`, so `-7 // 2` steps down to `-4`. Rust's `/` truncates toward zero, dropping the `.5` and keeping the whole-number part, so `-7 / 2` is `-3`. The modulo remainder follows whichever division its language uses, because quotient times divisor plus remainder must recover `-7`: with Python's quotient `-4`, the remainder is `1` (since `-4 * 2 + 1` is `-7`), and with Rust's quotient `-3`, the remainder is `-1` (since `-3 * 2 + -1` is `-7`). What stays fixed is that both languages produce one value per line, both share the same precedence, and both use the same operand-and-operator machinery; only the direction of rounding on a negative result, and the sign of the remainder that tracks it, changes.
</Fragment>
</WhatDiffers>

Had the numerator been positive, all of this would have stayed hidden: `7 // 2` and `7 / 2` are both `3`, and `7 % 2` is `1` in both languages. The negative numerator is the one case that forces floor and truncate to disagree, and it is exactly the case that bites when a real formula happens to feed a negative value into a whole-number division.
</Reveal>

## Find the Silent Precedence Bug

A precedence bug does not crash. The program runs, prints a number, and lies: the number is simply wrong. The program below is meant to convert `212` degrees Fahrenheit to Celsius using the formula that subtracts `32`, then scales by `5/9`. Boiling water is `212` Fahrenheit, which is `100` Celsius, so the correct answer is `100.0`. It prints something else. You find the bug with the systematic method: read the symptom, form a hypothesis, test it.

Run the program, see what it actually prints, then work out why the value is wrong and how one change fixes it.

```python title="convert.py"
print(212 - 32 * 5 / 9)
```

<Reveal label="Reveal the diagnosis and the fix">
```bash title="Run the buggy program"
python3 convert.py
```

```text frame="terminal" title="Output"
194.22222222222223
```

**Symptom.** There is no error message; the program runs and prints `194.22222222222223`, but converting `212` Fahrenheit should give `100.0`. The wrong output is the only signal you get.

**Hypothesis.** The formula is `(F - 32) * 5 / 9`, and it depends on subtracting `32` before scaling. But `*` and `/` outrank `-`, so without parentheses the reduction runs `32 * 5 / 9` first, about `17.78`, and only then subtracts that from `212`. The `212 - 32` that was supposed to happen first never happens at all:

```text title="Reducing 212 - 32 * 5 / 9 (buggy order)"
212 - 32 * 5 / 9
212 - 160 / 9           (32 * 5 is 160, because * and / outrank -)
212 - 17.77...          (160 / 9 is about 17.78, a float in Python)
194.22222222222223      (212 minus that)
```

**Test.** Force the subtraction to happen first by wrapping it in parentheses, so the whole difference is scaled by `5/9`:

```python title="convert.py (fixed)"
print((212 - 32) * 5 / 9)
```

```bash title="Run the fixed program"
python3 convert.py
```

```text frame="terminal" title="Output"
100.0
```

The parentheses reduce `212 - 32` to `180` before anything else, so `180 * 5 / 9` is `900 / 9`, which is the intended `100.0`. The fix is a single pair of parentheses. The lesson is that a precedence mistake produces a plausible number, `194.22222222222223` looks like a real temperature, not a crash, so hand-evaluation and a known expected value are what catch it.
</Reveal>

## Write a Seconds Splitter

A stopwatch has logged a run lasting `200` seconds total. Write a program that prints, on two separate lines, the whole number of minutes contained in `200` seconds and then the leftover seconds, using integer division and the remainder operator.

<Reveal label="Reveal a sample solution">
More than one correct program can produce this result; the one below is a sample solution, not the only path to it.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="split.py"
total_seconds = 200
minutes = total_seconds // 60
leftover_seconds = total_seconds % 60
print(minutes)
print(leftover_seconds)
```
</TabItem>
<TabItem label="Rust">
```rust title="split.rs"
fn main() {
    let total_seconds = 200;
    let minutes = total_seconds / 60;
    let leftover_seconds = total_seconds % 60;
    println!("{}", minutes);
    println!("{}", leftover_seconds);
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 split.py
```

```text frame="terminal" title="Output"
3
20
```

```bash title="Compile and run the Rust program"
rustc split.rs
./split
```

```text frame="terminal" title="Output"
3
20
```

`200 // 60` (Python) and `200 / 60` (Rust, on whole numbers) both floor to `3` whole minutes, and `200 % 60` leaves a remainder of `20` seconds in both languages, since the numerator here is positive and the two rules agree.
</Reveal>
