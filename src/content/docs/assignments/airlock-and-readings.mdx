### Problem 1: The Airlock Cycle Table

**Context.** Before the outer hatch may cycle, flight software checks three things: whether the vestibule has equalized pressure with the outside, whether the inner seal is fully engaged, and whether the flight director has thrown the manual override for an emergency egress. The override is a flight rule of its own: it clears the hatch to cycle no matter what the other two readings say, because a crew member in trouble outside cannot wait on a seal sensor.

**Requirements.**

1. Before writing any code, lay out the decision table below: three boolean conditions and one outcome. Overriding collapses four of the eight possible combinations into one row, since the other two readings stop mattering the moment the override is thrown.

   | `pressure_equalized` | `seal_engaged` | `override_engaged` | may cycle |
   |---|---|---|---|
   | any | any | `true` | `true` |
   | `true` | `true` | `false` | `true` |
   | `true` | `false` | `false` | `false` |
   | `false` | `true` | `false` | `false` |
   | `false` | `false` | `false` | `false` |

2. `airlock_may_cycle(pressure_equalized, seal_engaged, override_engaged)` must return `true` whenever `override_engaged` is `true`, regardless of what `pressure_equalized` and `seal_engaged` read.
3. When `override_engaged` is `false`, it must return `true` only when both `pressure_equalized` and `seal_engaged` are `true`, and `false` for every other combination of the two.

The modeling step is building the five-row table above, the one that exposes the override's collapse before any code exists to hide it; the analysis step is turning that table into a working function, in an order that checks the override first, exactly the way the [Decision Structures](/lectures/decision-structures/) lecture ordered its rain check ahead of the soil-dryness check.

### Problem 3: Classifying the Sensor Reading

**Context.** The primary pressure sensor is read live from the console, as text, the way the [Errors, Input, and Validation](/lectures/errors-input-and-validation/) lecture describes. The provided harness already reads that line and parses it, using exactly the `try`/`except` or `parse`-and-`match` idiom from the lecture; you are not writing that part. Text that does not parse at all (a blank line, a stray word) never reaches your function: the harness reports it as `unreadable` on its own, the way the lecture's parse step guards every call that follows it. What does reach your function is a number, and a number can still be untrustworthy in more than one way, so flight software sorts each parsed reading into a status code before it acts. `BACKUP_KPA` and `TOLERANCE_KPA` below are constants the harness already defines from the backup sensor's own line.

```python title="Provided in the harness: you do not write this"
reading_text = input("Live sensor reading (kPa): ")
try:
    reading = float(reading_text)
    if reading_status(reading, BACKUP_KPA, TOLERANCE_KPA) == 0:
        print("trusted")
    else:
        print("rejected")
except ValueError:
    print("unreadable")
```

```rust title="Provided in the harness: you do not write this"

        } else {
            println!("rejected");
        }

}
```

<Fragment slot="differs">
Both snippets reach the same `unreadable` outcome for garbage text, but by the two different routes the errors lecture described. Python's `float` raises a `ValueError` the instant the text fails to parse, and the surrounding `try`/`except` catches it after the fact. Rust's `parse::<f64>()` never raises anything; it always finishes and hands back a `Result`, and the `match` reads that value and picks the `Ok` or `Err` arm. Either way, `reading_status` is only ever called once a reading has already parsed into a number.
</Fragment>

**Requirements.**

1. `reading_status(reading_kpa, backup_kpa, tolerance_kpa)` must sort a parsed reading into one of four status codes, checking the conditions in this order:
   - Return `1` when `reading_kpa` is below `0.0`. A pressure below zero is physically impossible, and in practice a shorted sensor line reads negative, so this code flags a hardware fault at the low end.
   - Return `2` when `reading_kpa` is above `200.0`. A reading above the vestibule sensor's physical ceiling means the sensor has railed high, a different hardware fault the crew log records separately.
   - Otherwise the reading sits inside the physically possible range, `0.0` to `200.0` inclusive, so compare it to the backup: return `3` when the absolute difference between `reading_kpa` and `backup_kpa` is greater than `tolerance_kpa`, meaning the two sensors disagree by more than the allowed slack and at least one cannot be trusted.
   - Return `0` when the reading is inside the physical range and agrees with the backup (its absolute difference from `backup_kpa` is `tolerance_kpa` or less). This is the only trusted case.
2. The order matters: a reading is compared to the backup only after it has passed the physical-range check, so an out-of-range value is always reported as a range fault (`1` or `2`), never as a disagreement (`3`), even when it also happens to be far from the backup.
3. `trusted_or_default(reading_kpa, backup_kpa, tolerance_kpa)` must return the value the display should actually use: `reading_kpa` when the reading is trusted (its status is `0`), and `backup_kpa` otherwise. This is the override the crew relies on, so that a rejected live reading falls back to the backup sensor rather than showing a fault value on the panel.

The modeling step is naming the four states a reading can be in, a fault at each end of the physical range, a disagreement with the backup, and a trusted reading, and fixing the order they are checked in; the analysis step is computing them with an `elif`/`else if` chain, comparing the absolute difference against the tolerance rather than checking for exact equality, the same tolerance idea the [Booleans and Conditionals](/lectures/booleans-and-conditionals/) lecture introduced for comparing floats.

Do not compare `reading_kpa` to `backup_kpa` with `==`.
