Every program is data in motion: a number being added, a name being printed, a yes-or-no answer being checked. A computer, though, cannot work with a piece of data the way you read it off a page. Before it can add, compare, or even store anything, it has to settle two questions a person never stops to think about: what kind of thing is this piece of data, and where, exactly, is it being kept?

The computer's answers are stricter than a person's. You can write "seven," "7," or "VII" and mean the same number three ways, but every value a computer holds is ultimately a pattern of tiny switches, and each switch can only ever be in one of two states. This lecture works through both questions in order. First, what a value and its type are: the computer's answer to what kind of thing a piece of data is. Then, how that value is stored, as bits gathered into bytes and kept at numbered locations in memory: the computer's answer to where it lives. By the end, the numbers tucked inside type names like `i32` and `f64` will each mean something exact.

## Values

A **value** is a single piece of data that a program works with: the number 7, the number 3.14, the truth of a statement, or a short piece of text. A value is the simplest thing a running program can hold or produce. When you write a value directly into your code, such as typing the number 7, that value is called a **literal**: a value written out exactly as it is, rather than computed from something else.

This lecture uses four kinds of value, the ones both Python and Rust make available from the very first line of code you write. An **integer** is a whole number, with no fractional part, such as 7 or negative 3. A **float**, short for "floating-point number," is a number that can have a fractional part, such as 3.14. A **boolean** is a value that is only ever one of two things: true or false; it gets its name from the mathematician George Boole, who studied logic built from exactly two values. A **string** is a short piece of text, such as a word or a sentence, treated by the computer as data rather than as code to run.

## Types

Knowing that 7 and 3.14 are both values is not enough on its own; the computer also needs to know what kind of value each one is, because that changes what can be done with it.

A **type** is a category that tells the computer what kind of value something is and what can be done with it. Knowing a value's type tells the computer how much space to use for it, how to display it, and which operations make sense on it: you can divide two numbers, but dividing two pieces of text makes no sense. Every value from the previous section already has a type: 7 is an integer, 3.14 is a float, `true` is a boolean, and `"hello"` is a string.

A type is not only a label the computer checks; it is also a claim on how much memory a value takes up while the program runs. Later in this lecture, once you have seen how a computer actually stores a value as bits, you will see exactly how big a claim Python's whole-number type and Rust's whole-number type each make, and why the two languages make different ones.

### Static Typing

**Static typing** means a language works out the type of every value and checks that those types are used consistently before the program ever runs. Rust is statically typed: its compiler, the program that turns your source code into a runnable one, reads through your whole file and rejects it if a type does not fit where it is used, even in a line that would never actually execute. The check happens once, ahead of time, which is why it is called static.

### Dynamic Typing

**Dynamic typing** means a language decides whether a value's type makes sense for a given use only at the moment that use actually runs. Python is dynamically typed: it does not check the types on a line of code until the computer actually reaches that line while running the program. If an earlier line has a problem, Python will not notice until it gets there.

You can see the difference directly. The exact same expression, `3 + 2.5`, mixing a whole number and a decimal number, runs cleanly in Python and refuses to compile in Rust:

<TabItem label="Python">
```python title="Combining a whole number and a decimal number"
print(3 + 2.5)
```
</TabItem>
<TabItem label="Rust">
```rust title="Combining a whole number and a decimal number (will not compile)"

```
</TabItem>

<WhatDiffers>
<Fragment slot="differs">
Python resolves `3 + 2.5` to the float `5.5` the moment that line runs, coercing the whole number to a float on the fly, without checking in advance whether the two types are allowed to mix. Rust checks every type before the program runs, so the identical `3 + 2.5` never compiles at all: mixing a whole number with a decimal number is a type error it refuses to build.
</Fragment>
</WhatDiffers>

The compiler rejects that line before your program runs at all. That is what static typing means in practice: Rust confirms every type is used consistently while compiling, before your program takes its first step, while Python only confirms it line by line, while the program is already running. You will see this same static-versus-dynamic split reappear later in this lecture, once you learn exactly how many bits each language sets aside for a value's type.

## Binary and Bits

Values and their types describe *what* a program works with. The rest of this lecture is about how a computer actually holds that data, and it starts from the smallest thing memory can store.

### Bits

A **bit** is the smallest piece of information a computer can store: a single 0 or a single 1. Nothing smaller exists inside a computer's memory. A single bit on its own can tell you almost nothing: it can distinguish only two possibilities, such as on versus off, or yes versus no. Every value your program touches, whether a whole number, a decimal number, a true-or-false answer, or a piece of text, is ultimately stored as some longer pattern of these two symbols, strung together so that the pattern as a whole can represent far more than two possibilities.

### Binary

**Binary** is a number system that writes every value using only the two digits 0 and 1, the same two symbols a bit can hold. You already know a different number system by heart: the decimal system, which writes every value using ten digits, 0 through 9, where each position in a number is worth ten times the position to its right. The digit string "247" means 2 hundreds, plus 4 tens, plus 7 ones, because decimal positions are worth 100, 10, and 1. Binary works the same way, except each position is worth two times the position to its right instead of ten. The binary digit string `1000001` means one 64, plus one 1, with every other position worth 0, because binary positions (reading from the right) are worth 1, 2, 4, 8, 16, 32, 64, and so on: 64 plus 1 is 65. Binary is not a different kind of number, only a different way of writing the same whole numbers you already know, using an alphabet a computer's switches can actually hold.

## Bytes and Memory as Addressable Boxes

Knowing that a computer stores everything as 0s and 1s is only half the picture. The other half is where those bits actually live while a program runs, and how much of them a program groups together as one unit.

### Bytes

A single bit is too small to describe anything useful on its own, so computers handle bits in a fixed group: a **byte** is a group of 8 bits handled together as one unit. A byte is the unit programmers actually use to talk about how much space something takes, and it is also the size of the smallest separately addressable location in a computer's memory, which the next part explains. Eight bits, each either 0 or 1, can be arranged in 256 different patterns, so a single byte can represent any whole number from 0 up to 255.

### Memory Addresses

A running program's memory is organized as a long row of byte-sized boxes, one after another. A **memory address** is the number that identifies one specific box in that row, the same way a house number identifies one specific house on a street. Just as a delivery driver needs a house number to find the right house, a running program needs an address to find the right byte, out of the millions of bytes memory actually contains. Addresses are usually shown in hexadecimal (base 16) rather than decimal or binary, because hexadecimal writes large addresses in far fewer digits, but the address is still, underneath, just a whole number that names one box.

Here is what four consecutive bytes in memory might look like while a simple program runs, each holding a small whole number, each living at its own address one after the other:

## Integer Sizes: Fixed Width Versus Arbitrary Precision

Every value a program stores needs a fixed amount of memory set aside for it, and this is where Python and Rust part ways. The Types section earlier promised that a type is also a claim on memory; now that bits and bytes are on the table, that claim, and the numbers sitting inside type names like `i32` and `f64`, can finally be made exact.

### Integer Size

An **integer size** is the number of bits a language sets aside to store one whole-number value. Rust's default whole-number type, `i32`, reserves exactly 32 bits, no more and no less, for every value of that type, whether the value being stored is 0, 7, or the largest number those 32 bits can represent. That fixed budget of 32 bits is exactly what the `32` in `i32` names: not a version number, not an arbitrary label, but the number of bits Rust always sets aside for a value of that type. Because 32 bits can only form so many distinct patterns of 0s and 1s, `i32` has a largest value it can hold, 2,147,483,647, and a smallest one; a whole number outside that range simply does not fit in 32 bits, and Rust's compiler refuses to build a program that tries to write one as a plain `i32` literal. Rust's default decimal type, `f64`, follows the same idea with a different width: the `64` names 64 bits, or 8 bytes, set aside for every value of that type, giving `f64` a much wider range than `i32` while still being a fixed budget rather than an unlimited one.

### Arbitrary Precision

Python's whole-number type, `int`, makes the opposite choice. It is **arbitrary-precision**: instead of a fixed number of bits, it uses however many bits its current value actually needs, growing as large as the value requires. There is no whole number too big for Python's `int` to hold, short of running out of the computer's memory entirely. This is the direct payoff of everything this lecture has covered: a value's bits live somewhere in memory as bytes at addresses, and Python's `int` is simply free to claim as many of those bytes as a given value needs, while Rust's `i32` and `f64` always claim exactly the same number of bytes, 4 and 8, no matter what value they hold.

<WhatDiffers>
<Fragment slot="differs">
Python's literal is simply the value written out, and since its `int` type has no upper limit beyond the computer's memory, this 29-digit whole number prints back exactly as written. Rust's literal must fit inside `i32`'s 32-bit budget, and 2,147,483,647 is the largest whole number that budget allows; a bare literal even one more than that fails to compile, because Rust checks a whole-number literal against its 32-bit budget before your program ever runs.
</Fragment>
</WhatDiffers>

Here is that failure in practice. One whole number higher than `i32`'s largest value, and Rust's compiler refuses to build the program at all:

```rust title="A literal one past i32's largest value (will not compile)"
fn main() {
    println!("{}", 2147483648); // error: literal out of range for `i32` (Rust will not compile this)
}
```

Python has no equivalent failure here: because `int` grows to fit any value, no whole-number literal is ever too large for it to hold.

## Takeaways

Every value a program works with, an integer, a float, a boolean, or a string, has a type, and a type is more than a label: it tells the computer what can be done with a value and how much memory that value costs to hold. Python and Rust agree completely on what a value and a type are; they disagree on timing. Rust checks types statically, working out every type and confirming it fits before your program ever runs, which is why its compiler can reject a mixed-type line before your program takes a single step. Python checks types dynamically, only at the moment a line actually runs, which is why the same kind of mistake in Python would not surface until the program reached that line. Underneath both of these choices sits the same physical fact: every value a running program touches, no matter its type, is ultimately a pattern of bits, the 0s and 1s a computer's switches can actually hold, grouped into bytes and stored at addresses inside memory, the way this lecture pictured memory as a long row of addressable boxes. Binary is only a different way of writing the same whole numbers decimal already writes, using the two-symbol alphabet bits are built from. Type sizes are the last piece, and the direct payoff of the static-versus-dynamic split from earlier: a type is not only a category of value, it is also a fixed or flexible claim on memory, which is exactly why Rust's `i32` and `f64` reserve a fixed 32 or 64 bits and stop at a largest representable value, while Python's `int` grows without a built-in limit. With values, types, bits, bytes, addresses, and what a type's size actually costs all in view, a name like `i32` is no longer an arbitrary label: it is a precise statement about how many of memory's boxes a value of that type always occupies.
