Suppose you ask a computer to compute 7 divided by 2. Is the answer 3, or is it 3.5? A person could answer either way, depending on whether the 7 and the 2 stand for a whole count of items or a precise measurement. As you will see in this lecture, Python and Rust do not leave that question open: each language picks one exact rule for what dividing two whole numbers produces, and the two rules do not agree with each other.

Division is only the sharpest example of a bigger question. The moment a program combines more than one value using a symbol like `+`, `-`, `*`, or `/`, something has to decide the order those combinations happen in, and exactly what kind of answer they produce. This lecture is about that machinery: the symbols that combine values into new values, the rule that decides which combination happens first, and the exact behavior each language falls back on when a division, or a mix of types, does not have one obviously correct answer.

## Expressions

A program spends nearly all of its time combining small pieces of data into new ones. This section names the piece of code that does that combining.

### Expressions

An **expression** is a piece of code that produces a value when the computer runs it. The simplest possible expression is a literal on its own, the kind of value the [Data Representation and Memory](/lectures/data-representation) lecture introduced: the code `7` is already an expression, and running it produces the value 7. You can also build a larger expression out of smaller ones by combining values with operators, symbols such as `+` that take one or more values and produce a new one; the next section looks closely at operators. For now, know only this: combining values always builds a bigger expression, and every expression evaluates to a value, never to anything else.

Printing a value, which you saw in the previous lecture, works by first evaluating an expression down to a single value, then displaying that value in the terminal. Every example in this lecture follows that same pattern: write an expression, then print what it evaluates to.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="A literal expression and a combined expression"
print(7)
print(3 + 4)
```
</TabItem>
<TabItem label="Rust">
```rust title="A literal expression and a combined expression"
fn main() {
    println!("{}", 7);
    println!("{}", 3 + 4);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Rust wraps every runnable line inside a `fn main() { ... }` function; Python does not. Rust prints with `println!` and a placeholder marker `{}` that stands for the value; Python prints directly with `print(...)`.
</Fragment>
</WhatDiffers>

## Operators and Operator Precedence

A single value on its own is not very useful; programs become powerful once values can be combined into new ones. This section names the symbol that does the combining and the rule that decides which combination happens first.

### Operators

An **operator** is a symbol that combines one or more values to produce a new value. The familiar arithmetic operators, `+`, `-`, `*`, and `/`, take two number values and produce a new number: `3 + 4` is an expression built from the operator `+` and the two values 3 and 4, and it evaluates to the value 7.

### Operator Precedence

When an expression contains more than one operator, the computer needs a rule for which operation happens first. **Operator precedence** is the set of rules a language uses to decide that order. Both Python and Rust use the same order you likely already learned for ordinary arithmetic: multiplication and division happen before addition and subtraction, and parentheses around part of an expression force that part to be evaluated first, overriding the usual order. Take `3 + 4 * 2`: multiplication happens first, so `4 * 2` is 8, then `3 + 8` is 11, in both languages. Wrapping `3 + 4` in parentheses instead forces that addition to happen first, so `(3 + 4) * 2` becomes `7 * 2`, which is 14, again in both languages.

This course tracks exactly which pieces of each language are available at each point in the term; the current list lives on the [language ladder](/reference/language-ladder) page, and this lecture stays within its first entry.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Order of operations, with and without parentheses"
print(3 + 4 * 2)
print((3 + 4) * 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="Order of operations, with and without parentheses"
fn main() {
    println!("{}", 3 + 4 * 2);
    println!("{}", (3 + 4) * 2);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Nothing about the arithmetic itself differs: the symbols `+`, `*`, and `(`...`)` are written the same way in both languages. Rust's only extra requirement is wrapping the two lines in `fn main() { ... }`.
</Fragment>
</WhatDiffers>

## Integer Versus Float Division

Division deserves its own closer look, because it is the one arithmetic operator whose exact answer often cannot be represented as a whole number.

### Integer Division

Dividing two whole numbers raises a question that addition, subtraction, and multiplication do not: what happens when the exact answer is not itself a whole number? **Integer division** is division between two whole numbers that produces a whole-number result instead of the exact, possibly fractional, answer. Every language that performs integer division has to pick its own rule for which whole number to produce, and Python and Rust pick different rules.

Python's `/` operator always produces a float, even when both values are whole numbers; it is built to give the exact answer every time. Python has a separate operator, `//`, for integer division: it divides, then rounds down to the whole number below the exact answer.

Rust takes the opposite default. Its `/` operator performs integer division automatically whenever both values are whole numbers, and it does so by **truncation**: throwing away the fractional part of the exact answer and keeping only the whole-number part that is left, without rounding further up or down. To get the exact, possibly fractional, answer in Rust, at least one of the two values must already be a float, a type the [Data Representation and Memory](/lectures/data-representation) lecture covered. In neither language is discarding a fractional part a bug: it is a direct consequence of asking for a whole-number answer to a question that does not always have one.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Float division versus integer division"
print(7 / 2)
print(7 // 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="Float division versus integer division"
fn main() {
    println!("{}", 7 / 2);
    println!("{}", 7.0 / 2.0);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Python's plain `/` always gives the exact answer as a float: `7 / 2` is `3.5`. Its second operator, `//`, gives the whole-number version: `7 // 2` is `3`. Rust's plain `/` between two whole-number literals behaves like Python's `//` for positive numbers: `7 / 2` gives the whole number `3`, and the exact answer `3.5` needs both values written as floats, `7.0 / 2.0`. One difference is easy to miss: for negative numbers, Python's `//` always rounds down, toward negative infinity, so `-7 // 2` gives `-4`; Rust's integer `/` always truncates toward zero instead, so `-7 / 2` gives `-3`, discarding the fractional `-0.5` rather than rounding past it.
</Fragment>
</WhatDiffers>

It is easy to write Python's `/` when you actually want a whole-number answer:

```python title="Division: / versus //"
print(9 / 4)   # 2.25, not 2: Python's / always gives a float
print(9 // 4)  # 2: // is the whole-number division you probably meant
```

## Mixed-Type Expressions and Implicit Coercion

An expression does not have to combine values of the same type. This section looks at what each language does when it does not, and names the automatic behavior Python relies on to make it work.

### Mixed-Type Expressions

Python freely combines a whole number and a decimal number in the same expression, deciding on the fly what type the answer should have. Rust requires every value in an expression to already share the same type, so combining a whole-number literal with a decimal literal has to be fixed before a Rust program compiles at all. This difference is a direct consequence of the static-versus-dynamic split covered in the [Data Representation and Memory](/lectures/data-representation) lecture: Rust checks that every type is used consistently before your program takes a single step, so a mismatched pair of types cannot even reach the point of running, while Python only checks a line's types once that line actually runs.

### Implicit Coercion

**Implicit coercion** is when a language automatically converts a value from one type to another so that an operation can proceed, without you writing any conversion yourself. Python's `+` coerces a whole number into a float automatically whenever the other value in the expression is already a float: running `3 + 2.5` treats the 3 as `3.0` behind the scenes, producing the float `5.5`. Rust never coerces a value's type automatically. If you want to add a whole number and a decimal number in Rust, you have to write both values with the same type yourself; there is no automatic conversion waiting to rescue a mismatched expression.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Adding a whole number and a decimal number"
print(3 + 2.5)
```
</TabItem>
<TabItem label="Rust">
```rust title="Adding a whole number and a decimal number"
fn main() {
    println!("{}", 3.0 + 2.5);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Python coerces the whole number `3` into the float `3.0` the moment the line runs, so `3 + 2.5` resolves to `5.5` without you writing a conversion. Rust performs no such coercion, so this example writes both values as floats (`3.0` and `2.5`) instead of mixing a whole number with a decimal number.
</Fragment>
</WhatDiffers>

Rust will not accept the mixed-type version Python allows:

```rust title="Adding an integer literal to a float literal (will not compile)"
fn main() {
    println!("{}", 3 + 2.5); // error: cannot add a float to an integer (Rust will not compile this)
}
```

The compiler rejects this line before your program runs at all. Python's implicit coercion hides a type mismatch by quietly resolving it; Rust's refusal to coerce turns the same mismatch into a compile error you see immediately, before the program ever takes its first step.

## Evaluating Expressions by Hand

Reading an expression and working out its value in your head, or on paper, without running any code, is a skill worth building deliberately. It lets you predict what a program will do before you run it, catch a mistake in your own reasoning before it becomes a bug, and check a program's output against what you expected. Evaluating by hand means applying the same two rules from this lecture, in order: operator precedence decides which operation happens first, and each language's own division rule decides what kind of answer a division produces.

Take the expression `10 / 4 + 3 * 2`. Operator precedence says the multiplication and the division both happen before the addition, so you work out `10 / 4` and `3 * 2` first, then add the results. In Rust, `10 / 4` divides two whole numbers, so it truncates, giving `2`; `3 * 2` is `6`; adding them gives `8`. In Python, the same `10 / 4` is Python's float-producing division, so it gives `2.5`; `3 * 2` is still `6`; adding them gives `8.5`. The two languages read the exact same expression and, because of their different division rules, land on two different final values.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Evaluating 10 / 4 + 3 * 2 by hand"
print(10 / 4 + 3 * 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="Evaluating 10 / 4 + 3 * 2 by hand"
fn main() {
    println!("{}", 10 / 4 + 3 * 2);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Written out, the two expressions look identical. Python evaluates `10 / 4` as float division and prints `8.5`; Rust evaluates the same-looking `10 / 4` as integer division, since both 10 and 4 are whole-number literals, and prints `8`.
</Fragment>
</WhatDiffers>

## Takeaways

An expression is any piece of code, from a single literal to a combination built with operators, that evaluates down to one value; every operator you have seen in this lecture takes one or more values and produces a new one. Operator precedence gives both languages the same order of operations you already know from arithmetic, so an expression with more than one operator evaluates the same way in either language, once you know each language's own rule for what dividing two whole numbers produces. That rule is where Python and Rust genuinely part ways: Python's `/` always gives the exact, possibly fractional, answer, while Rust's `/` truncates whenever both values are whole numbers, discarding the fractional part instead of rounding toward it. Mixed-type expressions expose the same static-versus-dynamic split the Data Representation and Memory lecture introduced: Python's implicit coercion quietly converts a whole number into a float so an expression like `3 + 2.5` can run, while Rust never coerces, and rejects the same mismatch before your program takes a single step. Practicing hand evaluation, working out an expression's value before running it, turns all of these rules into a skill you can use to predict, and later debug, real programs.
