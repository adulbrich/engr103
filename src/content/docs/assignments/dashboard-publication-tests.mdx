WRO's public air-quality map shows a live PM2.5 reading from every station in its network, each one recalibrated on a fixed 90-day schedule, and neighbors use that map to decide whether to keep kids indoors on a smoky day. A reading only reaches the map after it clears one more gate: a publication check that looks at the value and the timestamp together, not just the value on its own. Nobody takes the check's word for it either: before it goes live, it has to clear its own review, backed by test cases that prove it does what its specification promises. Your job as a junior engineer on the office's software team is to write that test suite, and to judge AURA's claim about the check for yourself.

## How This Assignment Works

You work **test first**: you read the specification, design the cases that will prove the function meets it, plan your test function, and only then write it. You write the test function and nothing else: the program's `main`, its input and output, the function under test, and the local test runner are already written. The problem is solvable in Python or Rust, whichever you prefer, and both are checked the same way. Because the [Testing](/lectures/testing/) lecture is behind you, you write real `assert`-based tests now, not a table of rows on the page. The automated grader runs your test function twice over: against the correct implementation printed below, where every assertion you wrote must hold, and against several broken implementations, each of which gets one thing wrong somewhere in the specification, where each one must fail at least one of your assertions. The order is fixed: design your cases, plan your test function, then write it. After that comes an optional summit stretch, a short paper trace, and a two-sentence reflection.

## The Problem

Before a reading reaches the public map, the publishing service asks one function for clearance: `dashboard_cleared`, the check that decides whether a reading may go live. Two rules govern the decision, and your suite certifies the check against both.

Here is the specification your suite certifies against:

1. `dashboard_cleared(reading_ugm3, band_min_ugm3, band_max_ugm3, age_min, clock_fault)` returns `true` exactly when both rules hold. First, the reading `reading_ugm3` must sit inside the station's plausible band, from `band_min_ugm3` through `band_max_ugm3` with both ends of the band included: outside that band a reading is too implausible to show the public without a person looking at it first. Second, the reading's timestamp must still be fresh, meaning its age `age_min`, the whole number of minutes since it was logged, is under `15`, the window WRO's publication policy allows; a reading built on a stale timestamp misrepresents current conditions.
2. A reading is never published when the station's clock-fault flag, `clock_fault`, is set, no matter how good the value looks or how fresh the timestamp appears: a station whose own clock has faulted cannot be trusted to say how old any of its readings are.

**Provided code.** You do not write `dashboard_cleared`, and you do not fix it: the correct implementation is on file, and here it is, in both languages. This is the function your test suite exercises.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Provided: the correct dashboard_cleared, on file with the office"
def dashboard_cleared(reading_ugm3, band_min_ugm3, band_max_ugm3, age_min, clock_fault):
    if clock_fault:
        return False
    in_band = band_min_ugm3 <= reading_ugm3 <= band_max_ugm3
    fresh = age_min < 15
    return in_band and fresh
```
</TabItem>
<TabItem label="Rust">
```rust title="Provided: the correct dashboard_cleared, on file with the office"
fn dashboard_cleared(reading_ugm3: i32, band_min_ugm3: i32, band_max_ugm3: i32, age_min: i32, clock_fault: bool) -> bool {
    if clock_fault {
        return false;
    }
    let in_band = band_min_ugm3 <= reading_ugm3 && reading_ugm3 <= band_max_ugm3;
    let fresh = age_min < 15;
    return in_band && fresh;
}
```
</TabItem>
</Tabs>

## Step 1: Design Your Test Cases

Before writing any test code, decide what a certified `dashboard_cleared` must do on every kind of input, and capture it as a table. Write a set of test cases as a plain table of rows: the five inputs and the boolean you expect back, worked out from the specification, not from running the code. This table is your design; you turn each row into an assertion in Step 3.

Your table must include, and label, at least these cases:

- A routine reading that publishes: a value comfortably inside the band, on a fresh timestamp, with no clock fault.
- A reading withheld for a value below the band, and one withheld for a value above it.
- The boundary readings sitting exactly on each end of the band, on a fresh timestamp.
- A reading one microgram per cubic meter outside the band at each end.
- A reading with an in-band value whose timestamp age sits exactly at the freshness limit, and one whose age is just under it.
- The clock-fault case: an in-band, fresh-looking reading whose clock-fault flag is set.
- At least one more case whose expected boolean you work out fully by hand.

A reading can be withheld for more than one reason at once when it fails both rules together; a case like that tells you less about which rule failed than one that fails for exactly one reason.

## Paper Practice

Trace this program by hand, on paper. Build a table with one row per call to `safe_margin` and one row per `assert`: for each call, write the values held by its `reading` and `limit` parameters and the value it returns; for each `assert`, write whether the condition it checks is `True` or `False`. Write the exact line the program prints, and only that line.

```python title="trace_me.py"
def safe_margin(reading, limit):
    return reading <= limit

assert safe_margin(80.0, 100.0) == True
assert safe_margin(120.0, 100.0) == False
print("both checks passed")
```

<Reveal label="Reveal the completed trace">
The first call, `safe_margin(80.0, 100.0)`, binds `reading` to `80.0` and `limit` to `100.0`, evaluates `80.0 <= 100.0`, which is `True`, and returns `True`. The first `assert` checks `True == True`, which holds, so nothing visible happens and execution moves to the next line.

| Line | `reading` | `limit` | returns | assert condition |
|---|---|---|---|---|
| `assert safe_margin(80.0, 100.0) == True` | `80.0` | `100.0` | `True` | `True` |
| `assert safe_margin(120.0, 100.0) == False` | `120.0` | `100.0` | `False` | `True` |

The second call, `safe_margin(120.0, 100.0)`, binds `reading` to `120.0` and `limit` to `100.0`, evaluates `120.0 <= 100.0`, which is `False`, and returns `False`. The second `assert` checks `False == False`, which also holds. Both assertions passed silently, so the program reaches the final line and prints `both checks passed`, and nothing else.
</Reveal>
