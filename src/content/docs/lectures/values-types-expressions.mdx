Suppose you ask a computer to compute 7 divided by 2. Is the answer 3, or is it 3.5? A person can answer either way depending on what the 7 and the 2 represent: a whole count of items splits differently than a precise measurement does. A computer cannot guess which one you mean. Before it can add, divide, or compare two pieces of data, it needs to know exactly what kind of data each one is.

This is true of almost everything a program touches: a whole number of students in a class, a price with cents, a yes-or-no answer to a question, a name typed by a user. Each of these is a different kind of thing, and a computer needs a name for that kind before it can work with it correctly.

## Values and Types

A program spends nearly all of its time holding, combining, and displaying small pieces of data. This section names that basic unit of data, names the label the computer attaches to it, and names the code that produces it.

### Values

A **value** is a single piece of data that a program works with: the number 7, the number 3.14, the truth of a statement, or a short piece of text. A value is the simplest thing a running program can hold or produce. When you write a value directly into your code, such as typing the number 7, that value is called a **literal**: a value written out exactly as it is, rather than computed from something else.

### Types

A **type** is a category that tells the computer what kind of value something is and what can be done with it. Knowing a value's type tells the computer how much space to use for it, how to display it, and which operations make sense on it: you can divide two numbers, but dividing two pieces of text makes no sense, and the computer needs to know which situation it is in.

This lecture uses four types, the ones both Python and Rust make available from the very first line of code you write:

An **integer** is a whole number, with no fractional part, such as 7 or negative 3. A **float**, short for "floating-point number," is a number that can have a fractional part, such as 3.14. A **boolean** is a value that is only ever one of two things: true or false; it gets its name from the mathematician George Boole, who studied logic built from exactly two values. A **string** is a short piece of text, such as a word or a sentence, treated by the computer as data rather than as code to run.

### Expressions

An **expression** is a piece of code that produces a value when the computer runs it. The simplest possible expression is a literal on its own: the code `7` is already an expression, and running it produces the value 7. You can also build a larger expression out of smaller ones by combining values with **operators**, symbols such as `+` that take one or more values and produce a new one. The next section of this lecture looks closely at operators; for now, it is enough to know that combining values always builds a bigger expression, never something other than a value.

Printing a value, which you saw in the previous lecture, works by first evaluating an expression down to a single value, then displaying that value in the terminal. Every example in this lecture follows that same pattern: write an expression, then print what it evaluates to.

<TabItem label="Python">
```python
print(7)
print(3.14)
print(True)
print("hello")
```
</TabItem>
<TabItem label="Rust">
```rust
fn main() {
    println!("{}", 7);
    println!("{}", 3.14);

```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Rust wraps every runnable line in a `fn main() { ... }` function and prints with `println!`, a placeholder marker `{}` standing in for the value; Python prints directly with `print(...)`. Python spells its boolean values `True` and `False`, with a capital letter; Rust spells them `true` and `false`, all lowercase. Rust also lets a literal carry an explicit type tag, such as `7i32` or `3.14f64`, though it is not required here because Rust already assumes a whole-number literal is of type `i32` and a decimal literal is of type `f64` unless told otherwise; the next section explains exactly what the `32` and `64` in those names mean.
</Fragment>
<Fragment slot="cannot">
In both languages, each literal is an expression that stands for exactly one value of exactly one type: an integer, a float, a boolean, or a string. Running either program evaluates the same four expressions and prints the same four values, in the same order, no matter which language reads them.
</Fragment>
</WhatDiffers>

## How Values Are Stored

Knowing that a value has a type is only half the picture. The other half is what "type" actually costs inside the computer: where a value's pattern lives once your program is running, and how much room the computer sets aside to hold it. This section stays in plain terms, but by the end of it, a name like `i32` will no longer be an arbitrary label; you will know exactly what the `32` names.

### Bits and Bytes

A **bit** is the smallest piece of information a computer can store: a single 0 or a single 1. Nothing smaller exists inside a computer's memory. Every value your program touches, whether an integer, a float, a boolean, or a string, is ultimately stored as some pattern of these two symbols. A **byte** is a group of 8 bits handled together as one unit; a byte is the unit programmers actually use to talk about how much space something takes, since a single bit is too small to describe anything useful on its own.

### A Type Fixes Its Storage

The Types section above defined a type as the category that tells the computer what kind of value something is and what can be done with it. The other half of that definition is how the computer lays the value out in bits. A type is a set of possible values together with a fixed scheme for storing any one of those values as a pattern of bits. Integers and floats use different schemes: an integer's bits spell out the whole number itself, while a float's bits are split between the digits of the number and where its decimal point sits, a scheme this course looks at more closely in a later lecture. That difference is why 7 and 7.0 are not stored the same way inside the computer, even though a person reading them side by side sees two versions of the same value.

### Fixed Size Versus Arbitrary Precision

Here is where Python and Rust part ways in a way that matters for the rest of this course. Python's whole-number type, `int`, is **arbitrary-precision**: it uses however many bits its current value actually needs, growing as large as it has to, so there is no whole number too big for Python's `int` to hold, short of running out of memory. Rust's default whole-number type, `i32`, instead reserves a **fixed size** for every value: exactly 32 bits, no more and no less, whether the value being stored is 0, 7, or the largest number 32 bits can represent. That fixed budget of 32 bits is exactly what the `32` in `i32` names: not a version number or an arbitrary label, but the number of bits Rust sets aside for every value of that type. Because 32 bits can only form so many distinct patterns of 0s and 1s, `i32` has a largest and a smallest value it can represent, 2,147,483,647 at the top; a whole number outside that range simply does not fit in 32 bits. Rust's default decimal type, `f64`, follows the same idea: the `64` names 64 bits, which is 8 bytes, set aside for every value of that type, a wider budget that lets `f64` represent a much larger range of decimal numbers than `i32` can represent of whole numbers, but a fixed budget all the same.

<TabItem label="Python">
```python
print(99999999999999999999999999999)
```
</TabItem>
<TabItem label="Rust">
```rust
fn main() {
    println!("{}", 2147483647);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Python's literal is simply the value written out; the `int` type places no upper limit on it, only however much memory your computer has, so a whole number this long prints back exactly as written. Rust's literal must fit inside `i32`'s fixed 32 bits, and 2,147,483,647 is the largest whole number that type can hold. Writing a bare literal even one more than that would fail to compile, because Rust's default whole-number literal always has to fit inside the 32 bits it reserves.
</Fragment>
<Fragment slot="cannot">
In both languages, an integer literal is still a whole number spelled out directly in your code, and printing it shows that same value back. What cannot differ is only how much space the type behind it is allowed to use: fixed in advance, in Rust, or free to grow as needed, in Python.
</Fragment>
</WhatDiffers>

## Static Typing and Dynamic Typing

Every value has a type, but Python and Rust disagree about when that type gets checked. This difference is one of the biggest reasons the two languages feel different to write, and it shows up again in almost every later lecture.

### Static Typing

**Static typing** means a language works out the type of every value and checks that those types are used consistently before the program ever runs. Rust is statically typed: its compiler, the program that turns your source code into a runnable one, reads through your whole file and rejects it if a type does not fit where it is used, even in a line that would never actually execute. The check happens once, ahead of time, which is why it is called static.

### Dynamic Typing

**Dynamic typing** means a language decides whether a value's type makes sense for a given operation only at the moment that operation actually runs. Python is dynamically typed: it does not check the types used on a line of code until the computer actually reaches that line while running the program. If an earlier line has a problem, Python will not notice until it gets there.

You can see the difference directly. Adding a whole number to a decimal number is something Python allows without complaint, deciding on the fly that the answer should be a float:

<Tabs syncKey="lang">
<TabItem label="Python">
```python
print(3 + 2.5)
```
</TabItem>
<TabItem label="Rust">
```rust
fn main() {
    println!("{}", 7i32);
    println!("{}", 3.14f64);
    println!("{}", 3.0 + 2.5);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Python freely adds a whole number and a decimal number, resolving `3 + 2.5` to the float `5.5` the moment that line executes, without ever asking in advance whether the two types are allowed to mix. Rust settles each literal's type before the program runs, so the example instead writes each literal with its type already fixed (`7i32`, `3.14f64`) and adds two same-typed floats. If you instead try to compile Rust's version of `3 + 2.5` with one whole-number literal and one decimal literal, as Python does, the compiler stops you before the program ever runs, reporting that it cannot add a float to an integer.
</Fragment>
<Fragment slot="cannot">
In both languages, a value's type is a real, fixed fact about that value, never something the programmer can ignore. The only difference is timing: Rust confirms every type is used consistently while compiling, before your program takes its first step; Python confirms it line by line, while the program is already running.
</Fragment>
</WhatDiffers>

## Operators and Operator Precedence

A single value on its own is not very useful; programs become powerful once values can be combined into new ones. This section names the symbol that does the combining and the rule that decides which combination happens first.

### Operators

An **operator** is a symbol that combines one or more values to produce a new value. The familiar arithmetic operators, `+`, `-`, `*`, and `/`, take two number values and produce a new number: `3 + 4` is an expression built from the operator `+` and the two values 3 and 4, and it evaluates to the value 7.

### Operator Precedence

When an expression contains more than one operator, the computer needs a rule for which operation happens first. **Operator precedence** is the set of rules a language uses to decide that order. Both Python and Rust use the same order you likely already learned for ordinary arithmetic: multiplication and division happen before addition and subtraction, and parentheses around part of an expression force that part to be evaluated first, overriding the usual order.

This course tracks exactly which pieces of each language are available at each point in the term; the current list lives on the [language ladder](/reference/language-ladder) page, and this lecture stays within its first entry.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
print(3 + 4 * 2)
print((3 + 4) * 2)
```
</TabItem>
<TabItem label="Rust">
```rust
fn main() {
    println!("{}", 3 + 4 * 2);
    println!("{}", (3 + 4) * 2);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Nothing about the arithmetic itself differs: the symbols `+`, `*`, and `(`...`)` are written the same way in both languages, and Rust's only extra requirement is wrapping the two lines in `fn main() { ... }`.
</Fragment>
<Fragment slot="cannot">
The order of operations cannot differ. `3 + 4 * 2` evaluates to 11 in both languages, because multiplication happens before addition: `4 * 2` is 8 first, then `3 + 8` is 11. Adding parentheses around `3 + 4` forces that addition to happen first instead, so `(3 + 4) * 2` evaluates to 14 in both languages: `7 * 2`.
</Fragment>
</WhatDiffers>

## Integer Versus Float Division

Division deserves its own closer look, because it is the one arithmetic operator whose exact answer often cannot be represented as a whole number.

### Integer Division

Dividing two whole numbers raises a question that addition, subtraction, and multiplication do not: what happens when the answer is not itself a whole number? **Integer division** is division between two whole numbers that produces a whole-number result instead of the exact, possibly fractional answer. Every language that does integer division has to pick its own rule for which whole number to produce, and Python and Rust pick different rules.

Python's `/` operator always produces a float, even when both values being divided are whole numbers, because it is designed to give you the precise mathematical answer. Python has a separate operator, `//`, for integer division: it divides and then rounds down to the next whole number below the exact answer. Rust takes the opposite default: its `/` operator performs integer division automatically whenever both values are whole numbers, discarding the fractional part; to get a precise, non-whole answer in Rust, at least one of the two values must already be a float.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
print(7 / 2)
print(7 // 2)
```
</TabItem>
<TabItem label="Rust">
```rust
fn main() {
    println!("{}", 7 / 2);
    println!("{}", 7.0 / 2.0);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Python's plain `/` always gives the exact answer as a float, `3.5`, and its second operator `//` gives the integer version, `3`. Rust's plain `/` between two whole-number literals instead behaves like Python's `//`: `7 / 2` gives the whole number `3`, and getting the exact answer `3.5` requires writing both values as floats, `7.0 / 2.0`. There is one more, easy-to-miss difference for negative numbers: Python's `//` always rounds down, toward negative infinity, so `-7 // 2` gives `-4`; Rust's integer `/` instead always rounds toward zero, so `-7 / 2` gives `-3`.
</Fragment>
<Fragment slot="cannot">
In both languages, it is only the operator built to produce a whole-number result that discards the fractional part: Python's `//`, and Rust's default `/` whenever both values are whole numbers. Python's plain `/` never discards it, always returning the exact answer as a float, even when both values being divided are whole numbers. That discarding, where it happens, is not a bug in either language: it is a direct consequence of asking for a whole-number answer to a question that does not always have one.
</Fragment>
</WhatDiffers>

## Evaluating Expressions by Hand

Reading an expression and working out its value in your head, or on paper, without running any code, is a skill worth building deliberately. It lets you predict what a program will do before you run it, catch a mistake in your own reasoning before it becomes a bug, and check a program's output against what you expected. Evaluating by hand means applying the same two rules from this lecture, in order: operator precedence decides which operation happens first, and each language's own division rule decides what kind of answer a division produces.

Take the expression `10 / 4 + 3 * 2`. Operator precedence says the multiplication and the division both happen before the addition, so you work out `10 / 4` and `3 * 2` first, then add the results. In Rust, `10 / 4` divides two whole numbers, so it discards the fractional part, giving `2`; `3 * 2` is `6`; adding them gives `8`. In Python, the same `10 / 4` is Python's float-producing division, so it gives `2.5`; `3 * 2` is still `6`; adding them gives `8.5`. The two languages read the exact same expression and, because of their different division rules, land on two different final values.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
print(10 / 4 + 3 * 2)
```
</TabItem>
<TabItem label="Rust">
```rust
fn main() {
    println!("{}", 10 / 4 + 3 * 2);
}
```
</TabItem>
</Tabs>

<WhatDiffers>
<Fragment slot="differs">
Written out, the two expressions look identical. Python evaluates `10 / 4` as float division and prints `8.5`; Rust evaluates the same-looking `10 / 4` as integer division, since both 10 and 4 are whole-number literals, and prints `8`.
</Fragment>
<Fragment slot="cannot">
Operator precedence itself cannot differ: both languages compute the two multiplications and divisions before the one addition. Hand-evaluating an expression always means applying precedence first and each language's own division rule second, in that order, regardless of which language you are reading.
</Fragment>
</WhatDiffers>

## Takeaways

A value is a single piece of data, and every value has a type that fixes what the computer can do with it: an integer, a float, a boolean, or a string, in this lecture. A type is also, underneath, a fixed scheme for storing a value as bits, the 0s and 1s a computer can actually hold; that is why Python's arbitrary-precision `int` can grow without limit while Rust's `i32` and `f64` reserve a fixed 32 or 64 bits and stop at a largest representable value. An expression is any piece of code, from a single literal to a combination built with operators, that evaluates down to one such value. Python and Rust agree completely on what a value and a type are; they disagree on timing, checking types dynamically while a program runs versus statically before it runs, and that one disagreement is why Rust's compiler catches certain mistakes that Python would only discover later, mid-run. Operator precedence gives both languages the same order of operations you already know from arithmetic, so an expression with more than one operator evaluates the same way in either language, once you know each language's own rule for what dividing two whole numbers produces. Practicing hand evaluation, working out an expression's value before running it, turns all of these rules into a skill you can use to predict, and later debug, real programs. The next lecture builds directly on this one: it looks at how to give a value a name, so that it can be reused and changed instead of rewritten every time it is needed.
