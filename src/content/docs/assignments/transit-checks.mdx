Six weeks into the cruise to Mars, the crew keeps the habitat's daily safety checks running exactly the way they will once nobody on Earth can talk you through a bad call. Flight software leans on a family of interlocks: small yes-or-no checks that decide whether a suit is safe to don and whether a hatch is safe to open, and a larger status check that decides whether the habitat is nominal, needs attention, needs it right now, or has to hand control to the crew. HAB, the habitat's assistant, has already drafted one of these checks. Your job is to write the interlock and status functions the flight software depends on, and to catch HAB's mistake before it clears something that is not actually safe.

Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. ### Problem 3: The Habitat Status Code

**Context.** The crew display in the command module condenses the habitat's health into a single status code: `0` for nominal, `1` for advisory, `2` for critical, and `3` for an emergency override, when a crew member has thrown the manual switch and taken control by hand. Two live readings feed the decision, the cabin pressure and the cabin oxygen level, but the override switch outranks both: when it is thrown, the code is `3` no matter what the readings say.

**Requirements.**

1. `readings_nominal(cabin_pressure_kpa, oxygen_percent)` must return `true` only when the cabin pressure is at least `99.0` kilopascals *and* the oxygen level is at least `20` percent: both readings comfortably in range at once.
2. `system_status(cabin_pressure_kpa, oxygen_percent, emergency_override)` must return the status code, in this priority order:
   - Return `3` whenever `emergency_override` is `true`, no matter what the two readings say. The override collapses every other check: once it is thrown, nothing below it is even asked.
   - Otherwise, return `2` when the cabin pressure is below `95.0` kilopascals *or* the oxygen level is below `18` percent. Either reading breaching its hard floor is critical on its own.
   - Otherwise, return `1` when the readings are *not* nominal. Call `readings_nominal` and negate its result with `not`; a reading that is above its hard floor but not yet comfortably in range is an advisory.
   - Otherwise, return `0`.

Because `elif` is not on the ladder yet, write these four outcomes as nested `if`/`else` blocks: check the override first, and only once you have ruled it out ask about the readings, nesting each further decision inside the `else` of the one before it. `system_status` must call `readings_nominal` rather than repeating its two comparisons.

The modeling step is choosing the priority order, override first, then the hard-floor critical check, then advisory, then nominal, and deciding which comparisons and which of `and`, `or`, and `not` each row needs; the analysis step is writing that priority as nested `if`/`else` blocks that call `readings_nominal`, checking the highest-priority condition first so a thrown override is never masked by a good reading.

## Paper Practice

Trace this program by hand, on paper. Build a variable table: for the call to `is_low_power`, write the value its `battery_percent` parameter holds and what it returns; then, for `check_drill_status`, write the values bound to its two parameters, to `low_power`, and to `result`. Write the exact value the program prints. Photograph your table and trace and attach it. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.

```python title="trace_me.py"
def is_low_power(battery_percent):
    return battery_percent < 25

def check_drill_status(oxygen_percent, battery_percent):
    low_power = is_low_power(battery_percent)
    if oxygen_percent >= 20 and not low_power:
        result = 1
    else:
        result = 0
    return result

status = check_drill_status(22, 18)
print(status)
```

<Reveal label="Reveal the completed trace">
The call `check_drill_status(22, 18)` pushes a frame with `oxygen_percent = 22` and `battery_percent = 18`. Inside it, `is_low_power(18)` pushes a second frame with `battery_percent = 18`, computes `18 < 25`, and returns `true`; that frame is popped, and `true` is bound to `low_power` in `check_drill_status`'s own frame.

| Line | frame | `oxygen_percent` | `battery_percent` | `low_power` | `result` |
|---|---|---|---|---|---|
| `is_low_power(18)` called | `is_low_power` | | `18` | | |
| `return battery_percent < 25` | `is_low_power` | | `18` | | (returns `true`) |
| `low_power = is_low_power(battery_percent)` | `check_drill_status` | `22` | `18` | `true` | |
| `if oxygen_percent >= 20 and not low_power:` | `check_drill_status` | `22` | `18` | `true` | |
| `result = 0` | `check_drill_status` | `22` | `18` | `true` | `0` |

The condition checks `22 >= 20`, which is `true`, `and`ed with `not low_power`, which is `not true`, or `false`. `true and false` is `false`, so the `if` block is skipped and the `else` block runs, binding `result` to `0`. The program prints `0`.
</Reveal>
