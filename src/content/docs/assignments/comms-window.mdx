Earth and the habitat are drifting into solar conjunction, the weeks each Martian year when the sun sits almost directly between the two and chews every radio packet into static and dropped bits. Mission Control still has to reach the crew, so flight software leans on two old tricks: a simple cipher shifts each letter of a message so a bit of noise cannot be mistaken for real words, and a checksum folds every character's code into one number so a corrupted packet can be caught before anyone acts on it. The comms dish itself is being re-aimed 34 degrees to hold the signal as long as possible, a detail for the antenna log and nothing your functions need. Your job as the flight-software crew member on shift is to write the small, one-character-at-a-time functions the cipher and the checksum are built from.

## How This Assignment Works

You write the functions named below and nothing else: the program's `main`, its input, its output, and the local test runner are already written, and the automated grader calls your functions directly with values it chooses, reading only what you `return`. Every function here takes and returns only a `char`, an `i32`, or a `bool`: none takes or returns a whole string or a whole list, because `main` handles the looping over a message and calls your functions once per character. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your functions to the grader from the course starter repository. The assignment has four parts: the problem set below, a paper trace, a two-sentence reflection, and an optional summit problem.

## Problem Set

### Problem 1: The Cipher Shift, and One of HAB's Drafts

**Context.** The outbound cipher shifts every letter of a message forward through its own alphabet by a fixed number of positions, wrapping past the end back around to the start, so the same amount of shift can later be undone. A packet can carry uppercase letters, lowercase letters, and noise that is not a letter at all, and the cipher must treat the three differently. HAB already drafted the forward shift.

**Requirements.**

1. `shift_char(c, n)` must return the character that lies `n` positions forward from `c`, in whichever alphabet `c` belongs to. A lowercase letter wraps within `a` through `z`; an uppercase letter wraps within `A` through `Z`, keeping its case; a character that is not a letter at all must be returned unchanged, since the cipher never touches noise or punctuation. Shifting `a` forward by `1` gives `b`; shifting `z` forward by `1` wraps around to `a`; shifting `Z` forward by `1` wraps around to `A`, not `a`.

The modeling step is splitting "shift this character" into the three cases the mission's packets can contain, lowercase, uppercase, and non-letter, and representing each letter case as its own cycle of 26 positions rather than a straight line that stops at its last letter; the analysis step is computing the wrapped position within the right case and turning it back into a character, or leaving a non-letter untouched.

<Reveal label="Reveal a nudge on HAB's mistake">
HAB never wraps back to `a`, and never checks which case, or whether `c` is even a letter, either. Adding `n` straight onto `c`'s ASCII code keeps climbing past `z` (code `122`) into whatever punctuation sits next in the table, `'~'` in this case, instead of returning to the start of the alphabet. Work in a position relative to the letter's own starting point instead of the raw ASCII code: subtract `a`'s code (or `A`'s, for an uppercase letter) from `c`'s code to get a number from `0` to `25`, add `n`, wrap it back into `0` through `25` with `% 26`, and only then add the same starting code back before turning the number into a character. A character that is not a letter at all skips all of this and comes back unchanged.
</Reveal>
</Aside>

<Aside type="tip" title="Do not let the position go negative">
Subtracting `n` from `c`'s position relative to its own starting letter can land below `0` before you wrap it, and the `expressions and operators` lecture already flagged that `%` treats a negative left side differently in Python and in Rust. Sidestep the whole question: add `26` to the subtracted position before taking `% 26`, so the value handed to the remainder operator never goes negative in either language.
</Aside>

<WhatDiffers>
<Fragment slot="differs">
If you subtract first and take the remainder second, without adding `26` back in, Python's `%` still returns a value from `0` to `25` because Python's remainder always keeps the sign of the divisor. Rust's `%` on a negative left-hand value returns zero or a negative number, since Rust's remainder keeps the sign of the dividend instead, so the same expression that quietly works in Python can hand Rust a negative position and a wrong character. Adding `26` before the `% 26` avoids the divergence entirely, in both languages.
</Fragment>
</WhatDiffers>

### Problem 4: The Packet Checksum

**Context.** Every packet ends with a single checksum number, folded together one character at a time from each character's numeric code, so a receiver can tell whether conjunction noise corrupted anything on the way down. The checksum is kept inside one byte's range, `0` through `255`, by wrapping it every time it grows past that.

**Requirements.**

The modeling step is choosing to fold the packet down to one running number instead of keeping every character's code around; the analysis step is the addition and the modulo that keeps that number inside a byte.

## Paper Practice

Trace this program by hand, on paper. Build a variable table with a row for each call to `checksum_step`, tracking `running` before and after the call. Write the exact value the program prints. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.

```python title="trace_me.py"
def checksum_step(running, code):
    return (running + code) % 256

running = 0
c1 = 97
c2 = 98
c3 = 250
running = checksum_step(running, c1)
running = checksum_step(running, c2)
running = checksum_step(running, c3)
print(running)
```

<Reveal label="Reveal the completed trace">
Each call adds one more character's code into `running` and wraps the result back into `0` through `255`.

| Call | `running` before | `code` | `running` after |
|---|---|---|---|
| `checksum_step(running, c1)` | `0` | `97` | `97` |
| `checksum_step(running, c2)` | `97` | `98` | `195` |
| `checksum_step(running, c3)` | `195` | `250` | `189` |

The third call adds `195 + 250 = 445`, and `445 % 256` is `189`, the wraparound taking effect for the first time. The program prints `189`. The same program written in Rust prints the same whole number, `189`, with no display difference here since every value is a whole `i32`, never a float.
</Reveal>
