The previous lecture handed you the raw machinery of repetition: a `while` loop that re-checks a condition, a `for` loop that walks a range, and `break`, `continue`, and nesting to steer the passes. On their own those pieces feel open-ended, and a beginner staring at a new problem often knows a loop is needed without knowing how to shape one. What turns that machinery into a tool you reach for with confidence is a small discovery: nearly every loop you will ever write is one of a handful of recurring shapes. Adding up numbers, counting how many meet a test, hunting for the first match, reading input until a stop value, re-asking until an answer is valid, filling a grid: these come up again and again across problems that otherwise have nothing to do with each other. Each shape is a **pattern**, a reusable arrangement of a loop and a few variables that you learn once and then recognize everywhere. This lecture teaches those patterns as mechanisms, so that meeting a new problem you can ask not "how do I write a loop" but the sharper question "which of these shapes does this problem want."

## Accumulate a running total

An **accumulator** is a variable that holds a result being built up across the passes of a loop: you set it to a starting value before the loop, update it on every pass, and read its final value after the loop ends. The name comes from what it does, it accumulates, gathering a little more of the answer each time around. The running total is the plainest case: a variable that starts at zero and has each number added into it, so that after the last pass it holds the sum of them all.

The mechanism has three parts, and each sits in a different place relative to the loop, which is what makes the pattern recognizable. First, before the loop, you create the accumulator and give it a starting value that is correct for zero passes: for a sum that is `0`, because the sum of no numbers at all is zero. Second, inside the loop body, you update the accumulator using its own current value, `total = total + n`, which reads what the accumulator holds now and stores a new value one step further along. Third, after the loop, the accumulator holds the finished result and you use it. Miss the initialization and there is no value to add into; miss the update and the accumulator never grows; read it inside the loop instead of after and you see a half-finished total.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Summing 1 through 5"
total = 0
for n in range(1, 6):
    total = total + n
print(total)
```
</TabItem>
<TabItem label="Rust">
```rust title="Summing 1 through 5"
fn main() {
    let mut total = 0;
    for n in 1..6 {
        total = total + n;
    }
    println!("{}", total);
}
```
</TabItem>
</Tabs>

Trace `total` pass by pass, because the whole pattern lives in how that one variable changes. It starts at `0`. The `for` loop walks `n` through `1, 2, 3, 4, 5`, the half-open range from the loops lecture. On the first pass `n` is `1`, so `total = total + n` computes `0 + 1` and stores `1`. On the next pass `n` is `2`, so `total` becomes `1 + 2`, which is `3`. Then `n` is `3` and `total` becomes `3 + 3`, which is `6`; then `n` is `4` and `total` becomes `6 + 4`, which is `10`; then `n` is `5` and `total` becomes `10 + 5`, which is `15`. The range is now exhausted, the loop ends, and `total` holds `15`, the sum of `1` through `5`. Only now, after the loop, does `print` read it.

```text frame="terminal" title="Output"
15
```

A running product is the same pattern with two changes that follow directly from the trace above: start the accumulator at `1` instead of `0`, and multiply instead of add, `product = product * n`. The starting value is `1` because multiplying by the starting value must not disturb the result, and `1` is the number that leaves a product unchanged, just as `0` leaves a sum unchanged. Recognizing that the initial value has to be the neutral value for the operation is what lets you adapt the accumulator to sums, products, and beyond without re-deriving it each time.

## Count the matches

The **count pattern** is an accumulator with a gate in front of it: instead of updating on every pass, it adds `1` only on the passes where a condition is true, so that after the loop it holds the number of items that met the test. It answers "how many," and it is the accumulate pattern you just saw with two adjustments, the accumulator always grows by exactly `1`, and the growth is wrapped in an `if`.

That `if` is the whole idea. A counter starts at `0` before the loop, exactly like a sum. Inside the loop, an `if` checks the condition that decides whether the current item counts; when the condition is true the body runs `count = count + 1`, and when it is false the body does nothing and the counter keeps its value into the next pass. Because the increment is always `1`, the counter ends holding one for each pass on which the condition held, which is precisely the count you wanted. The example counts how many whole numbers from `1` to `20` are divisible by `3`, using the remainder operator `%` from an earlier lecture: `n % 3` is the remainder after dividing `n` by `3`, and it is `0` exactly when `3` divides `n` evenly.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Counting multiples of 3 up to 20"
count = 0
for n in range(1, 21):
    if n % 3 == 0:
        count = count + 1
print(count)
```
</TabItem>
<TabItem label="Rust">
```rust title="Counting multiples of 3 up to 20"
fn main() {
    let mut count = 0;
    for n in 1..21 {
        if n % 3 == 0 {
            count = count + 1;
        }
    }
    println!("{}", count);
}
```
</TabItem>
</Tabs>

Trace `count` against the passes that matter. It starts at `0`. As `n` walks `1, 2, 3, ..., 20`, most passes leave `count` untouched: `n` of `1` gives `1 % 3` of `1`, not `0`, so the `if` is false and nothing happens. The first pass that changes anything is `n` of `3`, where `3 % 3` is `0`, so the `if` is true and `count` becomes `1`. The same happens at `6`, lifting `count` to `2`, then at `9` to `3`, at `12` to `4`, at `15` to `5`, and at `18` to `6`. No later value up to `20` is divisible by `3`, so the loop finishes with `count` at `6`. The six passes that incremented it, `3, 6, 9, 12, 15, 18`, are exactly the multiples of `3` in range, which is the answer.

```text frame="terminal" title="Output"
6
```

The gate in front of the increment is the only thing that separates counting from summing, and seeing that connection is more useful than memorizing two patterns. A sum adds the value of each item; a count adds `1` for each item that passes a test. Change what you add, or when you add it, and the same loop skeleton produces a different answer.

## Search for the first match

The **search pattern** looks through items one at a time and stops the instant it finds one that satisfies a condition, using `break` to leave the loop early rather than running every remaining pass for nothing. Where accumulate and count must visit every item to be correct, a search is done the moment it succeeds, and the pattern's job is both to stop promptly and to remember what it found so the code after the loop knows the outcome.

Remembering the outcome is the part beginners miss, so it is worth stating plainly. A `break` leaves the loop, but by itself it leaves no record of *why* it left, and a loop can also end normally by exhausting its range without ever finding a match. The code after the loop needs to tell those two endings apart. The pattern solves this with a **found flag**: a boolean variable, set to `false` before the loop, that the body flips to `true` in the same `if` that runs the `break`. After the loop, the flag answers the one question that matters, did the search succeed, and a second variable records the matching value itself. The example finds the first whole number whose square is at least `50`.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="First number whose square reaches 50"
found = False
answer = 0
for n in range(1, 100):
    if n * n >= 50:
        answer = n
        found = True
        break
if found:
    print("First number whose square reaches 50:", answer)
else:
    print("No number found in range.")
```
</TabItem>
<TabItem label="Rust">
```rust title="First number whose square reaches 50"
fn main() {
    let mut found = false;
    let mut answer = 0;
    for n in 1..100 {
        if n * n >= 50 {
            answer = n;
            found = true;
            break;
        }
    }
    if found {
        println!("First number whose square reaches 50: {}", answer);
    } else {
        println!("No number found in range.");
    }
}
```
</TabItem>
</Tabs>

Trace it. Before the loop, `found` is `false` and `answer` is `0`, the values that are correct if nothing is ever found. The loop walks `n` from `1` upward. For `n` of `1` the square is `1`, not at least `50`, so the `if` is false and the loop moves on; the same for `2` through `7`, whose squares are `4, 9, 16, 25, 36, 49`, all below `50`. On the pass where `n` is `8`, the square is `64`, which is at least `50`, so the `if` is finally true: the body stores `8` into `answer`, sets `found` to `true`, and runs `break`. The loop stops at once, never testing `9` or anything above it. After the loop, `found` is `true`, so the first branch runs and prints the answer. Had the range held no qualifying number, the loop would have ended by exhaustion with `found` still `false`, and the `else` branch would report that instead.

```text frame="terminal" title="Output"
First number whose square reaches 50: 8
```

The `break` and the found flag work as a pair. The `break` from the loops lecture supplies the "stop early" half, and the flag supplies the "and here is what happened" half; without the flag the code after the loop cannot distinguish a successful early stop from a search that ran out of numbers. That pairing, a `break` inside an `if` alongside a flag the same `if` sets, is the signature of a search, and once you can spot it you will see it behind every "find the first" problem.

## Read until a sentinel

A **sentinel value** is a designated input that means "stop," a value chosen to signal the end of a series rather than to be processed as data. When a program reads a sequence of numbers from a person and cannot know in advance how many there will be, it needs some agreed signal for "that was the last one," and a sentinel is that signal: a specific value, `0` here, that the person types to end the series. Every value before the sentinel is real data to handle; the sentinel itself is only a marker and is never added to the result.

This pattern is the first here to read [console input](/lectures/errors-input-and-validation) inside a loop, so its shape differs from the range-driven patterns above. There is no range, because the number of inputs is unknown, so the loop is one that repeats on purpose until something inside it decides to stop: `while True` in Python and `loop` in Rust, the deliberate-forever loops from the loops lecture, each escaped by a `break`. On every pass the body reads one line, turns it into a number, and then checks it against the sentinel before doing anything else with it. If the number equals the sentinel, the body runs `break` and the loop ends immediately, so the sentinel is never processed. Otherwise the body treats the number as data, here adding it into a running total, exactly the accumulator from the first section, and loops back to read the next line.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Summing numbers until 0 is entered"
total = 0
while True:
    line = input()
    number = int(line)
    if number == 0:
        break
    total = total + number
print("Total:", total)
```
</TabItem>
<TabItem label="Rust">
```rust title="Summing numbers until 0 is entered"
use std::io;

fn main() {
    let mut total = 0;
    loop {
        let mut line = String::new();
        io::stdin().read_line(&mut line).expect("failed to read line");
        let number: i32 = line.trim().parse().expect("please enter a whole number");
        if number == 0 {
            break;
        }
        total = total + number;
    }
    println!("Total: {}", total);
}
```
</TabItem>
</Tabs>

Trace a run where the person types `3`, then `5`, then `2`, then `0`. Before the loop, `total` is `0`. On the first pass the body reads `3`, which is not the sentinel, so it adds `3` into `total`, making it `3`. The second pass reads `5`, not the sentinel, so `total` becomes `8`. The third pass reads `2`, not the sentinel, so `total` becomes `10`. The fourth pass reads `0`, which *is* the sentinel, so the `if` is true, `break` runs, and the loop ends before `0` can be added to anything. After the loop, `total` holds `10`, the sum of the three real values, and the `0` contributed nothing but the signal to stop.

To run each program, supply the four lines as input. The command pipes them in as if a person had typed each and pressed Enter, so the run is fully reproducible.

```bash title="Run the Python program"
printf '3\n5\n2\n0\n' | python3 sentinel.py
```

```text frame="terminal" title="Output"
Total: 10
```

```bash title="Compile and run the Rust program"
rustc sentinel.rs
printf '3\n5\n2\n0\n' | ./sentinel
```

```text frame="terminal" title="Output"
Total: 10
```

The order of the two steps in the body, check for the sentinel *before* handling the value, is not a detail you can rearrange. Add the number first and only then check for the sentinel, and the stopping value gets folded into the total before the loop notices it is the signal to quit. The pattern reads, tests for the sentinel, and only then treats the value as data, precisely so the marker never leaks into the result.

<WhatDiffers>
<Fragment slot="differs">
Reading input inside a loop is where the two languages diverge most. Python's `input` returns the typed line directly, and `int` parses it, so the body is two short lines. Rust reads with `io::stdin().read_line`, which appends the typed text onto a `String` and returns a `Result` you must handle, so the body creates a fresh `String` on each pass, calls `.trim()` to drop the newline `read_line` leaves attached, and parses with `.parse()`; the `.expect` calls turn a failed read or parse into a crash. Creating the `String` inside the loop gives each pass a clean, empty buffer to read into. The `&mut line` hands `read_line` permission to change the string rather than just look at it, exactly as in the errors lecture; the memory-model lecture, a few lectures ahead, explains `&mut` fully, so for now the recipe is all you need.
</Fragment>
</WhatDiffers>

## Validate until correct

The [errors and input lecture](/lectures/errors-input-and-validation) showed how to read a value, parse it into a number, and validate that the number makes sense, but it stopped at reporting a bad value once, because repeating a request until the answer is finally right is a loop, and loops had not been introduced. The **validate-until-correct** pattern is that missing piece: a loop that keeps re-prompting the person until the input both parses and passes validation, and only then lets the program move on with a value it can trust.

The pattern wraps the read-parse-validate sequence from that lecture in a deliberate-forever loop and uses `continue` to reject a bad value by jumping straight back to the top for another try. Each pass reads a line and attempts to parse it. If the parse fails, the value is not even a number, so the body prints a message and runs `continue`, abandoning the rest of the pass and looping back to re-prompt. If the parse succeeds, the body then checks the value against the program's rules; if that check fails, it likewise prints a message and runs `continue`. Only when both the parse and the validation succeed does the body reach the `break` that ends the loop, so the loop can only exit with a value that is known to be good. After the loop, the program uses that value with no further checking, because the loop's exit condition already guarantees it is valid. The example keeps asking for an age until it receives a whole number between `0` and `130`. Two spellings in the Rust version are worth a note as you read it: `let age;` declares the variable without giving it a value yet, so the loop can fill it in later, and the parse is written `.parse::<i32>()`, where the `::<i32>` names the target type when Rust cannot infer it from context; both are part of the fixed input recipe, not new machinery to learn.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Re-prompting until the age is valid"
while True:
    age_text = input("Enter your age: ")
    try:
        age = int(age_text)
    except ValueError:
        print("That is not a whole number. Try again.")
        continue
    if age < 0 or age > 130:
        print("That age is out of range. Try again.")
        continue
    break
print("You are", age, "years old.")
```
</TabItem>
<TabItem label="Rust">
```rust title="Re-prompting until the age is valid"
use std::io;

fn main() {
    let age;
    loop {
        println!("Enter your age: ");
        let mut line = String::new();
        io::stdin().read_line(&mut line).expect("failed to read line");
        let value = match line.trim().parse::<i32>() {
            Ok(n) => n,
            Err(_) => {
                println!("That is not a whole number. Try again.");
                continue;
            }
        };
        if value < 0 || value > 130 {
            println!("That age is out of range. Try again.");
            continue;
        }
        age = value;
        break;
    }
    println!("You are {} years old.", age);
}
```
</TabItem>
</Tabs>

Trace a run where the person types `abc`, then `200`, then `21`. On the first pass the body reads `abc` and tries to parse it; `abc` is not a number, so the parse fails, the body prints `That is not a whole number. Try again.` and runs `continue`, sending control back to re-prompt without reaching the range check or the `break`. On the second pass the body reads `200`, which parses to a genuine whole number, so the parse step is happy; but the range check `age < 0 or age > 130` is true, so the body prints `That age is out of range. Try again.` and runs `continue`, looping back once more. On the third pass the body reads `21`, which parses and also passes the range check, so control falls past both `continue` points to the `break`, which ends the loop. After the loop, `age` holds `21`, and the program reports it.

```bash title="Run the Python program"
printf 'abc\n200\n21\n' | python3 validate.py
```

```text frame="terminal" title="Output"
Enter your age: That is not a whole number. Try again.
Enter your age: That age is out of range. Try again.
Enter your age: You are 21 years old.
```

```bash title="Compile and run the Rust program"
rustc validate.rs
printf 'abc\n200\n21\n' | ./validate
```

```text frame="terminal" title="Output"
Enter your age: 
That is not a whole number. Try again.
Enter your age: 
That age is out of range. Try again.
Enter your age: 
You are 21 years old.
```

The two transcripts arrange the prompt differently because the languages print it differently: Python's `input("Enter your age: ")` writes the prompt without ending the line, so the answer would be typed right after it, while Rust's `println!` always ends the line, so the answer lands on the line below.

The reason this pattern is worth isolating is the guarantee it produces. Because the loop exits only through the `break`, and the `break` is reachable only after both the parse and the range check have succeeded, every line of code after the loop can treat `age` as a valid number without re-checking it. The validation is concentrated in one place, the loop, and everything downstream is freed from worrying about bad input. That is the payoff of validating in a loop rather than scattering checks throughout the program: the bad values are turned away at a single door.

<WhatDiffers>
<Fragment slot="differs">
The two languages reject a bad value through the different failure models from the errors lecture. Python wraps the parse in `try`/`except`; a `ValueError` jumps into the `except` block, which prints and runs `continue`. Rust's `parse` returns a `Result`, and a `match` reads it: the `Err` arm prints and runs `continue`, while the `Ok` arm hands back the number. Rust also declares `age` before the loop with `let age;` and assigns it only at the `break`; because the loop can exit no other way, the compiler can prove `age` is set before the final `println!` uses it, so this compiles even though `age` is given no starting value.
</Fragment>
</WhatDiffers>

## A grid with nested loops

The patterns so far each produce a single value or a single decision. A **nested-loop pattern** produces a two-dimensional result instead, pairing every value of one thing with every value of another, which is exactly what a table or grid is. The nested loops from the loops lecture supply the structure: an outer loop walks the rows, and for each row an inner loop walks the columns, so the inner body runs once for every row-and-column combination. A multiplication table is the clearest example, where the value in each cell is the row number times the column number.

The nesting itself works exactly as the loops lecture traced it; what is new here is the printing. Each pass of the inner loop prints one cell, and because the printing does not end the line, the cells of a row land next to each other. When the inner loop finishes a row, the outer loop's body prints an empty line to move down to the next row before the inner loop starts over. That combination, print each cell without a newline across a row, then print a newline at the row's end, is what turns a stream of numbers into a visible grid.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="A 5 by 5 multiplication table"
for row in range(1, 6):
    for col in range(1, 6):
        print(row * col, end="\t")
    print()
```
</TabItem>
<TabItem label="Rust">
```rust title="A 5 by 5 multiplication table"
fn main() {
    for row in 1..6 {
        for col in 1..6 {
            print!("{}\t", row * col);
        }
        println!();
    }
}
```
</TabItem>
</Tabs>

Trace the structure rather than every cell. With `row` fixed at `1`, the inner loop sweeps `col` through `1` to `5`, printing `1 2 3 4 5` across one line, each cell followed by a tab; the bare print at the row's end then drops to the next line. Each later pass of the outer loop restarts the inner loop for its row, ending with `5 10 15 20 25`. The inner body ran <Latex formula="5 \times 5 = 25" /> times in all, once per cell, the multiplying pass counts the loops lecture already explained.

```text frame="terminal" title="Output"
1	2	3	4	5
2	4	6	8	10
3	6	9	12	15
4	8	12	16	20
5	10	15	20	25
```

The pattern's signature is the split of work between the two loops: the inner loop builds one row, and the outer loop stacks the rows. Whenever a problem asks you to pair everything in one set with everything in another, a times table, a grid of coordinates, a chart with rows and columns, this is the shape it wants, and the question to answer first is only which quantity varies across a row and which varies down the rows.

<WhatDiffers>
<Fragment slot="differs">
Building a row means printing several cells on one line, so both languages need a way to print without ending the line. Python passes `end="\t"` to `print`, which replaces the newline `print` normally adds with a tab, then a bare `print()` at the row's end supplies the newline. Rust uses `print!`, the sibling of `println!` that does not add a newline, and a bare `println!()` ends the row.
</Fragment>
</WhatDiffers>

## Choosing the pattern from the problem

Knowing six patterns is only half the skill; the other half is reading a problem and recognizing which one it is asking for, before writing a single loop. The patterns are distinguished less by their loops, which look nearly alike, than by what they keep across the passes and when they stop, and a few words in a problem statement point almost directly at the answer.

Listen for what the problem wants at the end. If it asks for a single combined number built from many, a total, a product, an average, that is an **accumulator**: a variable started at the operation's neutral value and updated every pass. If it asks *how many* items meet some test, that is the **count pattern**, the same accumulator with the update guarded by an `if` and the step fixed at `1`. If it asks for the *first* item meeting a test, or whether any item does at all, that is the **search pattern**: a loop with a `break` and a found flag, stopping the moment it succeeds and recording that it did. These three all walk a known set of items to the end, except search, which is allowed to stop early.

Listen next for how the repetition ends. If the problem reads input whose length is not known ahead of time and a special value marks the end, that is the **sentinel value** pattern: a deliberate-forever loop that reads, checks for the marker before handling the value, and breaks on it. If it insists a value be acceptable before the program continues, re-asking on anything bad, that is **validate-until-correct**: the same forever loop, rejecting with `continue` and leaving only through a `break` that guarantees a good value. And if it pairs every item of one kind with every item of another, filling rows and columns, that is the nested-loop grid, an inner loop building a row inside an outer loop stacking the rows.

Seen this way, the patterns are not six unrelated tricks but a few ideas recombined. Count is accumulate with a condition. Search is a loop plus `break` plus a flag. Sentinel and validate are both a forever loop that reads and breaks, differing only in what makes them stop, a marker value versus a value that passes every check. The grid is one pattern nested inside itself. What you carry away is not six memorized snippets but the habit of asking, of any looping problem, what it keeps across passes and what makes it stop, because those two answers name the pattern.

## Takeaways

The loops lecture gave you the machinery of repetition; this one gives you the shapes that machinery almost always takes. An accumulator is a variable set to a neutral value before a loop, updated on every pass, and read after, and it is the root of two more patterns: the count pattern is an accumulator whose update is a fixed step of `1` guarded by an `if`, and a running product is an accumulator that multiplies from a start of `1`.

The search pattern trades visiting every item for stopping at the first match, pairing a `break` with a found flag so the code after the loop can tell a success from a search that ran out of items.

Reading input in a loop brings two patterns that repeat on purpose until something inside them stops. The sentinel pattern reads until a designated stop value appears, checking for that value before ever treating it as data. The validate-until-correct pattern re-prompts with `continue` until an input both parses and passes validation, exiting only through a `break` that guarantees every later line can trust the value.

Nested loops build a two-dimensional result, an inner loop laying down a row inside an outer loop stacking the rows, so the inner body runs once per cell and the pass counts multiply.

Underneath all six is a single skill worth more than any one of them: reading a problem to see what it keeps across passes and what makes it stop, and letting those two answers choose the pattern. The next lecture turns from numbers to text, introducing strings and the characters they are built from, where several of these same patterns, accumulate, count, and search, reappear applied to the letters of a word.
