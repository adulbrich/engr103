Every piece of flight software clears a qualification review before Mission Control trusts it in flight, and the review board does not take a function's word for it: it wants the test cases that prove the function does what its specification promises. On Sol 214 the crew holds the review slot for the maneuvering thruster's pulse clearance check, the guard that decides, before every firing, whether a commanded pulse may run. The thruster on the docket is rated to deliver `22` newtons of thrust. HAB has already run the check twice, watched both answers come back as it expected, and called the check qualified. Your job on the review board is to write the test suite that certifies the pulse clearance check, and to judge HAB's sign-off for yourself.

## How This Assignment Works

You work **test first**, the way flight software is really qualified: you read the specification, design the cases that will prove the function meets it, plan your test function, and only then write it. You write the test function and nothing else: the program's `main`, its input and output, the function under test, and the local test runner are already written. The problem is solvable in Python or Rust, whichever you prefer, and both are checked the same way. Because the [Testing](/lectures/testing/) lecture is behind you, you write real `assert`-based tests now, not a table of rows on the page. The automated grader runs your test function twice over: against the correct implementation printed below, where every assertion you wrote must hold, and against several broken implementations, where each broken one must fail at least one of your assertions. The order is fixed: design your cases, plan your test function, then write it. After that comes an optional summit stretch, a short paper trace, and a two-sentence reflection.

## The Problem

Before a maneuvering thruster fires, the flight computer asks one function for clearance: `pulse_cleared`, the check that decides whether a commanded pulse may run. Two rules govern the decision, and the board qualifies the check against both.

Here is the specification the board qualifies against:

1. `pulse_cleared(pulse_ms, min_pulse_ms, max_pulse_ms, age_s)` returns `true` exactly when both rules hold. First, the commanded pulse length `pulse_ms` must sit inside the thruster's rated band, from `min_pulse_ms` through `max_pulse_ms` with both ends of the band included: below the band a pulse is too short to fire cleanly, and above it the burn runs longer than the hardware is built to survive. Second, the guidance telemetry the command was computed from must still be fresh, meaning its age `age_s` is under `30` seconds; a command built on stale telemetry aims the burn at where the spacecraft used to be. If either rule fails, the function returns `false`.
2. One reading overrides everything: an `age_s` below `0` means the telemetry clock itself has faulted, since no reading can be a negative number of seconds old, and a command is never cleared on a faulted clock, no matter how good the pulse looks.

**Provided code.** You do not write `pulse_cleared`, and you do not fix it: the board's correct implementation is on file, and here it is, in both languages. This is the function your test suite exercises.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="Provided: the correct pulse_cleared, on file with the board"
def pulse_cleared(pulse_ms, min_pulse_ms, max_pulse_ms, age_s):
    if age_s < 0:
        return False
    in_band = min_pulse_ms <= pulse_ms and pulse_ms <= max_pulse_ms
    fresh = age_s < 30
    return in_band and fresh
```
</TabItem>
<TabItem label="Rust">
```rust title="Provided: the correct pulse_cleared, on file with the board"
fn pulse_cleared(pulse_ms: i32, min_pulse_ms: i32, max_pulse_ms: i32, age_s: i32) -> bool {
    if age_s < 0 {
        return false;
    }
    let in_band = min_pulse_ms <= pulse_ms && pulse_ms <= max_pulse_ms;
    let fresh = age_s < 30;
    return in_band && fresh;
}
```
</TabItem>
</Tabs>

Alongside it, the grader holds several broken implementations, each of which quietly gets one thing wrong somewhere in the two rules: an edge of the rated band made strict or moved by one, the freshness comparison written with the wrong operator or its limit off by one, or the clock-fault rule dropped so an impossible age slips through as fresh. Your job is to write `test_pulse_cleared`, a test function whose body is a sequence of assertions checking `pulse_cleared` against the specification, ending with a printed confirmation line once every assertion has held. A suite that passes the correct implementation but lets any broken one slip through has not qualified the check.

**Assumptions and edge cases.** All four inputs are whole numbers. `pulse_ms`, `min_pulse_ms`, and `max_pulse_ms` are zero or greater, with `min_pulse_ms` no greater than `max_pulse_ms`, and a zero pulse is a legal command. `age_s` can be any whole number, including a negative one, which a healthy sensor never reports.

## Step 1: Design Your Test Cases

Before writing any test code, decide what a qualified `pulse_cleared` must do on every kind of input, and capture it as a table. Write a set of test cases as a plain table of rows: the four inputs and the boolean you expect back, worked out from the specification, not from running the code. This table is your design; you turn each row into an assertion in Step 3.

Your table must include, and label, at least these cases:

- A routine command that clears: a pulse comfortably inside the band, on fresh telemetry.
- A command refused for a pulse below the band, and one refused for a pulse above it.
- The boundary commands sitting exactly on each end of the band, on fresh telemetry.
- A command one millisecond outside the band at each end.
- A command with an in-band pulse whose telemetry age sits exactly at the freshness limit, and one whose age is just under it.
- The clock-fault case: an in-band pulse whose telemetry age is negative.
- At least one more case whose expected boolean you work out fully by hand.

A weak suite passes a broken implementation without noticing; a strong suite has, for every way an implementation could get a rule wrong, at least one case on which the correct check and that wrong one are forced to disagree. Two rules interact here, so a case can be refused for more than one reason at once, and a case like that tells you less than one refused for exactly one reason. Think about what HAB claimed while you design these.

<WhatDiffers>
<Fragment slot="differs">
You write these assertions differently in the two languages, and this is a real difference, not just boilerplate. In Python an assertion is `assert pulse_cleared(500, 100, 500, 5) == True`, and the confirmation prints with `print`. In Rust the same check is `assert_eq!(pulse_cleared(500, 100, 500, 5), true);`, with `true` spelled in lowercase, and the confirmation prints with `println!`. The cases you check and the booleans you expect are identical in both.

## Paper Practice

Trace this program by hand, on paper. Build a table with one row per call to `safe_margin` and one row per `assert`: for each call, write the values held by its `reading` and `limit` parameters and the value it returns; for each `assert`, write whether the condition it checks is `True` or `False`. Write the exact line the program prints, and only that line.

```python title="trace_me.py"
def safe_margin(reading, limit):
    return reading <= limit

assert safe_margin(80.0, 100.0) == True
assert safe_margin(120.0, 100.0) == False
print("both checks passed")
```

<Reveal label="Reveal the completed trace">
The first call, `safe_margin(80.0, 100.0)`, binds `reading` to `80.0` and `limit` to `100.0`, evaluates `80.0 <= 100.0`, which is `True`, and returns `True`. The first `assert` checks `True == True`, which holds, so nothing visible happens and execution moves to the next line.

| Line | `reading` | `limit` | returns | assert condition |
|---|---|---|---|---|
| `assert safe_margin(80.0, 100.0) == True` | `80.0` | `100.0` | `True` | `True` |
| `assert safe_margin(120.0, 100.0) == False` | `120.0` | `100.0` | `False` | `True` |

The second call, `safe_margin(120.0, 100.0)`, binds `reading` to `120.0` and `limit` to `100.0`, evaluates `120.0 <= 100.0`, which is `False`, and returns `False`. The second `assert` checks `False == False`, which also holds. Both assertions passed silently, so the program reaches the final line and prints `both checks passed`, and nothing else.
</Reveal>

Photograph your trace and include it in your PDF on Canvas. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.
