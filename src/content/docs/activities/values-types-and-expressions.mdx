This activity puts into practice the [Values, Types, and Expressions](/lectures/values-types-and-expressions/) lecture. You will predict the value of a long mixed-operator expression before running it, compare how Python and Rust handle a division case where their rules may not agree, and decide why one of them refuses a line the other accepts. By the end, you will be able to reduce an expression by hand using precedence, modulo, and each language's division rule, and to say what a language checks before it runs your program and what it works out while running it.

## Reduce a Mixed Expression Step by Step

The lecture reduced `10 / 4 + 3 * 2`, an expression with two operators past the addition. This one has four, so you cannot eyeball the answer. You commit to an answer first, then run the program to check it.

Read the program below and write down, on paper or in a comment, the exact value you expect it to print in each language. Do not run it yet. Reduce the expression one operator at a time, and predict both values before opening the reveal.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="predict.py"
print(10 % 3 + 2 * 4 - 6 / 4)
```
</TabItem>
<TabItem label="Rust">
```rust title="predict.rs"
fn main() {
    println!("{}", 10 % 3 + 2 * 4 - 6 / 4);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the real outputs and reconcile them with your prediction">
```bash title="Run the Python program"
python3 predict.py
```

```text frame="terminal" title="Output"
7.5
```

```bash title="Compile and run the Rust program"
rustc predict.rs
./predict
```

```text frame="terminal" title="Output"
8
```

The two languages run the exact same steps in the exact same order, and only the single division `6 / 4` splits them. Precedence reduces `%`, `*`, and `/` before `+` and `-`, left to right, so `10 % 3` goes first, then `2 * 4`, then `6 / 4`; the leftover `+` and `-` reduce last, left to right.

In Python, `10 % 3` is `1` (the remainder of ten divided by three), `2 * 4` is `8`, and `6 / 4` is the exact float `1.5`, because Python's `/` always produces a float:

```text title="Reducing 10 % 3 + 2 * 4 - 6 / 4 in Python"
10 % 3 + 2 * 4 - 6 / 4
1 + 2 * 4 - 6 / 4        (10 % 3 is the remainder 1)
1 + 8 - 6 / 4            (2 * 4 is 8)
1 + 8 - 1.5             (6 / 4 is float division: 1.5)
9 - 1.5                 (1 + 8, leftmost of the equal-ranked + and -)
7.5                     (9 - 1.5)
```

In Rust, `10 % 3` is `1` and `2 * 4` is `8` just the same, but `6 / 4` divides two whole-number literals, so it is integer division and truncates `1.5` down to `1`:

```text title="Reducing 10 % 3 + 2 * 4 - 6 / 4 in Rust"
10 % 3 + 2 * 4 - 6 / 4
1 + 2 * 4 - 6 / 4        (10 % 3 is the remainder 1)
1 + 8 - 6 / 4            (2 * 4 is 8)
1 + 8 - 1               (6 / 4 is integer division: truncates 1.5 to 1)
9 - 1                   (1 + 8)
8                       (9 - 1)
```

If you predicted `8` for Python, you almost certainly truncated `6 / 4` to a whole number, which is the Rust rule, not Python's. If you predicted anything with the addition and subtraction reaching past `%`, `*`, or `/`, precedence was the slip: the three high-ranked operators always reduce before the `+` and the `-`, no matter where they sit in the line.
</Reveal>

## The Negative Case Where the Languages Split

For a positive numerator, Python's `//` and Rust's `/` agree: both make `7 / 2` into `3`, so the two rules look interchangeable. Whether they really are is what this section tests. You read both tabs and name what genuinely changes and what stays fixed.

Study the two programs below. Each divides `-7` by `2` as a whole-number division and then takes the modulo remainder. Before opening the reveal, write down the four values you expect, then name one thing that is truly different between the languages and one thing that is the same.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="divide.py"
print(-7 // 2)
print(-7 % 2)
```
</TabItem>
<TabItem label="Rust">
```rust title="divide.rs"
fn main() {
    println!("{}", -7 / 2);
    println!("{}", -7 % 2);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the outputs and what differs">
```bash title="Run the Python program"
python3 divide.py
```

```text frame="terminal" title="Output"
-4
1
```

```bash title="Compile and run the Rust program"
rustc divide.rs
./divide
```

```text frame="terminal" title="Output"
-3
-1
```

<WhatDiffers>
<Fragment slot="differs">
The exact answer of dividing `-7` by `2` is `-3.5`, sitting between `-4` and `-3`, and the two languages round it opposite ways. Python's `//` floors toward negative infinity, taking the largest whole number not exceeding `-3.5`, so `-7 // 2` steps down to `-4`. Rust's `/` truncates toward zero, dropping the `.5` and keeping the whole-number part, so `-7 / 2` is `-3`. The modulo remainder follows whichever division its language uses, because quotient times divisor plus remainder must recover `-7`: with Python's quotient `-4`, the remainder is `1` (since `-4 * 2 + 1` is `-7`), and with Rust's quotient `-3`, the remainder is `-1` (since `-3 * 2 + -1` is `-7`). What stays fixed is that both languages produce one value per line, both share the same precedence, and both use the same operand-and-operator machinery; only the direction of rounding on a negative result, and the sign of the remainder that tracks it, changes.
</Fragment>
</WhatDiffers>

Had the numerator been positive, all of this would have stayed hidden: `7 // 2` and `7 / 2` are both `3`, and `7 % 2` is `1` in both languages. The negative numerator is the one case that forces floor and truncate to disagree, and it is exactly the case that bites when a real formula happens to feed a negative value into a whole-number division.
</Reveal>

## Choose the Reason Rust Refuses

Python prints a value for `3 + 2.5`. Rust will not build the same line at all. Below is the question and four accounts of why; exactly one is right. Commit to one before you open the reveal.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="mix.py"
print(3 + 2.5)
```
</TabItem>
<TabItem label="Rust">
```rust title="mix.rs (will not compile)"
fn main() {
    println!("{}", 3 + 2.5); // error: cannot add a float to an integer (Rust will not compile this)
}
```
</TabItem>
</Tabs>

Which statement explains the difference?

- **(a)** Rust has no type that can hold `5.5`, so the sum has no value there.
- **(b)** Rust settles the type of every expression before the program runs, and `3` and `2.5` are different types, so it refuses; Python settles types as the line runs, and turns the `3` into a float on the spot.
- **(c)** The two languages disagree about the value: Python gives `5.5` and Rust would give `5`.
- **(d)** The languages agree about the value, and the Rust line fails only because `println!` needs a different placeholder for a decimal number.

<Reveal label="Reveal the answer and why each other option is wrong">

**(b) is correct.** The difference is *when* the types are settled, not what the numbers are worth. Rust works out the type of every expression at compile time, finds a whole-number type on the left of `+` and a float on the right, and refuses to build the program:

```text frame="terminal" title="rustc mix.rs"
error[E0277]: cannot add a float to an integer
 --> mix.rs:2:22
  |
2 |     println!("{}", 3 + 2.5);
  |                      ^ no implementation for `{integer} + {float}`
```

Python settles types while the line runs, and when it meets a whole number and a float in one `+`, it converts the whole number to a float first and adds two floats. That silent conversion is called implicit coercion, and it is why the same line is fine there:

```text frame="terminal" title="python3 mix.py"
5.5
```

**(a) is wrong.** Rust holds `5.5` perfectly well. Writing `3.0 + 2.5`, with both operands floats, compiles and prints `5.5`. Nothing about the value is the problem; the mismatch between the two operand types is.

**(c) is wrong.** Rust does not produce `5`, or any other number, because it never produces a program at all. There is no truncation happening here and no value to disagree about. Truncation is what whole-number division does, which is a different rule you met in the sections above.

**(d) is wrong.** The compiler names the trait `Add`, not the formatting: it is complaining about the addition, before printing is ever considered. `println!("{}", ...)` displays a float without any change.

</Reveal>

## Write a Seconds Splitter

A stopwatch has logged a run lasting `200` seconds total. Write a program that prints three lines: the whole number of minutes contained in `200` seconds, then the leftover seconds, then the exact decimal number of minutes those `200` seconds make.

<Reveal label="Reveal a sample solution">
More than one correct program can produce this result; the one below is a sample solution, not the only path to it.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="split.py"
print(200 // 60)
print(200 % 60)
print(200 / 60)
```
</TabItem>
<TabItem label="Rust">
```rust title="split.rs"
fn main() {
    println!("{}", 200 / 60);
    println!("{}", 200 % 60);
    println!("{}", 200.0 / 60.0);
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 split.py
```

```text frame="terminal" title="Output"
3
20
3.3333333333333335
```

```bash title="Compile and run the Rust program"
rustc split.rs
./split
```

```text frame="terminal" title="Output"
3
20
3.3333333333333335
```

`200 // 60` (Python) and `200 / 60` (Rust, on whole numbers) both give `3` whole minutes, and `200 % 60` leaves a remainder of `20` seconds in both, since the numerator is positive and the two rules agree there. The third line is where the languages part: Python's plain `/` already produces the exact float, while Rust's `/` would repeat the integer division, so both operands have to be written as floats, `200.0 / 60.0`, to get the same answer.
</Reveal>
