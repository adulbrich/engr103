Earth and the habitat are drifting into solar conjunction, the weeks each Martian year when the sun sits almost directly between the two and chews every radio packet into static and dropped bits. Mission Control still has to reach the crew, so flight software leans on three old tricks: a simple cipher shifts each letter of a message so a burst of noise cannot be mistaken for real words, a control character at the front of every packet says how that packet should be handled, and a checksum folds every character's code into one number so a corrupted packet can be caught before anyone acts on it. The comms dish itself is being re-aimed 34 degrees to hold the signal as long as possible, a detail for the antenna log and nothing your functions need. Your job as the flight-software crew member on shift is to write the small, one-character-at-a-time functions the cipher, the packet router, and the checksum are built from.

## How This Assignment Works

You write the functions named below and nothing else: the program's `main`, its input, its output, and the local test runner are already written, and the automated grader calls your functions directly with values it chooses, reading only what you `return`. Every function here takes and returns only a `char`, an `i32`, or a `bool`: none takes or returns a whole string or a whole list, because `main` handles the looping over a message and calls your functions once per character. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your functions to the grader from the course starter repository. The assignment has four parts: the problem set below, a paper trace, a two-sentence reflection, and an optional summit problem.

## Problem Set

### Problem 1: The Cipher Shift, and One of HAB's Drafts

**Context.** The outbound cipher shifts every letter of a message forward through its own alphabet by a fixed number of positions, wrapping past the end back around to the start, so the same amount of shift can later be undone. A packet can carry uppercase letters, lowercase letters, and noise that is not a letter at all, and the cipher must treat the three differently. HAB already drafted the forward shift.

**Requirements.**

1. `shift_char(c, n)` must return the character that lies `n` positions forward from `c`, in whichever alphabet `c` belongs to. A lowercase letter wraps within `a` through `z`; an uppercase letter wraps within `A` through `Z`, keeping its case; a character that is not a letter at all must be returned unchanged, since the cipher never touches noise or punctuation. Shifting `a` forward by `1` gives `b`; shifting `z` forward by `1` wraps around to `a`; shifting `Z` forward by `1` wraps around to `A`, not `a`.

The modeling step is splitting "shift this character" into the three cases the mission's packets can contain, lowercase, uppercase, and non-letter, and representing each letter case as its own cycle of 26 positions rather than a straight line that stops at its last letter; the analysis step is computing the wrapped position within the right case and turning it back into a character, or leaving a non-letter untouched.

### Problem 2: Reading the Reply

<Aside type="tip" title="Do not let the position go negative">
Subtracting `n` from `c`'s position relative to its own starting letter can land below `0` before you wrap it, and the [Expressions and Operators](/lectures/expressions-and-operators/) lecture already flagged that `%` treats a negative left side differently in Python and in Rust. Sidestep the whole question: add `26` to the subtracted position before taking `% 26`, so the value handed to the remainder operator never goes negative in either language.
</Aside>

<WhatDiffers>
<Fragment slot="differs">
If you subtract first and take the remainder second, without adding `26` back in, Python's `%` still returns a value from `0` to `25` because Python's remainder always keeps the sign of the divisor. Rust's `%` on a negative left-hand value returns zero or a negative number, since Rust's remainder keeps the sign of the dividend instead, so the same expression that quietly works in Python can hand Rust a negative position and a wrong character. Adding `26` before the `% 26` avoids the divergence entirely, in both languages.
</Fragment>
</WhatDiffers>

### Problem 3: Routing by the Header

**Context.** Every packet begins with a single control character that tells flight software what to do with the rest of it: transmit it, resend it, acknowledge it, or throw it away. Conjunction noise can flip a header into a character that means nothing at all, so the router must also have a way to say "this is not a command I recognize" instead of acting on garbage.

**Requirements.**

1. `header_action(c)` must read the packet's control character `c` and return the integer action code for it. The recognized commands and their codes are exactly these:
   - `'T'` (transmit the packet outbound) returns `0`.
   - `'R'` (resend the previous packet) returns `1`.
   - `'A'` (acknowledge receipt) returns `2`.
   - `'X'` (discard the packet) returns `3`.
   - Any other character at all, including a lowercase copy of a command letter such as `'t'`, is not a recognized command and must return `-1`, the code flight software uses to flag a header it cannot trust. The commands are uppercase, and the match is case-sensitive.

The modeling step is turning the four named commands into four distinct integer codes and reserving one more code, `-1`, for everything that is not a command; the analysis step is checking `c` against each command in turn and returning the matching code, or `-1` when none matches.

### Problem 4: Filtering the Static and Folding the Checksum

**Context.** A packet arrives one character at a time, and conjunction noise mixes real letters, upper or lowercase, with control codes, punctuation, digits, and spaces. Before flight software folds a character into the checksum, it has to know whether that character belongs to the message at all, then read the character's numeric code, then fold that code into a running total kept inside one byte's range, `0` through `255`, so a corrupted packet can be caught before anyone acts on it.

**Requirements.**

1. `is_message_char(c)` must return `True` (Rust `true`) when `c` is a letter, lowercase `a` through `z` or uppercase `A` through `Z`, and `False` (Rust `false`) for every other character, including a digit, punctuation, and a space.
2. `char_code(c)` must return the numeric code of `c` as a whole number.
3. `checksum_step(running, code)` must return the updated checksum after folding one more character's code in: the previous `running` value plus `code`, reduced modulo `256` so the result always stays from `0` through `255`.

The modeling step is defining "belongs to the message" as the union of the two letter ranges the cipher works over, and choosing to fold the packet down to one running number inside a byte instead of keeping every character's code around; the analysis step is a pair of range comparisons for the filter, and the addition and the modulo that keep the running number inside a byte.
