Every piece of flight software clears a qualification review before Mission Control trusts it in flight, and the review board does not take a function's word for it: it wants the test cases that prove the function does what its specification promises. On Sol 214 the crew holds the review slot for the maneuvering thruster's pulse-length safety check, the guard that keeps the flight computer from ever commanding a burn longer than the thruster is rated for. HAB has already run the check once, watched it return the answer it expected, and called it qualified, but a check that returns one right answer is not the same as a check that is qualified. Your job on the review board is to write the test suite that certifies the thruster check, and to judge HAB's claim for yourself.

## How This Assignment Works

You work **test first**, the way flight software is really qualified: you read the specification, design the cases that will prove the function meets it, plan your test functions, and only then write them. You write the test function and nothing else: the program's `main`, its input and output, the function under test, and the local test runner are already written. The problem is solvable in Python or Rust, whichever you prefer, and both are checked the same way. Because the [Testing](/lectures/testing/) lecture is behind you, you write real `assert`-based tests now, not a table of rows on the page. The automated grader runs your test function twice over: against a correct implementation of the function, where every assertion you wrote must hold, and against several broken implementations, where each broken one must fail at least one of your assertions. The order is fixed: design your cases, plan your test function, then write it. After that comes an optional summit stretch, a short paper trace, and a two-sentence reflection.

## What to Submit

You submit in two places. Mechanics are in [Running and Submitting Your Code](/practicalities/starter-repo-and-check/); each section below also repeats what it asks for.

- **Your code on Gradescope**: the test function `test_thruster_pulse_ok`, plus the extra-credit `test_pulse_in_range` if you attempt the summit.

## The Problem

Before a maneuvering thruster fires, the flight software checks that the commanded pulse length does not exceed the thruster's rated maximum, so the software can never command a burn longer than the hardware is built to survive. The thruster on the docket is rated to deliver `22` newtons of thrust, and its safety check is a single function the board must qualify: `thruster_pulse_ok`, which the flight computer calls before every firing. The board already has a correct implementation of this function on file, along with several implementations that quietly get one rule wrong. You do not write the function. You write the test that tells a qualified implementation from a broken one.

Here is the specification the board qualifies against:

1. `thruster_pulse_ok(pulse_ms, max_pulse_ms)` returns `true` when the commanded pulse length `pulse_ms` does not exceed the rated maximum `max_pulse_ms`, and `false` when it does exceed it. Both are whole numbers of milliseconds. You do not implement this function; the grader already has a correct version and several broken versions on file.
2. Write `test_thruster_pulse_ok`, a test function whose body is a sequence of assertions checking `thruster_pulse_ok` against that specification, ending with a printed confirmation line once every assertion has held. What cases you check, and how you order and label them, is entirely your decision.

The grader runs your test function against the correct `thruster_pulse_ok`, where every assertion must hold and your confirmation line must print, and against several broken versions, where each broken version must fail at least one of your assertions. A suite that passes the correct implementation but lets a broken one slip through has not qualified the check.

**Interface.** You are not implementing `thruster_pulse_ok`; this is the signature your test function calls against, alongside the test function you do write.

**Assumptions and edge cases.** `pulse_ms` and `max_pulse_ms` are always whole numbers, zero or greater. A commanded pulse of `0` is a legal command, and it never exceeds any rated maximum. The boundary is exact: a pulse exactly equal to the rated maximum does not exceed it, so the check passes for it. The thruster's rated thrust plays no part in the check.

## Step 1: Design Your Test Cases

Before writing any test code, decide what a qualified `thruster_pulse_ok` must do on every kind of input, and capture it as a table. Write a set of test cases as a plain table of rows: the two inputs, `pulse_ms` and `max_pulse_ms`, and the boolean you expect back. This table is your design; you turn each row into an assertion in Step 3.

Your table must include, and label, at least these cases:

- A typical command comfortably within the rated maximum, which passes.
- A typical command that clearly exceeds the rated maximum, which fails.
- The boundary case where the commanded pulse is exactly equal to the rated maximum.
- A command one millisecond over the rated maximum.
- The zero-pulse command.
- At least one more case whose expected boolean you work out fully by hand.

A weak suite passes a broken implementation without noticing; a strong suite has at least one case on which a correct implementation and a wrong one are forced to disagree. Think about what HAB claimed while you design these: a strong suite would catch an implementation that HAB's single passing case waves straight through.

**Submit your test table in your PDF on Canvas.**

## Step 3: Write Your Test Suite

Implement `test_thruster_pulse_ok` from your plan, in Python or Rust, following your own pseudocode. Each row in your table becomes an assertion: call `thruster_pulse_ok` with the inputs and assert that it equals the boolean you expect. End the function with a printed confirmation line, so a passing run says so out loud. Because the [Testing](/lectures/testing/) lecture is behind you, assertions are the right tool here, the same pattern that lecture's `test_coupon_discount` uses, not a table of rows.

The grader runs your test function against the correct `thruster_pulse_ok`, where every assertion must hold and your confirmation line must print, and against several broken implementations, where each one must fail at least one of your assertions. A suite that passes the correct implementation but lets any broken one through is not yet strong enough to qualify the check.

In Rust the same check is `assert_eq!(thruster_pulse_ok(500, 500), true);`, with `true` spelled in lowercase, and the confirmation prints with `println!`. ## Summit Problem (extra credit)

This one is a real stretch, and it earns extra credit. It is also your practice for the graded stretch problem in the recitation room, where a harder problem is waiting.

Some thrusters are qualified not against a single maximum but against a whole safe band: a pulse that is too short misfires, and a pulse that is too long overloads, so the check must confirm the command sits inside a range that is closed at both ends. The board qualifies `pulse_in_range(pulse_ms, min_pulse_ms, max_pulse_ms)`, which returns `true` when `pulse_ms` is at least `min_pulse_ms` and at most `max_pulse_ms`, both boundaries included, and `false` otherwise. You do not write this function; the grader has a correct version and several broken versions on file. Write `test_pulse_in_range`, a test function strong enough to hold against the correct version and fail at least one assertion against every broken one.

Because two boundaries now bound the safe band instead of one, a strong suite has to pin down each end on its own: an implementation that gets the low edge wrong and an implementation that gets the high edge wrong must each be caught by some assertion. Include, and label, at least a case inside the band, a case sitting exactly on each boundary, a case one millisecond below the low boundary, and a case one millisecond above the high boundary. A single case looks like this worked example: `assert pulse_in_range(200, 100, 500) == True`.

## Paper Practice

Trace this program by hand, on paper. Build a table with one row per call to `safe_margin` and one row per `assert`: for each call, write the values held by its `reading` and `limit` parameters and the value it returns; for each `assert`, write whether the condition it checks is `True` or `False`. Write the exact line the program prints, and only that line.

```python title="trace_me.py"
def safe_margin(reading, limit):
    return reading <= limit

assert safe_margin(80.0, 100.0) == True
assert safe_margin(120.0, 100.0) == False
print("both checks passed")
```

<Reveal label="Reveal the completed trace">
The first call, `safe_margin(80.0, 100.0)`, binds `reading` to `80.0` and `limit` to `100.0`, evaluates `80.0 <= 100.0`, which is `True`, and returns `True`. The first `assert` checks `True == True`, which holds, so nothing visible happens and execution moves to the next line.

| Line | `reading` | `limit` | returns | assert condition |
|---|---|---|---|---|
| `assert safe_margin(80.0, 100.0) == True` | `80.0` | `100.0` | `True` | `True` |
| `assert safe_margin(120.0, 100.0) == False` | `120.0` | `100.0` | `False` | `True` |

The second call, `safe_margin(120.0, 100.0)`, binds `reading` to `120.0` and `limit` to `100.0`, evaluates `120.0 <= 100.0`, which is `False`, and returns `False`. The second `assert` checks `False == False`, which also holds. Both assertions passed silently, so the program reaches the final line and prints `both checks passed`, and nothing else.
</Reveal>

Photograph your trace and include it in your PDF on Canvas. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.
