This activity puts into practice the [Loops](/lectures/loops/) lecture. You will predict the output of a nested loop that breaks partway and a `while` loop that both skips and stops early, trace a `while` loop where two variables change on every pass, and fix a counting loop that quietly drops its last value. By the end, you will be able to say which loop a `break` actually ends, follow two loop variables at once until a condition turns false, and spot a boundary that stops one value too soon.

## Warm-up

A quick refresher before the sections. A `while` loop runs its body while a condition stays true, and a `for` loop walks a variable through the values of a range. Here is the smallest example of each, back to back, in both languages.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="warmup.py"
count = 1
while count <= 3:
    print(count)
    count = count + 1
for i in range(3):
    print(i)
```
</TabItem>
<TabItem label="Rust">
```rust title="warmup.rs"
fn main() {
    let mut count = 1;
    while count <= 3 {
        println!("{}", count);
        count = count + 1;
    }
    for i in 0..3 {
        println!("{}", i);
    }
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 warmup.py
```

```text frame="terminal" title="Output"
1
2
3
0
1
2
```

Rust prints the same six lines. The `while` counts `1` to `3` and stops when `count` reaches `4`, and the `for` walks `range(3)` and `0..3`, which are the three values `0, 1, 2`. With those two shapes fresh, the sections below add a second loop, a second control statement, and a second variable, so the stopping point and the number of passes stop being obvious.

## Predict What Break and Continue Really Do

The two statements that reshape a loop are `break` and `continue`, and both are easy to misread: `break` looks like it ends everything, and a `continue` next to a counter looks like it might skip the counter too. You commit to an answer first, then run each program to check it. Read both programs below and write down, on paper or in a comment, every line each one prints, in order, including the final number the first program prints. Do not run them yet.

The first program is a nested loop. The outer loop steps `i` through `1, 2, 3`, and for each `i` the inner loop steps `j` through `1, 2, 3`, but the inner loop `break`s as soon as `j` reaches `i`. A counter records how many numbers actually print, and the last line prints that count. The question is not only what prints, but how many lines, and which loop the `break` stops.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="nested.py"
count = 0
for i in range(1, 4):
    for j in range(1, 4):
        if j == i:
            break
        print(i * 10 + j)
        count = count + 1
print(count)
```
</TabItem>
<TabItem label="Rust">
```rust title="nested.rs"
fn main() {
    let mut count = 0;
    for i in 1..4 {
        for j in 1..4 {
            if j == i {
                break;
            }
            println!("{}", i * 10 + j);
            count = count + 1;
        }
    }
    println!("{}", count);
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the output and which loop the break ended">
```bash title="Run the Python program"
python3 nested.py
```

```text frame="terminal" title="Output"
21
31
32
3
```

Rust prints the same four lines. The whole result turns on one fact: `break` ends only the loop it sits in, which here is the inner loop, not the outer one. Trace the outer passes. When `i` is `1`, the inner loop starts with `j` at `1`, the check `j == i` is `1 == 1`, true at once, so `break` runs before anything prints and the inner loop ends having printed nothing. The outer loop is untouched, so it moves on. When `i` is `2`, `j` starts at `1`: `1 == 2` is false, so `21` prints and `count` becomes `1`; then `j` is `2` and `2 == 2` breaks, ending only the inner loop again. When `i` is `3`, `j` runs `1` then `2` before `3 == 3` breaks, so `31` and `32` print and `count` reaches `3`. The outer loop then finishes on its own and `print(count)` shows `3`. If you predicted the whole thing stopped the first time `break` ran, you read `break` as leaving both loops; it leaves just the inner one, and the outer loop kept handing it fresh work.
</Reveal>

The second program is a single `while` loop that uses both `continue` and `break` in one body. The counter `n` is bumped up first, then a `continue` skips the even values and a `break` stops the loop at a particular value. Write down what it prints before opening the reveal, and watch the order of the three checks.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="filter.py"
n = 0
while n < 10:
    n = n + 1
    if n % 2 == 0:
        continue
    if n == 7:
        break
    print(n)
```
</TabItem>
<TabItem label="Rust">
```rust title="filter.rs"
fn main() {
    let mut n = 0;
    while n < 10 {
        n = n + 1;
        if n % 2 == 0 {
            continue;
        }
        if n == 7 {
            break;
        }
        println!("{}", n);
    }
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the real output and reconcile it with your prediction">
```bash title="Run the Python program"
python3 filter.py
```

```text frame="terminal" title="Output"
1
3
5
```

Rust prints the same three lines. The counter is raised at the top of every pass, so `continue` skips the rest of the body but never the update, which is what keeps the loop from running forever. Pass by pass: `n` becomes `1`, which is odd and not `7`, so `1` prints. `n` becomes `2`, even, so `continue` jumps back to the condition with nothing printed. `n` becomes `3` and prints; `n` becomes `4` and is skipped; `n` becomes `5` and prints; `n` becomes `6` and is skipped. Then `n` becomes `7`: it is odd, so `continue` does not fire, but `n == 7` is now true, so `break` ends the whole loop before `7` can print. The condition `n < 10` would have allowed three more passes, but `break` overrode it. The output is the odd numbers below `7`. If you included `7`, you missed that `break` runs before the `print` on that pass; if you included the evens, you missed that `continue` skips the `print` for them.
</Reveal>

## Trace a Loop Where Two Variables Move

An exam asks you to say what a loop prints without running it, and the only reliable way is to trace it: track every variable and re-check the condition at the top of each pass, exactly as the machine does. The loop below is harder than a single counter, because it carries two variables that change differently on every pass: `a` grows by three, and `b` doubles. The condition compares them, so where the loop stops depends on which value overtakes the other, and that is not obvious by eye. You will build the trace by hand.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="race.py"
a = 3
b = 1
while a > b:
    print(a - b)
    a = a + 3
    b = b * 2
```
</TabItem>
<TabItem label="Rust">
```rust title="race.rs"
fn main() {
    let mut a = 3;
    let mut b = 1;
    while a > b {
        println!("{}", a - b);
        a = a + 3;
        b = b * 2;
    }
}
```
</TabItem>
</Tabs>

Do not run it yet. Trace it on paper with these steps.

<Steps>

1. Write the starting values `a = 3` and `b = 1` at the top.

2. For each pass, write the condition `a > b` with the current values filled in, and mark it true or false.

3. If it is true, write down the value that `print` outputs, which is `a - b`, then compute the new `a` from `a = a + 3` and the new `b` from `b = b * 2`, and carry both to the next pass.

4. Stop the first time the condition is false. The output is every value you wrote in step 3, in order.

</Steps>

<Reveal label="Reveal the completed trace">
| Pass | `a` | `b` | `a > b` | Prints `a - b` | new `a` | new `b` |
|---|---|---|---|---|---|---|
| 1 | 3 | 1 | `3 > 1` is true | `2` | 6 | 2 |
| 2 | 6 | 2 | `6 > 2` is true | `4` | 9 | 4 |
| 3 | 9 | 4 | `9 > 4` is true | `5` | 12 | 8 |
| 4 | 12 | 8 | `12 > 8` is true | `4` | 15 | 16 |
| 5 | 15 | 16 | `15 > 16` is false | nothing, loop ends | | |

The loop prints `2`, `4`, `5`, `4` and stops. Notice the printed values are not increasing: they climb to `5`, then fall back to `4`, because `b` doubles faster than `a` grows and the gap between them first widens and then closes. The fifth check is the one that ends it: by then `b` has reached `16` while `a` is only `15`, so `15 > 16` is false, the body does not run again, and the `16` and `15` never turn into a printed line. Run both programs to confirm.

```bash title="Run the Python program"
python3 race.py
```

```text frame="terminal" title="Output"
2
4
5
4
```

```bash title="Compile and run the Rust program"
rustc race.rs
./race
```

```text frame="terminal" title="Output"
2
4
5
4
```

The loop ran exactly four times, not a number you could guess from the starting values alone. Because `b` doubles, it catches and passes `a` faster than the steady `+3` on `a` suggests, and the only way to know the pass where that happens is to carry both variables down the table. Tracking just one of the two would have left you unable to say when the condition flips.
</Reveal>

## Fix the Loop That Stops One Short

This loop is meant to print every even number from `2` through `10`, so its intended output is the five lines `2`, `4`, `6`, `8`, `10`. It compiles and runs with no error, but the output is wrong: it is missing a value. There is no crash and no message to read, so you diagnose it the systematic way, by comparing what the loop produces against what it was meant to produce and reasoning about the boundary.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="evens.py"
n = 2
while n < 10:
    print(n)
    n = n + 2
```
</TabItem>
<TabItem label="Rust">
```rust title="evens.rs"
fn main() {
    let mut n = 2;
    while n < 10 {
        println!("{}", n);
        n = n + 2;
    }
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the diagnosis and the fix">
```bash title="Run the Python program"
python3 evens.py
```

```text frame="terminal" title="Output"
2
4
6
8
```

Rust prints the same four lines. The program was supposed to print through `10`, but `10` is missing.

**Symptom.** The loop prints `2`, `4`, `6`, `8` and stops. That is four lines, one short of the five expected, and the missing value is exactly the last one, `10`.

**Hypothesis.** The counter steps `2, 4, 6, 8, 10`, and the loop prints `n` then checks `n < 10` again at the top of the next pass. After printing `8`, the body sets `n` to `10` and control returns to the condition. The check is `10 < 10`, which is false, so the loop ends before `10` is ever printed. The condition uses a strict `<`, which stops the loop as soon as `n` equals the boundary, one value too soon. To include `10`, the condition has to stay true when `n` is `10`, so it needs `<=` instead of `<`.

**Test.** Change the strict `<` to `<=` so the boundary value itself passes the check:

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="evens.py (fixed)"
n = 2
while n <= 10:
    print(n)
    n = n + 2
```
</TabItem>
<TabItem label="Rust">
```rust title="evens.rs (fixed)"
fn main() {
    let mut n = 2;
    while n <= 10 {
        println!("{}", n);
        n = n + 2;
    }
}
```
</TabItem>
</Tabs>

```bash title="Run the fixed Python program"
python3 evens.py
```

```text frame="terminal" title="Output"
2
4
6
8
10
```

Rust prints the same five lines. The single character `<` to `<=` is the whole fix. This is the boundary version of the half-open idea from the ranges you saw earlier: a condition written with `<` stops just before its limit, so when the limit is a value you actually want, `<` drops it and `<=` keeps it. The bug never crashes, which is what makes it dangerous. The loop looks right, runs cleanly, and simply produces a result that is quietly one value short, and the only way to catch it is to know exactly which values the loop was supposed to cover. This one reads the same in both languages: the mistake and the fix are identical in Python and Rust, because the boundary is in the condition, not in anything the two languages spell differently.
</Reveal>

## Bridge

These three reps feed the recitation family where a loop drives a piece of changing state to a boundary and stops there: a counter walked to a limit, or a condition re-checked at the top of each pass until it turns false, sometimes with one loop nested inside another so the inner sweep runs in full for every step of the outer, and sometimes with more than one value changing together as the loop advances. The by-hand tracing, the where-does-it-stop prediction, and the off-by-one hunt you practiced here are the guided first rung of that ladder.
