Sol 100 has arrived: the habitat's hundredth full day on the Martian surface, and Mission Control wants a complete status report, not just another routine readout. All day, the environmental system has been checking the cabin's internal air pressure and handing each reading to flight software as it comes in. Mission Control also logged that the habitat's solar arrays produced 4 percent more power than yesterday's report, a bright note for the log but not a number any of your functions need. Before the report can go out, the software has to check each reading against the safe range and record only the good ones into a running manifest, work out the sol's average pressure, decide whether that average is calm, cautious, or critical, and finally archive the manifest for the permanent mission log. HAB has already drafted the piece that archives the sol's manifest before Sol 101 begins adding to it; do not trust it until you have checked it yourself.

## How This Assignment Works

You write the functions named below and nothing else: the program's `main`, its input, its output, and the local test runner are already written, and the automated grader calls your functions directly with values it chooses. For a function that computes and returns a value, the grader reads what you `return`. For a function that takes the manifest by `&mut` (a mutable reference), there is nothing meaningful to return, so the grader instead calls your function and then looks at the caller's own list afterward, exactly the way the [Sharing and Mutation](/lectures/sharing-and-mutation/) lecture showed a function change a list its caller kept. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your functions to the grader from the course starter repository. The assignment has five parts: the problem set below, a paper trace, a one-page accessibility and equity critique, a two-sentence reflection, and an optional summit problem.

### Problem 2: Recording Only the Good Readings

**Context.** Every reading the environmental system hands over is checked before it is kept. A reading that passes the safe-range test joins one running list for the sol, the manifest; a reading that fails is discarded and the manifest is left exactly as it was. The manifest has to grow in place as good readings arrive, so the rest of the day's report always sees the full, current list, not a copy that stopped updating the moment it was made.

**Requirements.**

1. `record_reading(manifest, reading, low, high)` must append `reading` to the end of `manifest` when `reading` is within the safe range (greater than or equal to `low` and less than or equal to `high`), and must leave `manifest` completely unchanged when `reading` is outside that range. It does not return a value; the caller's `manifest` is what changes, and the grader inspects `manifest` after the call.

The modeling step is choosing one shared list that only valid readings join, passed by mutable reference so every part of the day's report reads from that one growing list; the analysis step is the safe-range check from Problem 1 followed by the conditional in-place append, so the manifest grows only when the reading belongs there.

<Aside type="tip" title="Say it with &mut, in the signature and at the call">
The [Sharing and Mutation](/lectures/sharing-and-mutation/) lecture spelled out the three places Rust needs `&mut` to agree: the owner declared `let mut`, the parameter typed `&mut Vec<i32>`, and the call site written `&mut manifest`. Python needs none of this, because a list is already shared the moment you pass it; a `.append` inside `record_reading` changes the caller's list whether you meant it to or not. Either way, the append here is conditional: nothing is added when the reading is out of range, so the case where `manifest` comes back unchanged is a real case the grader checks.
</Aside>

## Paper Practice

Trace this program by hand, on paper. Build a variable table with one row per call to `record_reading`, tracking what `manifest` holds after each line, and then the value bound to `average`. One of the three readings is out of the safe range and must not be recorded; deciding which is part of the trace. Write the exact value the program prints for `manifest` and for `average`. Photograph your table and trace and attach it. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.

```python title="trace_me.py"
def record_reading(manifest, reading, low, high):
    if reading >= low and reading <= high:
        manifest.append(reading)

def summarize_manifest(manifest):
    total = 0
    for r in manifest:
        total = total + r
    return total / len(manifest)

manifest = [100]
record_reading(manifest, 96, 95, 105)
record_reading(manifest, 110, 95, 105)
record_reading(manifest, 104, 95, 105)
average = summarize_manifest(manifest)
print(manifest)
print(average)
```

<Reveal label="Reveal the completed trace">
Each call to `record_reading` reaches into the one shared `manifest` object, but appends only when the reading passes the safe-range check; there is no return value to track, only the object itself changing, and only when the reading belongs.

| Line | Reading | In range `95` to `105`? | `manifest` after |
|---|---|---|---|
| `record_reading(manifest, 96, 95, 105)` | `96` | yes | `[100, 96]` |
| `record_reading(manifest, 110, 95, 105)` | `110` | no, discarded | `[100, 96]` |
| `record_reading(manifest, 104, 95, 105)` | `104` | yes | `[100, 96, 104]` |

The reading `110` is above `105`, so it is not recorded and the manifest is unchanged for that line. `summarize_manifest` then sums `100 + 96 + 104 = 300` and divides by the manifest's length, `3`, giving `average = 100.0`. The program prints `[100, 96, 104]`, then `100.0`. The same program written in Rust prints `[100, 96, 104]`, then `100`, the `f64` display without Python's trailing `.0`.

## Accessibility and Equity Critique

This part is not code. Write about one page (roughly 300 to 500 words) critiquing the accessibility and equity limitations of a real computational tool you actually use or have encountered, something people rely on today: a phone app, a website, a piece of assistive technology, a search engine, a hiring or screening algorithm, a fitness tracker, a voice assistant, a mapping app, a school or workplace platform. Pick a real, specific tool, not a hypothetical one and not anything from the Mission Ares story.

Your one page must address all three of these:

1. **Who is the tool built around.** Describe the "default" user the tool seems to assume: their abilities, their language, their income, their hardware, their situation. Be specific about what leads you to that description, drawn from how the tool actually behaves.
2. **Who it leaves out, and how.** Name one concrete accessibility or equity limitation: a group of people the tool underserves, excludes, or actively harms, and the specific mechanism, a design choice, an assumption baked into the software, a cost, a requirement, that produces that limitation. Vague statements like "it could be more inclusive" are not enough; name the mechanism.
3. **What closing the gap would take.** Describe one real change that would narrow the limitation you named, and name the trade-off it carries, more engineering effort, added cost, a slower feature, a different design entirely. A fix with no trade-off at all is a sign you have not looked closely enough.

This critique is graded on completion, evaluated on whether it genuinely engages with all three points about a real tool, not on whether the instructor agrees with your conclusions. It is not shared with anyone but the instructor.
