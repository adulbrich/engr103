Sol 100 has arrived: the habitat's hundredth full day on the Martian surface, and Mission Control wants a complete status report, not just another routine readout. All day, the environmental system has been checking the cabin's internal air pressure and handing each reading to flight software as it comes in. Mission Control also logged that the habitat's solar arrays produced 4 percent more power than yesterday's report, a bright note for the log but not a number any of your functions need. Before the report can go out, the software has to check every reading against the safe range, keep a running manifest of the sol's readings so far, work out the sol's average pressure, and decide whether that average is calm, cautious, or critical enough to raise an alarm. HAB has already drafted the piece that archives the sol's manifest for the permanent mission log before Sol 101 begins adding to it; do not trust it until you have checked it yourself.

## How This Assignment Works

You write the functions named below and nothing else: the program's `main`, its input, its output, and the local test runner are already written, and the automated grader calls your functions directly with values it chooses. For a function that only computes and returns a value, the grader reads what you `return`. For a function that takes the manifest by `&mut` (a mutable reference), there is nothing meaningful to return, so the grader instead calls your function and then looks at the caller's own list afterward, exactly the way the [Sharing and Mutation](/lectures/sharing-and-mutation/) lecture showed a function change a list its caller kept. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your functions to the grader from the course starter repository. The assignment has five parts: the problem set below, a paper trace, a one-page accessibility and equity critique, a two-sentence reflection, and an optional summit problem.

```text frame="terminal" title="rustc output"
error[E0507]: cannot move out of `*manifest` which is behind a shared reference
 --> archive.rs:2:12
  |
2 |     return *manifest;
  |            ^^^^^^^^^ move occurs because `*manifest` has type `Vec<i32>`, which does not implement the `Copy` trait
```

Work out why before you open the hint, then write the correct version yourself.

<Reveal label="Reveal a nudge on HAB's mistake">
HAB's Python line `return manifest` does not build a second list; it hands back the very same object `manifest` already refers to, the aliasing from the [Memory Model](/lectures/the-memory-model/) lecture. Recording a new reading afterward changes that one shared object in place, so the "archive" HAB returned changes right along with the live manifest, because there is only ever one list, wearing two names. Rust's version fails even earlier: `*manifest` tries to move the whole vector out from behind a shared reference, which Rust forbids outright because a `Vec` is not a small `Copy` value, exactly the rule the [Memory Model](/lectures/the-memory-model/) lecture built around `.clone()`. The fix in both languages is the same idea: build a genuine, independent copy, `list(manifest)` in Python or `manifest.clone()` in Rust, so the archive and the live manifest are two separate objects instead of one aliased pair.
</Reveal>
</Aside>

## Paper Practice

Trace this program by hand, on paper. Build a variable table with one row per call, tracking what `manifest` holds after each line, and the values bound to `average`.
```python title="trace_me.py"
def record_reading(manifest, reading):
    manifest.append(reading)

def summarize_manifest(manifest):
    total = 0
    for r in manifest:
        total = total + r
    return total / len(manifest)

manifest = [100]
record_reading(manifest, 96)
record_reading(manifest, 104)
average = summarize_manifest(manifest)
print(manifest)
print(average)
```

<Reveal label="Reveal the completed trace">
Each call to `record_reading` reaches into the one shared `manifest` object and appends to it in place; there is no return value to track, only the object itself changing.

| Line | Call | `manifest` after |
|---|---|---|
| `record_reading(manifest, 96)` | appends `96` | `[100, 96]` |
| `record_reading(manifest, 104)` | appends `104` | `[100, 96, 104]` |

`summarize_manifest` then sums `100 + 96 + 104 = 300` and divides by the manifest's length, `3`, giving `average = 100.0`. The program prints `[100, 96, 104]`, then `100.0`. The same program written in Rust prints `[100, 96, 104]`, then `100`, the `f64` display without Python's trailing `.0`.

## Accessibility and Equity Critique

This part is not code. Write about one page (roughly 300 to 500 words) critiquing the accessibility and equity limitations of a real computational tool you actually use or have encountered, something people rely on today: a phone app, a website, a piece of assistive technology, a search engine, a hiring or screening algorithm, a fitness tracker, a voice assistant, a mapping app, a school or workplace platform. Pick a real, specific tool, not a hypothetical one and not anything from the Mission Ares story.

Your one page must address all three of these:

1. **Who is the tool built around.** Describe the "default" user the tool seems to assume: their abilities, their language, their income, their hardware, their situation. Be specific about what leads you to that description, drawn from how the tool actually behaves.
2. **Who it leaves out, and how.** Name one concrete accessibility or equity limitation: a group of people the tool underserves, excludes, or actively harms, and the specific mechanism, a design choice, an assumption baked into the software, a cost, a requirement, that produces that limitation. Vague statements like "it could be more inclusive" are not enough; name the mechanism.
3. **What closing the gap would take.** Describe one real change that would narrow the limitation you named, and name the trade-off it carries, more engineering effort, added cost, a slower feature, a different design entirely. A fix with no trade-off at all is a sign you have not looked closely enough.

This critique is graded on completion, evaluated on whether it genuinely engages with all three points about a real tool, not on whether the instructor agrees with your conclusions. It is not shared with anyone but the instructor.
