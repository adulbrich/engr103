Earth and the habitat are drifting into solar conjunction, the weeks each Martian year when the sun sits almost directly between the two and chews every radio packet into static and dropped bits. Mission Control still has to reach the crew, so flight software leans on an old trick: a simple cipher shifts each letter of a message forward through the alphabet before it is sent and shifts it back on the other end, so a burst of noise cannot be mistaken for real words and a clean packet still decodes to exactly what was sent. The comms dish itself is being re-aimed 34 degrees to hold the signal as long as possible, a detail for the antenna log and nothing your functions need. Your job as the flight-software crew member on shift is to write the two one-character-at-a-time functions the cipher is built from: the one that encodes a character and the one that decodes it.

## How This Assignment Works

You work **test first**, the way flight software is really written: you read the problem, decide what correct behavior looks like by writing your own test cases, plan the code in pseudocode, and only then write the code. ## The Problem

The outbound cipher shifts every letter of a message forward through its own alphabet by a fixed number of positions, and the inbound decoder shifts each letter back by the same number, so a message that is encoded and then decoded comes out exactly as it started. The shift wraps: counting forward past the end of the alphabet continues from the start again, and counting backward past the start continues from the end. A lowercase letter always stays lowercase, an uppercase letter always stays uppercase, and a packet also carries noise that is not a letter at all, a digit, a space, or punctuation, which the cipher must leave completely untouched.

You will write two functions, one that encodes a single character and one that decodes it. What each must return:

1. `shift_char(c, n)` must return the character that lies `n` positions **forward** from `c`, staying inside `c`'s own alphabet and wrapping past the end back to the start. A lowercase letter shifts within `a` through `z`; an uppercase letter shifts within `A` through `Z` and keeps its case; a character that is not a letter must come back exactly as it was. Shifting past `z` wraps around to `a`, and shifting past `Z` wraps around to `A`, never to `a`.
2. `unshift_char(c, n)` must return the character that lies `n` positions **backward** from `c`, staying inside `c`'s own alphabet and wrapping past the start back to the end, so that decoding undoes encoding: `unshift_char(shift_char(c, n), n)` is `c` for any character `c`, letter or not, and any shift `n`. A lowercase letter wraps past `a` back to `z`; an uppercase letter wraps past `A` back to `Z`; a character that is not a letter comes back unchanged.

Each function returns a single `char`. How you turn a character into the shifted one, and what intermediate values you give names to along the way, is entirely your decision.

We give you **one** worked example to show the format. Encoding `a` with a shift of `1` moves it forward one letter to `b`, and decoding that `b` with the same shift of `1` moves it back to `a`:

| Call | Returns |
|---|---|
| `shift_char('a', 1)` | `'b'` |

**Assumptions and edge cases.** `c` can be a lowercase letter, an uppercase letter, or any other single character: a digit, punctuation, or a space. `n` is a whole number from `0` through `25`. A shift of `0` must return `c` unchanged. The cipher must wrap correctly in each letter case, both the lowercase wrap past `z` and the uppercase wrap past `Z`, and it must leave a non-letter exactly as it was no matter how large the shift.

<Fragment slot="differs">
Decoding shifts a character backward, and moving backward can drive the working position you compute below zero before you wrap it. The two languages disagree on the remainder operator here: Python's `%` always returns a result with the sign of the divisor, so a negative left-hand value still comes back in `0` through `25`, while Rust's `%` keeps the sign of the dividend, so the same expression can hand Rust a negative number and a wrong character. Because the languages genuinely differ, decide for yourself how your function keeps the backward position in range, in each language you use, rather than assuming one language's behavior carries to the other.

## Paper Practice

Trace this program by hand, on paper. It folds a run of character codes into a single running total that never leaves one byte's range, `0` through `255`, using the remainder operator from the [Expressions and Operators](/lectures/expressions-and-operators/) lecture, the same wrap-with-a-remainder idea your cipher uses in a different place. Build a variable table with a row for each call to `fold_code`, tracking the value of `running` before and after the call. Write the exact value the program prints.

```python title="trace_me.py"
def fold_code(running, code):
    return (running + code) % 256

running = 0
c1 = 97
c2 = 98
c3 = 250
running = fold_code(running, c1)
running = fold_code(running, c2)
running = fold_code(running, c3)
print(running)
```

<Reveal label="Reveal the completed trace">
Each call adds one more character's code into `running` and wraps the result back into `0` through `255`.

| Call | `running` before | `code` | `running` after |
|---|---|---|---|
| `fold_code(running, c1)` | `0` | `97` | `97` |
| `fold_code(running, c2)` | `97` | `98` | `195` |
| `fold_code(running, c3)` | `195` | `250` | `189` |

The third call adds `195 + 250 = 445`, and `445 % 256` is `189`, the wraparound taking effect for the first time. The program prints `189`. The same program written in Rust prints the same whole number, `189`, with no display difference here since every value is a whole `i32`, never a float.
</Reveal>

Photograph your trace and include it in your PDF on Canvas. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.
