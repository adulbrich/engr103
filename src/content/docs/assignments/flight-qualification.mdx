Every piece of flight software has to clear a qualification review before Mission Control trusts it in flight, and the review board does not take a function's word for it: it wants the test cases that prove the function does what its specification promises. Three systems are on the docket for Sol 214, the one slot the crew has before the board moves on to the next system: the coolant loop's status code, the cabin heater's duty cycle, and the thruster's pulse-length safety check. HAB has already drafted the thruster check and a test to go with it, but a test only qualifies a function if it is strong enough to catch a real mistake, and this one is not. Write the test suites that qualify all three systems, and where HAB's draft falls short, write the correct function yourself.

## How This Assignment Works

You write the test functions and, for one problem, the function itself; the program's `main`, its input and output, and the local test runner are already written, and the automated grader calls what you submit directly, reading only what your functions `return` and which assertions your test functions raise. Solve each problem in Python or Rust, whichever you prefer, and you may switch languages between problems; both are checked against the same acceptance cases. Submit your work to the grader from the course starter repository, as described in [Running and Submitting Your Code](/practicalities/starter-repo-and-check/). The assignment has four parts: the problem set below, a paper trace, a two-sentence reflection, and an optional summit problem.

## Problem Set

### Problem 1: Qualifying the Coolant Status Code

**Context.** The coolant loop reports its health as a status code, built from the temperature difference between its supply and return lines. The board already has a correct implementation of this function on file, and several implementations that quietly get one rule wrong; your test function is what tells them apart.

**Requirements.**

1. `coolant_status_code(delta_c)` takes the coolant loop's supply-to-return temperature difference, in degrees Celsius, and must return an integer status code from this specification: `-1` if `delta_c` is negative, since a working sensor never reports a negative difference and a negative reading means a wiring fault, not a temperature; `0` if `delta_c` is `0.0` up to but not including `5.0` (nominal cooling); `1` if `delta_c` is `5.0` up to and including `12.0` (elevated; watch it); `2` if `delta_c` is above `12.0` (overheating; alarm). You do not write this function. The grader already has a correct version and several broken versions on file.
2. Write a test function, `test_coolant_status_code()`, whose body is a sequence of `assert`/`assert_eq!` calls checking `coolant_status_code` against the specification above, ending with a printed confirmation line once every assertion has held. A single case looks like this worked example: `assert coolant_status_code(2.0) == 0`.
3. Your test function must include, and its structure should make clear which is which, at least these seven labeled cases: one typical value from each of the three bands (`0`, `1`, and `2`), the boundary where the sensor-fault case ends and the nominal band begins (`0.0`), the boundary where the nominal band ends and the elevated band begins (`5.0`), the boundary where the elevated band ends and the overheat band begins (`12.0`), and a negative reading that exercises the sensor-fault case. The grader runs your test function against the correct `coolant_status_code` (every assertion must hold) and against several broken versions (each broken version must fail at least one of your assertions).

The modeling step is turning the four-rule specification into the exact set of inputs that pins each rule down, especially the two closed-on-top boundaries; the analysis step is predicting each expected code by hand and expressing that prediction as an `assert` rather than a table row, exactly as the [Testing](/lectures/testing/) lecture's `test_coupon_discount` does.

**Interface.** You are not implementing `coolant_status_code`; this is the signature your test function calls against.

### Problem 2: Qualifying the Heater Duty Cycle

**Context.** The cabin heater reports what fraction of its on-off cycle it spent actually heating, as a percentage. A cycle length of zero seconds is meaningless as a fraction, so the specification defines a signal value for it rather than leaving a division by zero to happen by accident.

**Requirements.**

1. `duty_cycle_percent(on_seconds, cycle_seconds)` must return `-1.0` when `cycle_seconds` is `0.0`, since a zero-length cycle makes the percentage undefined and the function must say so rather than divide by zero. Otherwise, it must return the percentage of the cycle the heater was on: `on_seconds` divided by `cycle_seconds`, multiplied by `100.0`. You do not write this function; the grader already has a correct version and several broken versions on file.
2. Write a test function, `test_duty_cycle_percent()`, checking `duty_cycle_percent` against the specification above. Because this function returns a float, compare with a tolerance rather than `==`, the same pattern the [Testing](/lectures/testing/) lecture used for `average`: check that the absolute difference between the returned value and the expected value is smaller than `1e-9`. A single case looks like this worked example: `assert abs(duty_cycle_percent(30.0, 120.0) - 25.0) < 1e-9`.
3. Your test function must include, and its structure should make clear which is which, at least these four labeled cases: a typical value strictly between the two bands, the boundary where the heater is never on during the cycle (`on_seconds` of `0.0`), the boundary where the heater is on for the entire cycle, and the zero-length-cycle case that must return `-1.0`. The grader runs your test function against the correct `duty_cycle_percent` (every assertion must hold) and against several broken versions (each broken version must fail at least one of your assertions).

The modeling step is recognizing that "on the whole time" and "off the whole time" are boundaries of the ordinary formula, while a zero-length cycle is a case the formula cannot even evaluate; the analysis step is predicting each expected percentage by hand and writing the tolerance check correctly.

**Interface.** You are not implementing `duty_cycle_percent`; this is the signature your test function calls against.

<Aside type="caution" title="Compare floats with a tolerance, not ==">

### Problem 3: The Thruster Pulse Check, and HAB's Test That Should Have Caught It

**Context.** Before a maneuvering thruster fires, flight software checks that the commanded pulse length does not exceed the thruster's rated maximum. HAB drafted this check and wrote a test to qualify it. The test passed, so HAB signed the function off. It should not have.

**Requirements.**

1. `thruster_pulse_ok(pulse_ms, max_pulse_ms)` must return `true` when `pulse_ms` is less than or equal to `max_pulse_ms`, including a pulse exactly as long as the rated maximum, and `false` when `pulse_ms` exceeds `max_pulse_ms`. Write this function yourself; do not submit HAB's draft below.
2. Write a test function, `test_thruster_pulse_ok()`, that qualifies your corrected function against the specification above and would fail HAB's draft. It must include, at minimum: a typical safe pulse well under the maximum, a typical unsafe pulse well over the maximum, and a pulse exactly equal to the maximum. End the test function with a printed confirmation line once every assertion has held.

The modeling step is reading "does not exceed" as `<=`, not `<`, so that a pulse exactly at the rated maximum still counts as safe; the analysis step is writing the corrected function, and then writing the one test case, the exact-maximum pulse, that HAB's weaker test skipped and that would have caught HAB's mistake before it ever reached a review board.

HAB's test really does pass against HAB's function, and HAB's function really is wrong: for a pulse of exactly `500` against a maximum of `500`, HAB's draft returns `false`, when the specification says a pulse exactly at the maximum is still safe and must return `true`. Work out why HAB's test never noticed before you open the hint.

<Reveal label="Reveal a nudge on HAB's mistake">
HAB's function compares with `pulse_ms < max_pulse_ms`, a strict less-than, so a pulse exactly equal to the maximum fails that comparison and the function returns `false` when it should return `true`. HAB's test never tries `pulse_ms` equal to `max_pulse_ms`; it only checks a pulse well under the limit and a pulse well over it, and both of those give the same answer whether the comparison is `<` or `<=`. A test that never visits the boundary a rule turns on cannot tell a correct comparison from an off-by-one one, no matter how many times it passes.
</Reveal>

## Paper Practice

Trace this program by hand, on paper. Build a table with one row per call to `safe_margin` and one row per `assert`: for each call, write the values held by its `reading` and `limit` parameters and the value it returns; for each `assert`, write whether the condition it checks is `True` or `False`. Write the exact line the program prints, and only that line. Photograph your table and trace and attach it. This part is graded on completion (the attached photograph), not on whether every cell is right, so attempt it by hand first, then open the reveal to check yourself.

```python title="trace_me.py"
def safe_margin(reading, limit):
    return reading <= limit

assert safe_margin(80.0, 100.0) == True
assert safe_margin(120.0, 100.0) == False
print("both checks passed")
```

<Reveal label="Reveal the completed trace">
The first call, `safe_margin(80.0, 100.0)`, binds `reading` to `80.0` and `limit` to `100.0`, evaluates `80.0 <= 100.0`, which is `True`, and returns `True`. The first `assert` checks `True == True`, which holds, so nothing visible happens and execution moves to the next line.

| Line | `reading` | `limit` | returns | assert condition |
|---|---|---|---|---|
| `assert safe_margin(80.0, 100.0) == True` | `80.0` | `100.0` | `True` | `True` |
| `assert safe_margin(120.0, 100.0) == False` | `120.0` | `100.0` | `False` | `True` |

The second call, `safe_margin(120.0, 100.0)`, binds `reading` to `120.0` and `limit` to `100.0`, evaluates `120.0 <= 100.0`, which is `False`, and returns `False`. The second `assert` checks `False == False`, which also holds. Both assertions passed silently, so the program reaches the final line and prints `both checks passed`, and nothing else.
</Reveal>
