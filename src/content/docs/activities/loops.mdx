This activity puts into practice the [Loops](/lectures/loops/) lecture. You will predict the output of a `for` loop over a range and a `while` loop that breaks early, trace a `while` loop by hand one pass at a time, and fix a Rust loop that refuses to compile. By the end, you will be able to work out where a half-open range stops, follow a loop variable until its condition turns false, and read the compiler error that a loop counter without `mut` produces.

## Warm-up

A quick refresher before the blocks. A `while` loop runs its body while a condition stays true, and a `for` loop walks a variable through the values of a range. Here is the smallest example of each, back to back, in both languages.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="warmup.py"
count = 1
while count <= 3:
    print(count)
    count = count + 1
for i in range(3):
    print(i)
```
</TabItem>
<TabItem label="Rust">
```rust title="warmup.rs"
fn main() {
    let mut count = 1;
    while count <= 3 {
        println!("{}", count);
        count = count + 1;
    }
    for i in 0..3 {
        println!("{}", i);
    }
}
```
</TabItem>
</Tabs>

```bash title="Run the Python program"
python3 warmup.py
```

```text frame="terminal" title="Output"
1
2
3
0
1
2
```

Rust prints the same six lines. The `while` counts `1` to `3` and stops when `count` reaches `4`, and the `for` walks `range(3)` and `0..3`, which are the three values `0, 1, 2`. With those two shapes fresh, the blocks below make the stopping point and the number of passes harder to guess.

## Block 1: Predict the Passes

The value that trips people up in a loop is the last one: exactly where a range stops, and exactly which pass a `break` cuts off on. You commit to an answer first, then run each program to check it. Read both programs below and write down, on paper or in a comment, every line each one prints, in order. Do not run them yet.

The first program uses `continue` to skip a single pass. Watch what the range does at its top end, and note that Python and Rust do not spell the range the same way.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="skip.py"
for i in range(5):
    if i == 2:
        continue
    print(i)
```
</TabItem>
<TabItem label="Rust">
```rust title="skip.rs"
fn main() {
    for i in 0..=5 {
        if i == 2 {
            continue;
        }
        println!("{}", i);
    }
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal both outputs and why they differ">
```bash title="Run the Python program"
python3 skip.py
```

```text frame="terminal" title="Output"
0
1
3
4
```

```bash title="Compile and run the Rust program"
rustc skip.rs
./skip
```

```text frame="terminal" title="Output"
0
1
3
4
5
```

In both programs, `continue` skips only the pass where `i` is `2`, so `2` is missing from each output while every other value prints. The two do not end at the same number, though, and that is the point. Python's `range(5)` is half-open: it starts at `0` and stops just before `5`, so its last value is `4`. Rust's `0..=5` is the inclusive form written with the equals sign, so it runs from `0` all the way through `5`, and its last value is `5`. If you predicted the Rust loop would also stop at `4`, you read `0..=5` as if it were `0..5`; the `=` is exactly the difference between the two.

<WhatDiffers>
<Fragment slot="differs">
Both loops step the loop variable through a range one value at a time, and both use `continue` the same way, to skip the rest of the body on a single pass without ending the loop. What differs is the top of the range. Python's `range(5)` excludes its stop value, so it covers `0` through `4`. Rust's `0..=5` uses the inclusive form, so it covers `0` through `5` and prints one extra line. The half-open `0..5` in Rust would have matched Python exactly.
</Fragment>
</WhatDiffers>
</Reveal>

The second program is a `while` loop that leaves early with `break`. The counter starts at `0` and the condition allows up to ten passes, but the `break` never lets it get that far. Write down what it prints before opening the reveal, and watch the order of the two lines inside the loop.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="stopearly.py"
n = 0
while n < 10:
    n = n + 1
    if n == 4:
        break
    print(n)
```
</TabItem>
<TabItem label="Rust">
```rust title="stopearly.rs"
fn main() {
    let mut n = 0;
    while n < 10 {
        n = n + 1;
        if n == 4 {
            break;
        }
        println!("{}", n);
    }
}
```
</TabItem>
</Tabs>

<Reveal label="Reveal the real output and reconcile it with your prediction">
```bash title="Run the Python program"
python3 stopearly.py
```

```text frame="terminal" title="Output"
1
2
3
```

Rust prints the same three lines. The counter `n` is bumped up at the very top of the body, before anything is printed, so the printed value is always one more than the value the pass started with. On the first pass `n` goes from `0` to `1`, the `if` is false, and `1` prints. The next two passes print `2` and `3` the same way. On the fourth pass `n` becomes `4`, the condition `n == 4` is now true, and `break` runs: the loop stops at once, so the `print` on the last line never runs for `4`. The condition `n < 10` would have allowed six more passes, but `break` overrode it. If you predicted the output ran up to `9`, or included `4`, you missed that `break` ends the loop the instant it runs, before the rest of the body.
</Reveal>

## Block 2: Trace the While by Hand

An exam asks you to say what a loop prints without running it, and the only reliable way is to trace it: track the loop variable and re-check the condition at the top of every pass, exactly as the machine does. The loop below multiplies its variable instead of adding, so the stopping point is not obvious at a glance. You will build the trace by hand.

<Tabs syncKey="lang">
<TabItem label="Python">
```python title="grow.py"
n = 1
while n < 20:
    print(n)
    n = n * 3
```
</TabItem>
<TabItem label="Rust">
```rust title="grow.rs"
fn main() {
    let mut n = 1;
    while n < 20 {
        println!("{}", n);
        n = n * 3;
    }
}
```
</TabItem>
</Tabs>

Do not run it yet. Trace it on paper with these steps.

<Steps>

1. Write `n = 1`, the starting value, at the top.

2. For each pass, write the condition `n < 20` with the current value filled in, and mark it true or false.

3. If it is true, write down the value that `print` outputs, then compute the new `n` from `n = n * 3` and carry it to the next pass.

4. Stop the first time the condition is false. The output is every value you wrote in step 3, in order.

</Steps>

<Reveal label="Reveal the completed trace">
| Pass | `n` at the check | `n < 20` | Prints | `n` after `n = n * 3` |
|---|---|---|---|---|
| 1 | 1 | `1 < 20` is true | `1` | 3 |
| 2 | 3 | `3 < 20` is true | `3` | 9 |
| 3 | 9 | `9 < 20` is true | `9` | 27 |
| 4 | 27 | `27 < 20` is false | nothing, loop ends | |

The loop prints `1`, then `3`, then `9`, and stops. The fourth check is the one that ends it: by then `n` is `27`, the condition `27 < 20` is false, so the body does not run a fourth time and nothing more prints. Run both programs to confirm.

```bash title="Run the Python program"
python3 grow.py
```

```text frame="terminal" title="Output"
1
3
9
```

```bash title="Compile and run the Rust program"
rustc grow.rs
./grow
```

```text frame="terminal" title="Output"
1
3
9
```

The value `27` never prints, even though the pass that produced it started with the printed `9`. The condition is only checked at the top of a pass, so the loop always takes one extra look that comes out false and ends it. Missing that final check is the most common way a hand trace lands one value too long.
</Reveal>

## Block 3: Fix the Loop That Will Not Compile

This loop is meant to print `0`, `2`, `4` by stepping a counter up by two, but the Rust version refuses to compile. There is no wrong output to inspect, because the program never runs. You diagnose it with the systematic method: read the error, form a hypothesis, test it.

```rust title="stepbug.rs"
fn main() {
    let step = 0;
    while step < 5 {
        println!("{}", step);
        step = step + 2;
    }
}
```

<Reveal label="Reveal the diagnosis and the fix">
```bash title="Compile the broken program"
rustc stepbug.rs
```

```text frame="terminal" title="Output"
error[E0384]: cannot assign twice to immutable variable `step`
 --> stepbug.rs:5:9
  |
2 |     let step = 0;
  |         ---- first assignment to `step`
...
5 |         step = step + 2;
  |         ^^^^^^^^^^^^^^^ cannot assign twice to immutable variable
  |
help: consider making this binding mutable
  |
2 |     let mut step = 0;
  |         +++
```

**Symptom.** There is no output at all; the compiler rejects the program with error `E0384`, "cannot assign twice to immutable variable `step`," and points at the line `step = step + 2` inside the loop.

**Hypothesis.** The loop body reassigns `step` on every pass to move it toward the boundary, but `step` was declared with plain `let`, which makes it immutable. Rust forbids reassigning an immutable variable, and the compiler even shows the first assignment on line 2 as the binding it will not let you change. The fix the compiler suggests is to declare the counter mutable with `let mut`.

**Test.** Add `mut` to the declaration so the body is allowed to update the counter:

```rust title="stepbug.rs (fixed)"
fn main() {
    let mut step = 0;
    while step < 5 {
        println!("{}", step);
        step = step + 2;
    }
}
```

```bash title="Compile and run the fixed program"
rustc stepbug.rs
./stepbug
```

```text frame="terminal" title="Output"
0
2
4
```

The single word `mut` is the whole fix. A loop counter has to change on every pass, or the condition would stay true forever and the loop would never stop; Rust requires you to mark that a variable will change, and turns a counter you forgot to make mutable into a compile error before the program can run. Python has no such rule, so the same loop written in Python needs no equivalent keyword.
</Reveal>

## Bridge

These three reps feed the recitation family where a loop drives a piece of changing state to a boundary and stops there: a counter walked through a range, or a condition re-checked at the top of each pass until it turns false, sometimes with several such loops nested so one sweeps a whole grid of values for each step of another. The by-hand tracing and the where-does-it-stop prediction you practiced here are the guided first rung of that ladder.
